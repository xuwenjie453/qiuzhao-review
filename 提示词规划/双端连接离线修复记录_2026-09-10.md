# 双端连接离线修复记录（2026-09-10）

> 一句话结论：iPad 一直「离线」的根因是 **daemon 被强杀未发 Bonjour goodbye 包，iPad 系统 mDNS 缓存残留死地址（旧端口）**；对 daemon 做**优雅重启**（SIGTERM 后重启）即自愈，iPad 秒级自动重连。**全程无数据丢失**。

## 2. 根因链

```text
daemon 强杀(无 Bonjour goodbye 包)
  → iPad mDNSResponder 系统缓存残留旧 SRV 记录(端口 52721, TTL 内不失效)
  → App 的 NWBrowser 从系统缓存解析到死地址
  → WS 连接失败 → SyncEngine 停在 cachedOffline("离线 · 显示本地内容")
  → App 层重启不触发系统缓存失效 → 表现为"重启也连不上"
```

关键认知：**Bonjour 服务实例名不变（daemon_id 稳定），只换端口时，iPad 缓存更容易拿旧记录**。App 内的发现循环不会主动清系统缓存。

## 3. 修复步骤（下次照抄）

```bash
# 1) 确认 Mac 侧四项全绿（IP/监听/防火墙/Bonjour 可发现）——先排除 Mac 自身问题
node DualEnd-Mac/bin/qreview-dual.mjs daemon status
lsof -nP -i :<bridge_port>                                   # 端口在听
/usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate
dns-sd -B _qiuzhaoreview._tcp local.                          # 4 秒内能看到服务即广播正常

# 2) 看 daemon 日志有无连接尝试：零尝试 = 问题在 iPad 侧发现层（本案例位置）
系统数据/dual-end/logs/*.log

# 3) 决定性修复：优雅重启 daemon（发 goodbye 包让 iPad 缓存失效）
kill -TERM <daemon_pid>          # 不要 kill -9！强杀等于复现故障
# 确认进程清零后，以脱离方式重启（教训见 §5-③）：
nohup node DualEnd-Mac/bin/qreview-dual.mjs daemon start >> 系统数据/dual-end/logs/daemon.log 2>&1 & disown

# 4) 验证：15 秒内 sessions 应变 1；再确认 journal 有新写入（实时同步）
node DualEnd-Mac/bin/qreview-dual.mjs daemon status | grep sessions
sqlite3 系统数据/dual-end/state/dual-end.db "SELECT max(server_seq), max(committed_at) FROM sync_journal;"
```

## 4. devicectl 真机调试工具箱（本次实测有效）

前置：iPad 与 Mac 同网 Wi-Fi；`xcrun devicectl list devices` 显示 `available (paired)` 即可达（本案例 transportType=localNetwork，无需插线）。

```bash
DEV=AD98BAD8-7CB8-5EE3-AC86-8517E419613F   # 设备 ID 会变，以 list devices 实测为准
APP=local.qiuzhaoreview.ipad2（2026-09-11 起新 Bundle ID，旧容器已随旧 App 卸载消失）

# 拉取 App 数据（只读，不碰用户数据）：
xcrun devicectl device copy from --device $DEV --domain-type appDataContainer \
  --domain-identifier $APP --source "Library/Preferences/local.qiuzhaoreview.ipad.plist" --destination /tmp/prefs.plist
#   ↑ 判据：有 dualend.preferred_daemon 键 = 历史上成功连过（注意 cfprefsd 可能延迟落盘，缺键不是铁证）
xcrun devicectl device copy from --device $DEV --domain-type appDataContainer \
  --domain-identifier $APP --source "Library/Application Support/QiuZhaoReader/client-store.sqlite" --destination /tmp/store.sqlite
#   ↑ 金矿：outbox(待发队列)/ink_cache(笔迹)/inbox_dedup(收到过多少事件)/graphs_cache

# 强制全新启动 App（重走发现流程；本案例证明这修不了系统缓存，但排障时有用）：
xcrun devicectl device info processes --device $DEV | grep -i qiuzhao   # 找 pid
xcrun devicectl device process terminate --device $DEV --pid <pid> --kill
xcrun devicectl device process launch --device $DEV $APP

# 拉取诊断探针产物（Debug 构建）：
xcrun devicectl device copy from --device $DEV --domain-type appDataContainer \
  --domain-identifier $APP --source "Documents/hover-probe.jsonl" --destination /tmp/hover-probe.jsonl
```

本次 Xcode 版本无 `device console` 子命令；unified log 需 `sudo log collect --device-udid`（交互式密码，Agent 环境不可用）——所以**iPad 端日志主要靠拉容器内文件反推**。

## 5. 教训清单

① **判"离线"先分侧**：Mac 四项全绿 + daemon 日志零连接尝试 = iPad 侧发现层问题，别在 Mac 侧瞎折腾。

② **强杀 daemon 是禁忌**：`kill -9`/终端直接关 = 无 goodbye 包 = 复现本故障。一律 `kill -TERM`，确认进程退出后再重启。

③ **daemon 必须脱离会话启动**：挂在 AI 会话/终端 shell 下，会话结束或停后台任务时会被连带杀死（本次 13:06 实际发生）。用 `nohup … & disown`，日志重定向到 `系统数据/dual-end/logs/`。

④ **iPad 数据没丢的判据**（断线后先查，安人心）：canonical `dual-end.db` 的 `ink.blob_sha256` 与 iPad outbox `payload_json$.blob_sha256` 对得上 → 数据已到，只是 ACK 丢了。

⑤ **良性报错识别**：daemon 日志 `UNIQUE constraint failed: sync_journal.message_id` = iPad 僵尸 outbox 重放被正确去重，**无害**（本次仅 1 次）。数据完整性以 canonical 库为准，不以此报错为故障信号。

## 6. 遗留问题（不阻断，明确不修）

- iPad 本地 3 条僵尸 outbox 记录（rev 123/124/125，内容均已在 canonical）：每次重连重放一次，daemon 去重报错一次。彻底清除需改 daemon 代码（对 journal 已有 message_id 回「已收过」ACK 而非抛错）——属系统改动，用户发话才做。
- `sync_journal.message_id` 存的是 daemon 侧分配的消息号，与客户端 outbox 的 message_id 不同源；今天 12:24:38 的入库记录（seq 603–605）与 outbox 三条对不上号即是此因。排查数据时以 blob_sha256/revision 对账，勿用 message_id 跨库对账。

## 9. 复发补记（2026-09-11 14:39）：触发因不止"强杀"——Mac 隔夜换 IP 同样致病，同一招通杀

**现象**：次日午后再现"iPad 离线"。与首例的差异：daemon 全程存活、端口未变、无强杀。

**取证**：
- `daemon status` READY、sessions=0；日志自昨 16:55 后零连接尝试 → 同signature：Mac 侧正常，iPad 发现层不通
- `ifconfig en0`：**Mac IP 隔夜由 192.168.1.200 变为 192.168.1.199（DHCP 重新分配，Mac 睡眠跨夜）**
- `xcrun devicectl list devices`：iPad `unavailable`（仅说明开发者隧道未激活，iPad 锁屏休眠所致；**不代表 Wi-Fi 不通**，勿被误导）

**修复**：同一招 `kill -TERM` 优雅重启 daemon → 15 秒内 sessions=1，iPad 自动重连。

**结论升级**：本故障是一类问题——「**Mac 侧网络身份变化（强杀换端口 / DHCP 换 IP / 睡眠唤醒后 mDNS 重注册延迟）+ iPad mDNS 缓存陈旧 → App 停在 cachedOffline**」。修复动词唯一：**优雅重启 daemon**（goodbye + 新公告让缓存失效）。Mac 睡眠跨夜后 iPad 离线，优先怀疑 IP 变了，先 `ifconfig` 对比再动手。


## 10. 大修记录（2026-09-11 下午）：Apple 账号更换引发的连环修复

**起因**：用户更换 iPad 的 Apple 账号 → ① 旧团队开发描述文件被用户在「VPN与设备管理」手动删除 → 旧 App（local.qiuzhaoreview.ipad）失效；② 开发者配对/开发者模式状态被动 → devicectl 长时间 unavailable；③ 旧 Bundle ID 被旧团队占用，新账号无法注册（Xcode 报 "cannot be registered ... not available"）。

**修复链（按序，全部实证）**：
1. USB 直连 + 解锁 → 「信任此电脑」（弹窗不出现时：拔插线 / 开「USB 配件」开关 / 还原定位与隐私）
2. 设置 → 隐私与安全性 → **开发者模式重新开启 + 重启 iPad**（换账号后模式仍显示 enabled 但隧道起不来的，重启即恢复 connected）
3. 新 Bundle ID `local.qiuzhaoreview.ipad2` + 真实团队：**从钥匙串证书猜团队 ID 会翻车**（证书 OU 可能是历史加入过的团队，非当前个人团队）。正确姿势：在 Xcode Signing 页手选 Team，Xcode 会把真实 ID 写回 pbxproj（本案真身 = 6R3PZDAJGW，与项目原值相同）
4. 「团队无设备」报错：**用具体设备做构建目标自动注册**：`-destination 'platform=iOS,id=<UDID>' -allowProvisioningUpdates`（比 generic + Xcode 点 Try Again 可靠）
5. 卸载旧 App（连带僵尸 outbox 一并消失）→ 安装新版 → 启动即连，快照同步成功（journal GRAPH_SNAPSHOT #684），**连接循环彻底消失**（30 秒日志零增长）

**诊断修正（重要）**：之前 §8/毒丸理论需要修正——全新空容器的 App 首连也在日志出现一次 `UNIQUE constraint failed: sync_journal.message_id`，且紧随其后的 GRAPH_SNAPSHOT 正常入库。结论：该报错与客户端僵尸无关，是 daemon 对「新客户端快照请求」重放既有消息时的 journal 重复插入，**一次性、良性、不影响快照送达**；早先的"连接死循环"更可能是旧 App 失效 + mDNS 缓存陈旧的复合症状，而非单纯 outbox 中毒。

## 11. 随身 WiFi 移动协议（2026-09-11 定，用户指令）

**背景**：家用路由是随身 WiFi（LTE CPE），会被用户整体拿走/放回。拿走 = 全网消失（Mac 与 iPad 同时断网）；放回 = 网络重建，但 iPad 的 mDNS 缓存与 App 重连循环易卡死在离线态（2026-09-11 第四次离线的根因，静态绑定本身工作正常）。

**协议（AI 必须遵守）**：

| 用户说 | AI 做 |
|---|---|
| "要把随身 WiFi 拿走了" | `kill -TERM <daemon_pid>` 优雅停止 daemon（发 Bonjour goodbye），确认进程清零后回复"已优雅停止" |
| "随身 WiFi 放回来了" | `nohup node DualEnd-Mac/bin/qreview-dual.mjs daemon start >> 系统数据/dual-end/logs/daemon.log 2>&1 & disown` → 确认 READY → 提示用户把 App 划掉重开（或 USB 在线时由 devicectl 代杀重启）→ 验证 sessions≥1 |

**已知行为（未修，等用户授权）**：App 在「网络整体消失又恢复」后不会自愈重连（Bonjour 浏览只在启动时跑一次）。治标=重启 App；治本=App 回前台时强制重新发现+连接（一行级改动，属系统代码修改，需用户明确授权）。

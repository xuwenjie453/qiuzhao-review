# 02 — 根因分析与不可破坏契约

本文件冻结本 Bug 的技术判断与修复边界。实现型 AI 必须先理解这里的状态依赖关系，再修改代码。

## 1. 当前状态流

问题图中存在两套完全不同的位移语义：

### A. Node position

节点视觉位置来自：

```text
state.dragTransient[nodeId]
    ?? state.pendingPositions[nodeId]
    ?? canonical node.layout
```

含义：

- `dragTransient`：当前手指拖动帧的瞬时节点位置；
- `pendingPositions`：本地已 durable、等待 server ACK 的 canonical move；
- `node.layout`：server canonical layout。

这条链属于“节点布局”。

### B. Viewport position

画布局部 viewport 来自：

```text
committedCanvasOffset
+ canvasDragTranslation
→ clampedViewportOffset(...)
→ liveCanvasOffset
```

这条链属于“相机/视口”。

这两个状态域必须独立。

## 2. 当前 Bug 的耦合点

现实现中：

```text
baseNodeCenters
→ point(for: node)
→ normalizedPosition(for: node)
→ dragTransient 优先
```

于是 viewport clamp 的 bounds 会使用正在拖动中的节点瞬时位置。

设：

```text
O = committed viewport offset
N(t) = 正在拖动节点的 transient position
B(N) = 根据 node centers 算出的 clamp bounds
```

当前每帧实际执行：

```text
O_live(t) = clamp(O, B(N(t)))
```

即使 canvas gesture translation 为 0，只要 `B(N(t))` 变化，`O_live(t)` 就可能变化。

因此：

> “Node Drag 时 Canvas 也在动”并不要求背景 DragGesture 真正产生 translation；仅 viewport clamp 的动态依赖就足以触发。

## 3. 为什么会表现为闪烁/抖动

`NodeShapeView` 为了支持 pan 后正确拖节点，会做逆变换：

```text
visual pointer position
- viewportOffset
→ graph-space position
→ normalized canonical/transient position
```

这是正确设计。

但若 `viewportOffset` 又被 Node Drag 自身间接改变，则形成闭环：

```text
拖节点
→ transient node position 变化
→ viewport clamp 变化
→ viewportOffset 变化
→ inverse transform 结果变化
→ transient node position 再变化
```

SwiftUI 每次状态变化都会重绘 pannable layer，因此视觉上可能表现为：

- 背景左右/上下微跳；
- 节点似乎被画布“拉回”；
- 连线抖动；
- 大幅拖动时整图明显跟随；
- 触点附近出现持续闪烁感。

## 4. 修复后的依赖图

必须改成：

```text
Node Drag visual position
    ↓
dragTransient
    ↓
node glyph + links

stable node position
    ↓
viewportConstraintCenters
    ↓
Canvas clamp bounds

Canvas gesture
    ↓
canvasDragTranslation
    ↓
liveCanvasOffset
```

关键是：

```text
dragTransient ─X→ viewportConstraintCenters
```

## 5. Stable position 的定义

V1 推荐：

```text
stableNormalizedPosition
= pendingPositions ?? canonical layout
```

不使用 `dragTransient`。

原因：

- pendingPositions 已代表一次真实 Node Drag 结束后的本地 durable intent；
- 它不是当前手指每帧 transient；
- server ACK 前用户看到 pending layout 是合理的；
- canonical snapshot 到来后自然收敛。

如果实现者选择只使用 canonical layout 也能切断反馈环，但可能在 MOVE_NODE pending 期间让 pan bounds 暂时基于旧位置；因此优先使用 `pendingPositions ?? layout`。

## 6. 不可破坏的 Canvas Pan 契约

修复不能破坏这些已有能力：

1. Canvas offset 是纯 iPad local UI state；
2. blank drag 可平移整图；
3. links 与 nodes 共享同一 pannable layer；
4. Canvas Pan 不生成 `MOVE_NODE`；
5. graph 切换时 offset reset；
6. clamp 仍允许最边缘节点中心到达 viewport center；
7. pan 后 Node Drag 使用 inverse transform 写回 graph-space normalized position。

## 7. 不可破坏的 Node Drag 契约

1. CENTER 不可移动；
2. 非 CENTER drag 仍保留 grab offset，不能吸附到手指中心；
3. drag transient 只用于实时显示；
4. drag end 仍走原有 callback / store / outbox / MOVE_NODE；
5. pendingPositions 优先于 canonical layout 继续保持；
6. parent-child link 在 child/parent 被拖时实时更新。

## 8. Gesture ownership 契约

当前使用父层 `.simultaneousGesture(canvasPanGesture)` 并不天然错误。

允许保留 simultaneous gesture，条件是：

```text
canvasPanGesture 对 startLocation 命中 node 的 drag 全程不产生 pan translation/commit
```

不要根据“当前 location 是否还在 node 上”动态切换 ownership。

建议抽纯判断：

```swift
func canStartCanvasPan(at startLocation: CGPoint, viewportOffset: CGSize) -> Bool
```

语义：

```text
return !containsNode(at: startLocation, viewportOffset: viewportOffset)
```

`.updating` 和 `.onEnded` 都复用同一 ownership 规则。

## 9. 允许的进一步稳定化

如果测试证明仅排除 `dragTransient` 后仍存在“pan 过程中 snapshot 更新导致 clamp jump”，可以把 Canvas Pan 一次 gesture 的 constraint centers 在开始时冻结。

但这是二级增强，不要一开始就引入复杂 gesture state machine。

优先顺序：

1. 先切断 `dragTransient → clamp`；
2. 加回归测试；
3. 只有仍有稳定性问题时再冻结 pan-session bounds。

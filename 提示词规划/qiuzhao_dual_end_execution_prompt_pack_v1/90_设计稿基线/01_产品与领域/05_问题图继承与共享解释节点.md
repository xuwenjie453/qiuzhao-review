# 问题图继承与共享解释节点（V1 详细设计）

## 0. 设计目的

本设计为 QuestionGraph 增加 graph-to-graph inheritance，使 Review Probe QuestionGraph 可以继承其来源 Question Bank QuestionGraph 的持久解释节点。

核心目标：

1. 试题库问题图先产生；
2. 用户完成学习并达到 `LEARNING_VERIFIED` 后生成 Review Capsule；
3. Capsule 被调度并物化为 Review Probe QuestionGraph；
4. Review Probe graph 拥有自己的 CENTER；
5. Review Probe graph 直接访问来源 Question Bank graph 的 EXPLANATION；
6. inherited EXPLANATION 不复制，所有图共享同一 `node_id`；
7. 对 inherited EXPLANATION 的标题、布局、Ink 修改 write-through 到 canonical node；
8. 同一 Question Bank graph 可以被多个 Review graph 继承；这些 child graph 共享相同解释节点。

本设计不把 Review graph 变成 Question Bank graph 的副本；它定义的是 **live shared reference inheritance**。

---

## 1. 术语

### 1.1 Owner Graph

节点在 canonical store 中真正归属的 graph。

`nodes.graph_id` 在 V1 中继续保留字段名，但语义冻结为 `owner_graph_id`。

### 1.2 View Graph

用户当前在 iPad/Mac 打开的 graph。一个 view graph 可以展示自身 owned nodes，也可以展示继承得到的 EXPLANATION。

### 1.3 Effective Graph View

```text
EffectiveNodes(G)
= OwnedVisibleNodes(G)
+ InheritedExplanationNodes(G)
```

### 1.4 Inheritance Edge

QuestionGraph 到 QuestionGraph 的有向关系：

```text
child_graph --inherits--> parent_graph
```

V1 的 inheritance kind 固定为：

```text
SHARED_EXPLANATIONS
```

### 1.5 Shared Explanation

canonical owner 在 parent graph，但在 child graph effective view 中可见的 EXPLANATION。

## 2. 业务生命周期

### 2.1 Question Bank 学习阶段

```text
Question Bank Question
        ↓ question.open
QuestionGraph B
        ↓ 用户要求解释入图
B owns E1, E2, E3
        ↓ 学习通过
LEARNING_VERIFIED
        ↓ Review Probe Compiler
Review Capsule C
        ↓ Scheduler
Review Probe P
```

### 2.2 Review Graph 建立阶段

物化 Review Probe P 时：

```text
question.open(REVIEW_CAPSULE)
        ↓
create/open Review Graph A
        ↓
resolve primary source question
        ↓
resolve Question Bank Graph B
        ↓
ensure inheritance A -> B
        ↓
return effective snapshot(A)
```

结果：

```text
B:
  CENTER_B
  E1
  E2
  E3

A:
  CENTER_A
  [inherited] E1
  [inherited] E2
  [inherited] E3
```

A 与 B 的 CENTER 可以完全不同。

## 3. 数据模型

### 3.1 新表：graph_inheritance

Mac canonical SQLite 新增：

```sql
CREATE TABLE IF NOT EXISTS graph_inheritance(
  child_graph_id TEXT NOT NULL REFERENCES graphs(graph_id) ON DELETE CASCADE,
  parent_graph_id TEXT NOT NULL REFERENCES graphs(graph_id) ON DELETE CASCADE,
  inheritance_kind TEXT NOT NULL DEFAULT 'SHARED_EXPLANATIONS'
    CHECK(inheritance_kind IN ('SHARED_EXPLANATIONS')),
  created_at TEXT NOT NULL,
  PRIMARY KEY(child_graph_id, parent_graph_id),
  CHECK(child_graph_id <> parent_graph_id)
);

CREATE INDEX IF NOT EXISTS idx_graph_inheritance_parent
  ON graph_inheritance(parent_graph_id);
```

### 3.2 V1 cardinality

Schema 允许一个 child 对多个 parent，以保留未来扩展空间；但 Runtime V1 业务约束为：

- Question Bank graph 不自动继承任何 graph；
- Review graph 最多有一个 `primary parent`；
- parent 必须为 `QUESTION_BANK`；
- child 必须为 `REVIEW_CAPSULE`；
- 继承图禁止形成 cycle。

若未来允许多来源 Capsule，可通过升级运行规则开放多个 parent，无需再改 schema。

### 3.3 Capsule 来源锚点

现有 `review_capsules.source_questions` 是多值证据集合，不足以稳定表达 inheritance parent。

建议为 review_capsules 新增：

```text
primary_source_question_id TEXT nullable
```

语义：生成该 Capsule 的主要正式题来源。

规则：

- 若 Capsule 从一次明确 Question Bank 学习会话生成，必须写入；
- `source_questions` 继续保留全部来源证据；
- `primary_source_question_id` 仅承担 inheritance anchor；
- 若无法唯一确定，则不自动建立 inheritance，并记录诊断状态，不猜测。

## 4. 继承可见性规则

### 4.1 可继承节点

| Node Kind | 是否继承 | 原因 |
|---|---:|---|
| CENTER | 否 | child 有自己的中心问题 |
| EXPLANATION | 是 | 持久学习解释，应跨复习连续存在 |
| TEMPORARY | 否 | round scoped，不应跨会话传播 |

### 4.2 动态继承

Inheritance 记录关系，不记录复制后的 node 列表。

若 parent 后续新增 EXPLANATION：

```text
B initially: E1 E2
A inherits B
later B adds E3
```

A 下一次 effective snapshot 必须自动看到 E3。

禁止在 inheritance 创建时固化：

```text
A inherits [E1,E2]
```

### 4.3 Child 自有节点

Review graph 自己新增 Explanation：

```text
owner_graph_id = child graph
```

不会反向进入 parent，也不会自动传播到 sibling review graphs。

例如：

```text
B owns E1,E2
A1 inherits B, owns X1
A2 inherits B

A1 sees E1,E2,X1
A2 sees E1,E2
B  sees E1,E2
```

## 5. Canonical Mutation 语义

### 5.1 Rename

对 inherited EXPLANATION 执行 rename：

```text
child view -> node_id E1 -> canonical E1
```

直接更新 owner node 的 title 与 node_revision。

所有可见该 node 的 graph 最终一致看到新 title。

### 5.2 Move / Layout

Layout 是 canonical node-scoped。

对 inherited node 拖动，写同一个 `layouts[node_id]`。因此 parent 与所有 sibling child 共享位置。

这是 V1 的明确产品语义，不提供 per-graph layout override。

### 5.3 Ink

Ink 是 canonical node-scoped。

任何 graph 中对 shared EXPLANATION 的 Pencil 写入都更新同一 `ink[node_id]`。

Ink revision 单独演进，不进入 graph_revision。

### 5.4 Delete

V1 采用 **global delete** 语义：删除 inherited EXPLANATION 等价于删除 canonical owner node。

影响：

```text
B owns E1
A1,A2 inherit B
A1 delete E1
=> B/A1/A2 均不再显示 E1
```

iPad 必须对 inherited node 显示明确警告：

> 这是共享解释节点。删除会同时影响原题图及所有继承该节点的问题图。

V1 不实现“仅在当前 child 隐藏”的 exclusion override，以避免引入 per-graph tombstone/exception set。

## 6. Effective View 查询

### 6.1 Owned nodes

```sql
SELECT ... FROM nodes
WHERE graph_id = :graph_id
  AND deleted_at IS NULL
  AND (
    kind <> 'TEMPORARY'
    OR round_id = :active_round_id
  );
```

### 6.2 Inherited explanations

概念查询：

```sql
SELECT n.*
FROM graph_inheritance gi
JOIN nodes n ON n.graph_id = gi.parent_graph_id
WHERE gi.child_graph_id = :graph_id
  AND gi.inheritance_kind = 'SHARED_EXPLANATIONS'
  AND n.kind = 'EXPLANATION'
  AND n.deleted_at IS NULL;
```

### 6.3 Dedup

Effective view 按 `node_id` 去重。

即使未来多 parent 指向同一 shared node，也只能出现一次。

### 6.4 排序

建议返回：

1. owned CENTER；
2. inherited EXPLANATION，按 owner created_at / node created_at 稳定排序；
3. owned EXPLANATION；
4. current-round TEMPORARY。

UI 可以重新布局展示，但 wire payload 顺序必须 deterministic，便于测试。

## 7. Revision 模型

### 7.1 为什么 owner graph_revision 不够

当 shared node E1 被修改：

```text
B owns E1
A1,A2 inherit B
```

E1 title/layout/delete 变化会改变 B/A1/A2 的 effective structural view。

若只增加 B.graph_revision，A1/A2 的 snapshot revision 不变，则现有 Patch base/target 机制无法表达 child view 已变化。

### 7.2 Affected Graph Set

定义：

```text
AffectedGraphs(node)
= owner_graph(node)
+ all descendant graphs whose effective view includes node
```

V1 若只允许一层 QuestionBank -> Review，可直接取 owner + direct children；实现上建议写成可递归函数，为未来多层继承保留正确性。

### 7.3 Structural mutation

以下变更需要 touch affected graphs：

- ADD parent EXPLANATION；
- RENAME shared EXPLANATION；
- MOVE shared EXPLANATION；
- DELETE shared EXPLANATION；
- create/remove inheritance edge。

对每个 affected graph：

```text
graph_revision += 1
updated_at = now
```

随后按 graph_id 广播 patch 或 snapshot。

### 7.4 Ink

Ink 不增加任何 graph_revision。

Ink 通过现有 ink channel / revision 传播。

## 8. Snapshot / DTO

每个 snapshot node 增加视图元数据：

```json
{
  "node_id": "E1",
  "owner_graph_id": "B",
  "visibility": "OWN | INHERITED",
  "kind": "EXPLANATION",
  "title": "...",
  "body_markdown": "...",
  "node_revision": 4,
  "layout": {"x":0.2,"y":0.3,"revision":5}
}
```

Snapshot 顶层新增：

```json
{
  "graph_id": "A",
  "parent_graphs": [
    {
      "graph_id": "B",
      "inheritance_kind": "SHARED_EXPLANATIONS"
    }
  ]
}
```

`owner_graph_id` 是诊断与正确 mutation 路由的重要字段，不能只在 server 内部保存。

## 9. Command 语义

现有 client mutation 仍以 `node_id` 为 canonical target：

- RENAME_NODE
- MOVE_NODE
- DELETE_NODE
- INK_PUT

`graph_id` 继续表示用户发起操作时所在的 view graph，用于：

1. 权限/可见性验证：该 node 必须在该 graph effective view 中可见；
2. 诊断；
3. affected graph patch 选择。

Server 不应根据 command.graph_id 改写 node owner。

新增 Agent/local control command：

```text
graph.inherit
```

建议 payload：

```json
{
  "command_id": "uuid",
  "child_graph_id": "A",
  "parent_question_ref": {
    "source": "QUESTION_BANK",
    "question_key": "qb:Redis-01"
  },
  "inheritance_kind": "SHARED_EXPLANATIONS"
}
```

要求幂等：相同 child-parent relation 重复提交只产生一次 effect。

更推荐在 Review `question.open` 中允许 declarative `inherit_from`，由 QuestionGraphService 内部调用同一 inheritance service，减少 Agent 多步竞态。

## 10. Review Runtime 集成

### 10.1 Capsule Compiler

生成 Capsule 时写：

```text
primary_source_question_id
```

### 10.2 Review Engine / Runtime Prompt

Review Probe 物化前解析：

```text
capsule
 -> primary_source_question_id
 -> qb:<id>
 -> QuestionBank graph B
```

然后 `question.open` Review graph A，并声明/确保：

```text
A inherits B
```

### 10.3 Parent graph 尚不存在

若正式题从未进入双端 QuestionGraph，禁止创建“空壳 parent”并伪造历史解释。

两种允许策略：

- 无 inheritance 打开 Review graph，并记录 `parent_graph_missing`；
- 如果 Question Bank graph identity 可安全创建且 CENTER source snapshot 可获得，可创建，但不得生成任何 Explanation。

V1 推荐第一种，保持事实性。

## 11. iPad 交互语义

### 11.1 视觉

Inherited EXPLANATION 保持圆形，不新增第四种 NodeKind。

可增加轻量 inherited badge/链路标记，但不应让用户误以为这是节点副本。

### 11.2 Reader

Double tap inherited node 后仍走：

```text
ReaderRoute(node_id)
```

因为 body 与 Ink 都以 canonical node_id 读取。

### 11.3 Rename/Move/Ink

对 inherited node 与 own Explanation 使用同样交互；无需“复制后编辑”。

### 11.4 Delete

Inherited node 管理 sheet 必须展示共享影响警告，再允许提交 global delete。

## 12. iPad Cache 正规化

现有 `nodes_cache(node_id PRIMARY KEY, graph_id ...)` 同时承担 canonical node 与 graph membership，无法表达同一 node 出现在多个 graph。

V1 目标 schema：

```sql
CREATE TABLE nodes_cache(
  node_id TEXT PRIMARY KEY,
  owner_graph_id TEXT NOT NULL,
  kind TEXT NOT NULL,
  title TEXT NOT NULL,
  body_markdown TEXT NOT NULL,
  node_revision INTEGER NOT NULL,
  x_norm REAL NOT NULL,
  y_norm REAL NOT NULL,
  layout_revision INTEGER NOT NULL,
  locally_deleted INTEGER NOT NULL DEFAULT 0,
  updated_at TEXT NOT NULL
);

CREATE TABLE graph_node_membership_cache(
  graph_id TEXT NOT NULL,
  node_id TEXT NOT NULL,
  visibility TEXT NOT NULL CHECK(visibility IN ('OWN','INHERITED')),
  PRIMARY KEY(graph_id,node_id)
);
```

Ink 继续：

```text
ink_cache(node_id PRIMARY KEY,...)
```

无需按 graph 复制。

Snapshot apply 应原子完成：

1. upsert graph；
2. upsert canonical nodes；
3. replace 当前 graph membership；
4. 保留其他 graph membership；
5. durable 后 ACK。

## 13. Patch 传播

Shared node structural mutation 后，server 对当前连接 iPad 的 active/eager-cached graph 发送对应 graph patch。

若一次 mutation 影响多个 graph，可以产生多个 GRAPH_PATCH，每个 patch 使用各自 graph 的 base/target revision。

若 client 当前只 active 一个 graph，至少必须保证 active graph 收到更新；其他 graph 可在再次打开时通过 snapshot 收敛。

V1 推荐 server 对所有受影响 graph 写 durable journal；实时 push 可以只发给 session 当前订阅/active graph，避免无意义流量。

---

## 14. Cycle 与非法关系防护

`graph.inherit` 必须拒绝：

- child == parent；
- parent 不存在；
- child 不存在；
- child source != REVIEW_CAPSULE（V1）；
- parent source != QUESTION_BANK（V1）；
- relation 会形成 cycle；
- unsupported inheritance_kind。

建议错误码：

```text
GRAPH_INHERITANCE_INVALID_SOURCE
GRAPH_INHERITANCE_SELF
GRAPH_INHERITANCE_CYCLE
GRAPH_INHERITANCE_PARENT_NOT_FOUND
```

---

## 15. 删除 Graph / Parent 可用性

V1 不提供 graph delete 产品操作，因此无需定义 parent graph 被主动删除后的级联 UI。

数据库 FK 使用 `ON DELETE CASCADE` 清 inheritance relation，仅作为数据清理保护。

---

## 16. 迁移原则

旧数据没有 inheritance，不需要迁移 existing nodes。

Mac schema 从 v1 升为 v2：

- 新建 graph_inheritance；
- `nodes.graph_id` 不改列，只更新语义文档；
- existing graph revision 保持；
- existing Review graph 不自动猜 parent。

只有可由 Capsule `primary_source_question_id` 明确解析的 Review graph 才可补建 relation。

禁止根据 `source_questions[0]` 批量猜测历史 parent。

## 17. 必须测试的不变量

### Domain

1. child CENTER != parent CENTER，且 parent CENTER 不出现在 child effective view。
2. TEMPORARY 永不继承。
3. EXPLANATION inherited 时 node_id 不变。
4. parent 新增 Explanation 后 child 下次 snapshot 自动可见。
5. child 新增 Explanation 不出现在 parent/sibling。
6. 多 child 可共享同一 parent Explanation。

### Mutation

7. child rename inherited node 后 parent/sibling 同 title。
8. child move inherited node 后 parent/sibling 同 layout。
9. child Ink 写入后 parent/sibling 读取同 ink revision/blob。
10. child delete inherited node 后所有 graph 均不可见。
11. stale node/layout revision 仍触发现有 CAS 冲突。

### Revision / Sync

12. shared structural mutation 使所有 affected graph revision 单调 +1。
13. 每个 affected graph patch 的 base/target 连续。
14. patch base mismatch 仍 snapshot recover。
15. duplicate graph.inherit one effect。
16. reconnect 后 inherited membership 可由 snapshot 完整重建。

### Migration

17. v1 DB 升级不改变 existing graph/node/ink 数据。
18. 没有明确 parent 的旧 Review graph 保持独立，不猜测。

---

## 18. 明确非目标

V1 不做：

- arbitrary graph DAG UI；
- inherited node per-child title override；
- inherited node per-child layout override；
- per-child hide/exclusion；
- parent Explanation copy-on-write；
- Review child Explanation 自动反向合并到 Question Bank graph；
- 多 parent 的产品入口；
- 跨用户/跨设备账户级协同编辑。

---

## 19. 最终冻结语义

一句话定义：

> Review QuestionGraph 继承 Question Bank QuestionGraph 时，不复制父图，而是在自己的 CENTER 周围展示父图拥有的持久 EXPLANATION；这些 EXPLANATION 保持同一 canonical node identity，因此标题、布局与笔迹天然在原题图及所有继承图之间共享。

核心公式：

```text
Graph != exclusive Node[]

Graph View
= Owned Nodes
+ Referenced Inherited Explanations
```

这使首次学习与未来复习形成同一条连续的解释历史，而不是多个彼此孤立的问题图副本。

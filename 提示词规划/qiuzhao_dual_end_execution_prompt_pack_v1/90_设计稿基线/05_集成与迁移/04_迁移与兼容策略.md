# 迁移与兼容策略

> 本文已升级到 QuestionGraph Inheritance V1。目标是从当前已经上线的双端 v1 schema 平滑迁移，而不是重新初始化数据。

## 1. 总原则

迁移必须 additive、可回滚诊断、不得猜测历史关系。

现有 canonical 数据：

- graphs；
- rounds；
- nodes；
- layouts；
- ink；
- journal / dedup；

全部保留。

问题图继承只新增 relation 和 view semantics，不复制已有 node。

## 2. Mac Store schema 升级

当前 `SCHEMA_VERSION = 1`，实现时升级为 v2。

新增：

```sql
CREATE TABLE IF NOT EXISTS graph_inheritance(
  child_graph_id TEXT NOT NULL REFERENCES graphs(graph_id) ON DELETE CASCADE,
  parent_graph_id TEXT NOT NULL REFERENCES graphs(graph_id) ON DELETE CASCADE,
  inheritance_kind TEXT NOT NULL DEFAULT 'SHARED_EXPLANATIONS',
  created_at TEXT NOT NULL,
  PRIMARY KEY(child_graph_id,parent_graph_id),
  CHECK(child_graph_id <> parent_graph_id)
);
CREATE INDEX IF NOT EXISTS idx_graph_inheritance_parent
  ON graph_inheritance(parent_graph_id);
```

`nodes.graph_id` 不做 destructive rename；代码与文档把其语义解释为 `owner_graph_id`。

迁移过程不得改写：

- node_id；
- graph_id；
- node_revision；
- layout_revision；
- ink_revision；
- graph_revision。

## 3. Existing Graph 行为

所有升级前 graph 默认：

```text
parent_graphs = []
```

因此升级后 effective view 与升级前完全等价。

这是兼容性核心保证。

## 4. Existing Review Graph 不自动猜 Parent

现有 Review graph 即使 `question_source = REVIEW_CAPSULE`，也不能直接根据：

```text
source_questions[0]
```

猜 inheritance parent。

原因：`source_questions` 是证据集合，不等同于主来源。

只有满足以下条件之一才允许补建 relation：

1. Capsule 已有明确 `primary_source_question_id`；
2. 有不可歧义的历史事件/会话证据能证明来源，并由专用 migration 明确验证。

否则保持独立 Review graph。

## 5. Review Capsule schema 升级

三引擎 review_capsules 建议 additive 增加：

```text
primary_source_question_id TEXT NULL
```

现有 row 全部保持 NULL。

新 Capsule 若由明确 Question Bank learning flow 生成，则写入。

历史 NULL 不补猜。

## 6. iPad Cache schema 升级

旧：

```text
nodes_cache(node_id PK, graph_id,...)
```

新语义需要 canonical node 与 graph membership 分离。

建议迁移为：

```text
nodes_cache(
  node_id PK,
  owner_graph_id,
  ...
)

graph_node_membership_cache(
  graph_id,
  node_id,
  visibility,
  PRIMARY KEY(graph_id,node_id)
)
```

迁移旧 rows：

```text
owner_graph_id = old.graph_id
membership(graph_id=old.graph_id,node_id,visibility='OWN')
```

因此旧缓存在升级后视觉完全一致。

## 7. iPad Cache 可重建原则

iPad SQLite 是 durable cache，不是 canonical source。

若 migration 失败或 schema 不一致，允许：

1. 保留 outbox 安全数据；
2. 清理可重建 graph/node/membership cache；
3. 从 Mac snapshot 重建；
4. 重放未 ACK outbox。

不得以清 cache 为理由丢失本地未 ACK 用户 mutation。

## 8. Wire Protocol 升级

Snapshot node 新增：

```text
owner_graph_id
visibility
```

Snapshot 顶层新增：

```text
parent_graphs
```

建议 wire protocol `v` 升级一个 major/minor contract 版本；Mac 与 iPad 同版本交付。

若不实现旧 client 兼容窗口，则 daemon 在 HELLO 阶段对旧 protocol 明确 reject，并给出 upgrade-required，而不是让旧 client 错误解析 inherited snapshot。

## 9. Lazy Relation Creation

不要为所有 Question Bank graph 或 Capsule 批量创建 inheritance。

在 Review Probe 第一次 materialize/open 时：

```text
resolve capsule primary source
-> resolve existing parent graph
-> ensure relation
```

relation 创建必须幂等。

## 10. Parent Graph Missing

若 Capsule 有 `primary_source_question_id`，但对应 Question Bank graph 尚未存在：

V1 默认：

- Review graph 正常打开；
- 不建立 relation；
- 写诊断 `parent_graph_missing`；
- 不伪造 Explanation。

以后原题 graph 真正建立后，可以在下一次 Review open 时再次 ensure inheritance。

## 11. Rollback

因为 migration 是 additive，Mac rollback 可：

- 旧代码忽略 graph_inheritance；
- existing node 数据无格式破坏。

但一旦已经产生 inheritance-only UX，回退旧 client 会看不到 inherited nodes。因此产品发布上应把 Mac daemon + iPad client 作为同一兼容批次。

## 12. Migration 验收

必须覆盖：

1. v1 Mac DB -> v2 后 integrity ok；
2. existing graph effective view 不变；
3. existing node/layout/ink revision 不变；
4. existing Review graph parent 为空；
5. old iPad node rows 正确映射 OWN membership；
6. cache rebuild 不丢 outbox；
7. new inherited snapshot 可 durable apply；
8. rollback/旧代码不会破坏 canonical DB（但不承诺显示 inheritance）。

# 试题库最终纠错 QA 总控 Prompt

## 角色

你是一名严格的技术题库质量审计员。

当前题库已经完成大规模扩展。你的工作不是继续建设题库，而是：

> **发现并修复确定性错误，把现有题库变成稳定可长期使用的版本。**

`https://github.com/xuwenjie453/qiuzhao-review`

`试题库/`

- 制作模拟卷
- 做学习系统
- 把 QA 报告写进正式题库目录

这是**纠错工程，不是扩展工程**。

# 三、总策略

执行顺序：

```text
Phase 0 基线
→ Phase 1 结构全查
→ Phase 2 高风险全查
→ Phase 3 普通题分层抽约300
→ 统计明确错误率
→ 若 >=2%：升级2385题全库内容核验
→ 若 <2%：只修已发现错误
→ Phase 4 修复
→ Phase 5 第二批独立样本复验
→ Phase 6 最终结构复验
```

另有一个独立触发器：

> 一旦发现批量/系统性错误模式，不等待 2% 阈值，立即全查受影响范围。

---

# 四、错误处理总原则

只处理真正影响题库可信度的问题。

## 直接修

- 答案确定错误
- 计算结果确定错误
- SQL结果错误
- 代码输出错误
- 算法代码错误
- 解析中明确事实错误
- 题干转录错误且可恢复
- importance 明显荒谬

## 删除

- 关键题干无法恢复
- 关键图片/表格缺失且无法恢复
- 选项缺失导致无法作答
- 高度近义重复且没有额外训练价值

删除后：
- 同时删除 SQLite 记录
- 原 question_id 永久空缺
- 禁止补号/重编号

## 不自动改

- 版本口径存在真实争议
- 不同标准均可能成立
- 证据不足
- 只有风格问题

放入最终“争议题清单”。

# 五、Phase 0：基线

在任何修改前：

1. 记录当前 Git commit/hash；
2. 如可行，创建一个 QA 前备份提交或 tag；
3. 统计：
   - Knowledge
   - Algorithms
   - Projects
   - 总题数
   - SQLite记录数
4. 记录所有 Markdown 文件及最大题号。

不要在 `试题库/` 下新增基线文件。

---

# 六、Phase 1：结构层 100% 全查

这部分不抽样。

必须：

1. SQLite `PRAGMA integrity_check;`
2. 扫描全部 Markdown
3. Markdown ↔ SQLite 1:1
4. question_id 唯一
5. question_id 与文件路径一致
6. importance 与 Markdown 星级一致
7. question_text 对应完整题干
8. answer 对应 Markdown 答案
9. 无空题干
10. 无空答案
11. 无失效 markdown_path

SQLite 官方说明 `PRAGMA integrity_check` 会检查低层格式、缺页、索引以及 UNIQUE/CHECK/NOT NULL 等一致性错误；无错误时结果应为 `ok`。

# 七、Phase 2：高风险题全部检查

高风险题不计入普通 300 道样本。

必须全量：

## 408
全部 633 道。

## Algorithms
全部现有算法题（当前约173道）。

## 计算题
所有：

## 并发确定性题

## 残缺题候选

# 八、Phase 3：普通题分层抽约300

排除高风险题后，从普通题中分层抽约 300。

原则：

- Knowledge 各子类至少 3 道；
- 大子类按题量比例多抽；
- 小子类不能完全漏掉；
- Projects 额外抽约 30 道；
- Algorithms 已全查，不占样本额度；
- 使用固定随机 seed；
- 保存抽样列表到临时工作区，不放正式题库。

对样本逐题判断：

1. 题干能否正常作答？
2. 答案是否正确？
3. 解析是否存在实质性事实错误？
4. 是否存在多个明显正确答案？

---

# 九、明确错误率

只把以下情况计入“明确错误”：

- 答案错误
- 解析存在实质性事实错误
- 关键题干缺失
- 选择题无法唯一作答
- 题干与答案不匹配
- 算法代码错误
- SQL/代码输出错误

不计：

- 解析太短
- 文风不好
- 三星/四星分歧
- 单纯轻微重复
- 格式不够美观

---

# 十、2%升级机制

第一批普通样本约 300 道。

如果明确错误数：

`>= 6`

即：

`>= 2%`

立即升级：

> **对全部正式题目执行内容级逐题核验。**

即使错误率 < 2%，如果发现：
- 某 Markdown 批次连续错
- 某年408答案错位
- 某生成脚本造成统一错误
- 某批算法代码存在共同缺陷

也立即全查受影响范围。

---

# 十一、全库核验被触发时

对全部正式题逐题只回答四个问题：

1. 题干完整吗？
2. 答案正确吗？
3. 解析有实质性错误吗？
4. 应该保留、修复还是删除？

不要顺便：
- 润色
- 扩写
- 重分类

按 Markdown 文件逐个处理，处理完一个文件立即同步 SQLite。

---

# 十二、Phase 4：修复

## 答案错误
修改 Markdown + SQLite `answer`。

## 解析错误
只改错误句，不重写整段。

## 题干转录错误
若可从可靠原始题恢复，修复题干并同步 SQLite。

## 残缺且无法恢复
删除 Markdown 题 + SQLite记录。

## 高度重复
保留更完整题；质量相同保留较早 ID。

## importance
只修极明显异常。

## 争议题
不自动改，进入最终报告。

---

# 十三、权威资料优先级

QA 查证时：

- 网络协议：RFC/IETF
- Java：Oracle/OpenJDK
- MySQL：MySQL官方文档
- Redis：Redis官方文档
- Spring：Spring官方文档
- Python：Python官方文档
- AI/LLM：官方文档、论文、项目仓库
- 408：原始真题/PDF、可靠答案、教材逻辑交叉验证

不要优先使用营销文章修正题库。

例如 TCP `ssthresh` 初始值不应无条件写死为 64KB；RFC 5681说明其初始值应设置得足够高，而不是一个普适固定常数。

# 十四、Phase 5：第二批独立样本复验

修复完成后：

重新抽一批约 300 道普通题。

要求：
- 与第一批样本完全不重叠；
- 同样分层；
- 同样计算明确错误率。

如果第二批仍 >=2%：

> 继续全库核验/回查，不能宣布完成。

---

# 十五、Phase 6：最终结构复验

修复完成后再次：

1. `PRAGMA integrity_check;`
2. Markdown题数 = SQLite记录数
3. 无孤儿 Markdown
4. 无孤儿 SQLite
5. 无重复 question_id
6. importance 一致
7. markdown_path 全部有效
8. answer 一致
9. Algorithms 再全部运行一次

---

# 十六、完成标准

只有同时满足：

- 第二轮独立抽样明确错误率 < 2%
- 408 全查完成
- Algorithms 全查完成
- 计算题全查完成
- SQL结果题全查完成
- 代码输出题全查完成
- 残缺题候选全查完成
- 已确认错误全部修复
- 已确认无法作答题全部删除
- SQLite integrity_check = ok
- Markdown ↔ SQLite 严格1:1
- 无重复 question_id
- 不存在已知确定性错误

才可宣布 QA 完成。

少量真正无法确定的争议题可以保留，但必须在最终回复单独列出。

# 十八、核心纪律

1. 纠错，不扩题。
2. 修事实，不美容。
3. 题号永不变。
4. 确定性错误直接修。
5. 争议问题不擅自改。
6. 残缺且无法恢复就删。
7. 高风险全查。
8. 普通题先分层抽样。
9. 2%即升级全库。
10. 系统性错误不等阈值。
11. 修改必须同步 SQLite。
12. 最终目录结构冻结。

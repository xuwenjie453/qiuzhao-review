### RAG-001-001 | ★★★★★

完整描述一个 RAG 系统的工作流程。

**答案：**
分离线（Ingest）与在线（Query）两条链路。离线：①数据接入（文档解析：PDF/Word/HTML/表格，清洗去噪）→ ②切块（Chunking：按语义边界切分，带重叠）→ ③向量化（Embedding 模型编码每个 chunk）→ ④入库（向量库建立索引，保留原文与元数据）。在线：⑤查询处理（Query 改写/补全上下文）→ ⑥检索（向量相似度 TopK，常混合 BM25 关键词检索）→ ⑦重排（Rerank 精排取 TopN）→ ⑧提示组装（检索内容+系统提示+引用标记）→ ⑨生成（LLM 依据资料回答）→ ⑩评测与观测（命中率/忠实度/bad case 回流）。答题要点是讲出"每一环都可能出问题"：解析错、切块差、检索偏、重排弱、生成跑飞——RAG 工程本质是对这条流水线的持续治理。


### RAG-001-002 | ★★★★☆

RAG 解决什么问题？和微调怎么选？

**答案：**
RAG 解决四类问题：知识时效（训练截止后的新知识、频繁变更的知识）、私有知识（企业文档不进公网模型）、可溯源（答案附引用，可审计）、成本可控（无需训练，文档即改即生效）。微调解决的是"行为与风格"（K-LLM-008 的决策框架），二者的本质区别：RAG 改"模型能看到什么"，微调改"模型倾向怎么答"。判断口诀：问题答案是"某个具体事实/文档内容"→RAG；答案是"某种表达方式/任务格式"→微调；两者可叠加。RAG 的固有局限也要讲：检索不到就答不了（召回是天花板）、上下文长度限制注入量、多跳推理（跨文档组合）仍是弱项。


### RAG-001-003 | ★★★★★

文档切块（Chunking）有哪些策略？怎么平衡块大小？

**答案：**
策略从粗到细：①固定长度+重叠（最简单，如 500 token、重叠 50~100，重叠防语义被切断）；②按结构切分（Markdown 标题、段落、条款号——尊重文档天然边界，优先级高于固定长度）；③语义切分（相邻句向量相似度骤降处切分）；④父小子块（small-to-big：检索引小而精的子块，返回其父块/整节提供上下文）；⑤表格/代码特殊处理（表格整体一块+摘要描述，代码按函数切）。大小权衡：块太小→语义不完整检索不到；块太大→噪声稀释相关信号且占上下文。经验起点 300~800 token，实测调优；元数据（标题路径、章节、来源、时间）必须随块存储，检索后可过滤与溯源。


### RAG-001-004 | ★★★★☆

Embedding 模型是什么？怎么选型和评估？

**答案：**
Embedding 模型把文本编码为固定维度的稠密向量，语义相近的文本向量距离近（余弦相似度）——它是"语义检索"的地基。选型五看：①榜单基线（MTEB/C-MTEB 中文榜）划定候选；②业务语料自测——拿真实 query-文档对构建小评测集算召回率，比榜单可信；③维度与成本（维度高效果好但存储/计算贵）；④长文本支持（最大输入长度是否覆盖你的块大小）；⑤部署形态（商用 API vs 开源自托管，数据合规要求）。进阶选项：指令式 embedding（query 与 passage 加不同前缀）、多语言/跨模态模型。评估指标：给定标注对算 Recall@K / MRR，关注"真实业务问题的命中率"而非通用相似度对。换模型的连锁反应：向量要全量重建，所以 embedding 选型要留有余地、版本固化。


### RAG-001-005 | ★★★★☆

向量检索的召回质量差，你的排查和优化套路？

**答案：**
结构化排查：①先定性——标注 50~100 条 bad case 分类：该检索不到（库内没有/切块丢了）、检索到但排序靠后（rerank/相似度问题）、检索对但答错（生成问题）——三类问题药方完全不同；②该检索不到 → 查数据管道（解析丢内容、切块切断语义、未建索引），或换 query 改写补关键词；③排序靠后 → 上混合检索（BM25 兜住关键词精确匹配：型号、专有名词，向量对短/罕见词弱）、调 rerank、检查 query 与文档表达差异（口语 vs 书面）；④生成错 → 提示词约束引用、换模型。优化手段清单按性价比：查询改写 > 混合检索 > rerank > 切块调优 > 换 embedding > 微调。所有优化都必须在固定评测集上回归验证（K-PROMPT-004），避免拍脑袋。


### RAG-001-006 | ★★★★☆

什么是混合检索（Hybrid Search）？为什么需要？

**答案：**
混合检索=向量语义检索 + 关键词检索（BM25/倒排索引）并行召回再融合。必要性来自两者互补：向量懂语义（"怎么退货"命中"退换货流程"）但对**精确符号弱**——型号、错误码、人名、生僻术语在向量空间里区分度低甚至被平滑掉；BM25 精确匹配字面强但不懂同义改写。企业知识库大量查询是"精确名词"形态，纯向量召回经常翻车。融合方法：RRF（倒数排名融合，无需调分数纲，简单稳健）或加权分数归一融合。工程落地：ES/OpenSearch 8.x 原生支持 kNN+BM25 混合、或"向量库+ES"双路自研融合。加分认知：BM25 的分词/同义词配置同样是检索质量变量，中文要用合适的分词器。


### RAG-001-007 | ★★★★☆

Rerank（重排）是什么？为什么不直接用向量相似度排序？

**答案：**
召回（双塔/向量）与精排（rerank）的算力分工不同：向量检索把 query 和文档**独立**编码，索引可预建、检索毫秒级，但两段编码缺少交互，只能算"粗语义近邻"；Cross-Encoder rerank 把 query+文档**拼在一起**过模型，token 级交叉注意力能判断细粒度相关性，精度显著更高，但对每个候选都要跑一次模型，只能承受几十条的量。所以标准管线是"向量/BM25 粗召回 Top 50~200 → rerank 精排出 Top 3~10 进 prompt"。收益实测普遍显著（NDCG/命中率提升明显），是 RAG 链路里性价比最高的一环之一。选型：商用 rerank API、开源 bge-reranker 系列；延迟预算内候选数控制在 50~100。


### RAG-001-008 | ★★★☆☆

查询改写（Query Rewrite）和多路召回怎么做？

**答案：**
用户原始 query 常有四类毛病：口语化/省略（"那个怎么弄"）、多轮指代（"它的费用呢"）、一词多义、表达与文档不一致。改写手段：①指代补全与规范化——结合对话历史改写为独立完整问题（多轮 RAG 的必选项）；②同义扩展/关键词抽取——生成多个检索变体并行召回（多路召回）；③HyDE——让模型先生成一个假设性答案，用答案去检索（答案与文档的表述更接近）；④意图路由——先判断 query 类型（闲聊/查库/计算）再走不同链路，避免知识库硬答闲聊。多路召回：向量+BM25+同义词+结构化过滤并行，RRF 融合（K-RAG-006）。代价控制：每次改写多一次 LLM 调用，延迟敏感场景用小模型/规则做轻量改写。


### RAG-001-009 | ★★★★☆

RAG 系统怎么评测？有哪些指标和工具？

**答案：**
分层评测，检索与生成分开定位问题：检索层——Recall@K（正确文档是否被召回）、MRR/ NDCG（排序质量），需要标注"每个问题对应的标准文档"；生成层——忠实度/ groundedness（答案是否被检索内容支撑，防幻觉）、答案相关性（是否答到问题）、正确性（与标准答案比对）。工具：RAGAS（LLM 评审判忠实度/相关性/上下文利用率）、TruLens、自研跑批脚本（固定评测集+LLM 裁判+抽样人工校准，K-PROMPT-004 的方法论）。工程闭环：评测集从 bad case 持续回流；每次改切块/换模型/调 prompt 必跑回归；线上再配业务指标（采纳率、转人工率、引用点击率）形成离线+在线双层验证。一句话：RAG 是流水线，评测是流水线的"单元测试"。


### RAG-001-010 | ★★☆☆☆

GraphRAG 是什么？解决什么问题？

**答案：**
GraphRAG 在向量检索之上引入图结构：离线用 LLM 从文档抽取实体与关系（"张三—任职—A 部门"）构建知识图谱+社区摘要；在线检索时先实体识别，再沿图扩展多跳关联子图，把"结构化关联上下文"注入生成。解决向量 RAG 的两个短板：①全局性/汇总性问题（"这个项目的主要风险有哪些"需要跨全库聚合，局部相似检索捞不全）；②多跳推理（"A 公司的 CEO 的母校"需要两跳关联，向量相似度一跳召回难以覆盖）。代价：离线抽取成本高（全量 LLM 调用）、图谱质量依赖抽取精度、维护复杂。定位判断：知识有强关系结构、查询常涉多跳/全局聚合时才值得上；普通文档问答向量+混合检索足够——把它当拔高选项而不是默认架构。


### RAG-001-011 | ★★★★☆

多租户 RAG 的隔离设计

**答案：**
三级隔离按合规与成本选：物理隔离（每租户独立 collection/实例，最安全最贵）、元数据逻辑隔离（tenant_id 强制过滤，主流）、分区预过滤（按租户分片索引，过滤在 ANN 之前，召回不衰减）。铁律：过滤条件服务端注入、不信任前端参数；权限（部门/密级）与租户是两个维度叠加；跨租户检索默认禁止、白名单豁免。测试：越权用例（改 tenant_id、跨部门查询）进回归。

**解析：**
后置过滤的召回陷阱（TopK 全被不可见项占满）→ 预过滤设计（分区键=租户，K-VEC-005）。共享知识与私有知识的组织：公共库独立 collection + 合并检索，权限分别标注。审计：检索日志记租户/用户/查询/命中来源。


### RAG-001-012 | ★★★☆☆

向量相似度的几种度量方式？选哪种？

**答案：**
三种常用度量：余弦相似度（夹角，忽略模长，范围 -1~1）、内积 IP（点积，受向量模长影响——模长大者得分高）、欧氏距离 L2（空间直线距离，越小越近）。选型与 embedding 模型的训练目标绑定：模型用什么度量训练就用什么度量检索，混用会破坏排序——这是最重要的一句话。文本语义检索默认余弦（只关心方向/语义）；推荐系统常用内积（模长携带"热度"信息是有意为之）。归一化后的向量：余弦与内积单调等价，可用内积加速。工程上还要确认向量库的 metric 配置与模型一致（milvus/faiss 都要显式指定 metric type）。


### RAG-001-013 | ★★★★☆

向量索引的原理？HNSW 为什么快？

**答案：**
精确最近邻（暴力扫）在亿级向量上不可行，用近似最近邻（ANN）换速度。三大类：①HNSW（分层可导航小世界图）：多层跳表式图结构——上层稀疏长边快速"跳到目标区域"，下层稠密短边精细搜索，查询从顶层贪心下降；查询 O(logN) 级、召回率高，是默认首选；代价：内存占用大（存图）、构建慢、删除麻烦。②IVF（倒排文件）：先聚类成 N 个桶，查询只扫最近的 nprobe 个桶——省计算，召回受 nprobe 影响；常与 PQ（乘积量化，向量切子段压缩编码）组合成 IVF-PQ 压缩亿级数据到内存可承载。③ Flat 暴力：小集合（<百万）直接用，精确无召回损失。选型直觉：百万级以内 Flat/HNSW；亿级内存受限 IVF-PQ/磁盘索引（DiskANN）。


### RAG-001-014 | ★★★☆☆

主流向量数据库怎么选？

**答案：**
按"数据规模+运维能力+生态绑定"三条线选：①已用 ES/OpenSearch——直接用其 kNN（HNSW）+ BM25 混合检索（K-RAG-006），一体化免新增组件，千万级内够用；②数据在 PostgreSQL 生态/中小规模（百万~千万）——pgvector：SQL 一把梭、标量过滤天然强、事务一致性，团队心智成本最低；③亿级+高 QPS 专业场景——Milvus（存算分离、索引丰富、分布式）或云托管（阿里云 VectorRetrieval/Pinecone 类）；④轻量原型——Faiss（库不是服务，单机内存）或 Chroma/Qdrant（易上手）。决策反问：量级真到亿级了吗？多数企业知识库在十万~千万级，pgvector/ES 是更务实的选择。加分认知：向量库的核心考察点不止 ANN 算法——标量过滤下的召回、批量吞吐、副本高可用、与主数据的一致性同步，这些工程属性往往比算法差异更影响落地。


### RAG-001-015 | ★★☆☆☆

Embedding 模型是怎么训练出来的？（对比学习）

**答案：**
主流是对比学习：正样本对（query-相关文档）拉近、负样本对推远，损失函数常用 InfoNCE——把"匹配正确文档"当成从候选中分类的问题。训练数据三层：无监督共现（标题-正文、引用关系）、弱监督（搜索引擎点击对）、人工标注精标对。结构多为双塔（query/passage 分别编码），检索时可离线编码文档建索引；进阶蒸馏：用交叉编码器的打分教双塔模型（精度向效率蒸馏）。这层原理支撑两个工程判断：①为什么训练度量要一致（损失按某度量优化）；②为什么业务微调 embedding 有效——用领域正负对继续做对比学习即可（K-RAG-004 的进阶）。


### RAG-001-016 | ★★★☆☆

向量检索怎么和权限/标量条件结合？（企业落地必考）

**答案：**
企业场景向量检索必须回答"谁能看什么"。三种隔离强度：①物理隔离——按租户/部门分 collection/索引，最安全，成本高；②逻辑隔离——元数据字段（tenant_id、dept_path、密级）+ 检索时强制带过滤条件，注意过滤与 ANN 的交互（K-VEC-003 的过滤召回问题，选预过滤友好设计：分区键用租户）；③后置过滤——检索后过滤（错误做法：TopK 全被无权限项占满导致漏召回）。落地规范：过滤条件由服务端注入（从会话/权限系统取），绝不信任前端传参；权限模型复杂（数据行级权限）时，向量检索前先走权限系统拿到"可见集合"，再作为过滤条件下发；审计日志记录检索与命中。金融场景加分：密级+部门矩阵的双维过滤设计与测试用例。


### RAG-001-017 | ★★☆☆☆

多模态 Embedding 是什么？图片检索怎么实现？

**答案：**
多模态 embedding 模型（CLIP 及其后续）把图片和文本映射到**同一个向量空间**，实现"以文搜图/以图搜图"：训练时用图文对做对比学习，匹配的图文对拉近。应用侧：图片入库时编码存储；查询文本编码后在同空间检索。工程要点：①同空间才能跨模态互检，文本编码器和图像编码器是不同塔但共享空间；②中文图文检索选中文对齐的模型或商用 API；③文档场景常见组合：OCR+版面解析产出文本走文本 embedding，图表/图片用多模态模型生成描述（caption）再文本化，或直接多模态向量入库。图生文（VLM）描述方案更稳但丢失视觉细节，按业务取舍。


### RAG-001-018 | ★★☆☆☆

向量库的容量与性能怎么估算和优化？

**答案：**
内存估算公式要会：原始向量内存 ≈ 条数 × 维度 × 4 字节（float32）。例：1000 万条 × 1024 维 ≈ 40GB，再加 HNSW 图结构开销（约 10%~50%，与 M 有关）与标量/原文存储——这就是为什么亿级要 IVF-PQ 压缩或磁盘索引（K-VEC-002）。优化方向：①降维或量化（int8/PQ）压缩向量；②只存向量+ID，原文与元数据放主库按 ID 回查；③分 collection 分片控单索引规模。写入优化：批量 upsert（千条级 batch）、构建期先大批量导入后建索引（比边插边建快数倍）、增量更新走队列削峰。性能验证：压测真实 query 的 QPS/P99 与召回率抽样（对比暴力检索的 Recall），发布前出基线报告。


### RAG-001-019 | ★★★★☆

RAG 检索失败定位

RAG 系统答错，经查正确文档存在但未进入 Top-K，问题出在：

A. 生成模型幻觉
B. 检索层（召回/排序）——需优化切块、查询改写、混合检索或 rerank
C. Prompt 格式
D. 温度参数

**答案：** B

**解析：**
正确文档未召回/排序靠后是检索层问题；A 是"有据可查仍编造"型；C/D 影响输出不影响检索命中。

RAG 排障先分层：检索对了没有→生成对不对。

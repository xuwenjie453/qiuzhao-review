### InformationSecurity-001-001 | ★★★★☆

对称加密、非对称加密、摘要算法分别用在什么场景？密码怎么存？

**答案：**
三类工具各司其职：对称加密（AES-GCM）速度快，加密"数据"（报文体、落库敏感字段），难点是密钥分发与管理（KMS）；非对称（RSA/ECC）解决"密钥分发与身份认证"——TLS 握手、签名验签，慢，不用于大数据量；摘要（SHA-256/SM3）单向不可逆，用于完整性校验与指纹，配合 HMAC 做带密钥的签名。密码存储是"摘要的特化场景"：绝不能明文或普通 MD5/SHA——要用**慢哈希+自动加盐**的密码哈希算法（bcrypt/argon2/PBKDF2），它们内置盐、可调成本因子，抗彩虹表与暴力破解。国密要求场景：SM2（非对称）/SM3（摘要）/SM4（对称），金融央国企常考，知道对应关系即可。


### InformationSecurity-001-002 | ★★★★☆

SQL 注入、XSS、CSRF 的原理与防御？

**答案：**
SQL 注入：用户输入拼进 SQL 改变语义（`' or '1'='1`）。防御唯一正解是**参数化查询/预编译**（#{} 占位），ORM 也要防拼接（${} 是注入源）；纵深：最小权限账号、WAF、错误信息不暴露 SQL。XSS：恶意脚本注入页面被他人浏览器执行——存储型（入库）、反射型（URL）、DOM 型。防御：输出编码（按上下文 HTML/JS/URL）、CSP 内容安全策略、HttpOnly Cookie 降窃取危害、富文本白名单过滤（别用黑名单正则）。CSRF：借用户已登录 Cookie 伪造跨站请求。防御：SameSite Cookie（K-NET-008）、CSRF Token（表单/头携带服务端校验）、关键操作二次验证；JWT 放 localStorage 的系统天然免疫 CSRF 但承担 XSS 风险——取舍要能说。


### InformationSecurity-001-003 | ★★★★☆

开放 API 的接口安全怎么设计（签名、防重放、加密）？

**答案：**
开放接口四件套：①身份认证：AppKey/AppSecret 或 OAuth2 客户端凭证；②请求签名：对"方法+路径+排序后的参数+时间戳+nonce+body 摘要"计算 HMAC-SHA256 放入头，服务端同算法重算比对——防篡改与身份伪造（参数必须规范化排序，双方一致）；③防重放：时间戳窗口（±5 分钟）+ nonce 去重（Redis 记 nonce TTL=窗口，重复拒绝）；④敏感数据加密：HTTPS 保传输，字段级再 AES 加密（金融类）。增强：密钥定期轮换、私钥不落前端（前端防不了逆向，重要操作走服务端中转或设备级安全）、限流按 Key 配额（K-DIST-007）。答题主线：认证（你是谁）→ 完整性（没被改）→ 新鲜性（不是重放）→ 保密（看不懂）。


### InformationSecurity-001-004 | ★★★☆☆

日志应该怎么打？有哪些规范和红线？

**答案：**
三层规范：①级别语义——ERROR（需要人处理：失败+已影响）/WARN（可自愈但异常）/INFO（关键业务动作与状态变化，生产默认级）/DEBUG（诊断细节，按需开）；红线：catch 后只 printStackTrace、System.out.println、吞异常不打日志。②内容规范——结构化/键值化（traceId、userId、订单号、耗时、入参摘要），MDC 注入 traceId 全链路串联（K-MS-006）；参数化占位 `log.info("order={} paid", id)` 避免字符串拼接开销与 isDebugEnabled 判断。③安全红线（金融重点）——密码/证件号/银行卡/手机号必须脱敏（掩码或哈希），日志不得含 token/密钥/完整卡号（PCI 类合规硬要求）；日志异步化（AsyncAppender+队列丢弃策略）防 IO 拖垮主线程。


### InformationSecurity-001-005 | ★★★★☆

密钥与敏感配置的全生命周期管理

**答案：**
四个环节：存储——KMS/Vault 集中管理，代码与镜像零硬编码（CI 扫描拦截）；分发——运行时按需拉取（环境注入/_SIDE 注入），信封加密（数据密钥被主密钥加密）；轮换——定期+事件触发（人员变动/疑似泄漏）双轨，应用支持双密钥并存过渡；审计——访问日志可回溯、泄漏演练。本地开发用 .env+gitignore+示例文件占位；误提交的密钥视同泄漏立即轮换（git 历史删不干净）。

**解析：**
信封加密为什么：KMS 每次解密的 QPS 与延迟撑不住业务量，业务数据用数据密钥本地加解密，KMS 只管数据密钥。密钥分级：主密钥（KMS 内不出域）>密钥加密密钥>数据密钥。云上 KMS+RAM 权限最小化；自建 Vault 的 unseal 与备份。


### InformationSecurity-001-006 | ★★★★☆

对称加密与非对称加密的本质区别与组合使用？

**答案：**
对称加密（AES/SM4）：加密解密同一把钥匙，速度快，适合加密**大数据量**，死穴是密钥分发（钥匙怎么安全给对方）。非对称加密（RSA/ECC/SM2）：公钥加密私钥解（保密性），私钥签名公钥验证（认证性），解决了密钥分发，但慢，只适合小块数据。标准组合即 TLS 的做法：**非对称完成身份认证与密钥协商，对称加密传输实际数据**。密钥管理生产上交 KMS（密钥管理系统），绝不硬编码。


### InformationSecurity-001-007 | ★★★★☆

数字签名和数字证书的工作原理？

**答案：**
数字签名解决"完整性 + 不可抵赖"：发送方对内容先做摘要（Hash），再用**私钥**加密摘要得签名；接收方用**公钥**解出摘要、对原文重算摘要比对——一致则内容未被篡改且必然出自私钥持有者。剩余问题是"这把公钥真的属于他吗"——由**数字证书**回答：CA（证书权威）用自己的私钥对"持有者身份+公钥"信息签名，形成证书链，根证书预装在操作系统/浏览器信任库。验证证书=逐级验签+检查有效期+域名匹配+吊销状态（CRL/OCSP）。


### InformationSecurity-001-008 | ★★★★☆

常见的密码攻击有哪些？怎么防御？

**答案：**
针对口令的四类：①暴力破解——全组合尝试，防御：慢哈希（bcrypt/argon2）提高单次成本+登录限流+验证码；②字典攻击——用常见口令清单尝试，防御：密码强度策略（长度+复杂度+弱口令黑名单）；③彩虹表——预计算"哈希→明文"大表反查，防御：**加盐**使同口令不同哈希、表失效（bcrypt 自动加盐，盐无需保密需唯一）；④撞库——拿外泄的"账号-密码"对来试，防御：密码不能与别处复用的提醒、多因素认证（MFA）、异地登录检测。根上一条：口令存储必须是慢哈希+盐（K-SEC-001），传输必须 TLS。


### InformationSecurity-001-009 | ★★★★☆

重放攻击与中间人攻击的防御？

**答案：**
重放攻击：截获合法请求原样重发（如重复转账请求）。防御组合：时间戳窗口（超窗拒绝）+ 一次性随机数 nonce（窗口内去重）+ 序列号/一次性令牌；本质是给请求加"新鲜性"；配合签名防篡改（K-SEC-003 的完整方案）。中间人攻击：攻击者劫持通信两端，窃听/篡改/冒充。防御：TLS 全站 + HSTS 强制 + 证书校验不放松（客户端禁用不安全信任策略）+ 内网 mTLS；对 DNS 劫持补充 DoH/HTTPDNS。两句话记忆：防重放加"新鲜性凭证"，防中间人加"可信身份锚点"。


### InformationSecurity-001-010 | ★★★★☆

加密算法选型

需要将 100MB 的敏感文件加密后传输给合作方，双方已通过安全渠道交换过密钥，最适合的算法类型是：

A. RSA 非对称加密，直接加密文件
B. AES 对称加密（如 AES-256-GCM）
C. SHA-256 摘要算法
D. Base64 编码

**答案：** B

**解析：**
- A：错误。RSA 加密极慢且有明文长度限制（远小于 100MB），不用于大数据量。
- B：正确。已解决密钥分发的前提下，对称加密是大数据量的标准选择；GCM 模式还自带完整性校验。
- C：错误。摘要算法单向不可逆，无法解密还原，不用于保密传输。
- D：错误。Base64 是编码不是加密，无保密性。

对称加密大数据、非对称做密钥交换与签名、摘要做完整性。


### InformationSecurity-001-011 | ★★★★☆

签名与验签流程

发送方使用自己的私钥对消息摘要进行签名，接收方应使用（　）验证签名，从而确认消息来源与完整性。

A. 发送方的公钥
B. 接收方的公钥
C. 发送方的私钥
D. 双方协商的对称密钥

**答案：** A

**解析：**
- A：正确。私钥签名、对应公钥验签；公钥 openly 可分发，任何人可验证但无法伪造。
- B：错误。接收方公钥用于"别人给接收方发加密消息"的场景。
- C：错误。私钥绝不交给验证方。
- D：错误。对称密钥方案是 HMAC，不是非对称数字签名的验签方式。

签名：私钥签 → 公钥验；加密：对方公钥加密 → 对方私钥解。


### InformationSecurity-001-012 | ★★★★★

口令存储方案

用户登录口令在数据库中的正确存储方式是：

A. 明文存储，便于忘记密码时找回
B. MD5 加密后存储
C. 使用 bcrypt/argon2 等慢哈希并自动加盐后存储
D. AES 加密后存储，密钥写在配置文件中

**答案：** C

**解析：**
- A：错误。明文存储是最严重的安全与合规事故。
- B：错误。MD5 速度极快，GPU 每秒可试数十亿次，加盐也无法抵御现代暴力破解。
- C：正确。慢哈希故意提高单次验证成本，自动加盐打破彩虹表，是行业标准。
- D：错误。可逆加密存储口令意味着密钥泄露即全量泄露；且口令本不该可逆——验证时用同样的哈希过程比对即可。

口令存储：慢哈希 + 盐；验证是"重算比对"，不是"解密比对"。


### InformationSecurity-001-013 | ★★★★☆

重放攻击防御

开放接口为防御重放攻击，请求中应包含并校验的要素有：

A. 时间戳（服务端校验在允许窗口内）
B. 随机数 nonce（服务端在窗口期内去重）
C. 请求签名（覆盖时间戳与 nonce）
D. 用户的真实 IP 地址

**答案：** A、B、C

**解析：**
- A：正确。时间戳限定新鲜性窗口。
- B：正确。nonce 保证窗口内每个请求唯一，截获重发即被识别。
- C：正确。签名必须覆盖时间戳与 nonce，否则攻击者可篡改它们绕过校验。
- D：错误。IP 可被伪造且存在代理/NAT 场景，不能作为防重放依据，仅可作风控信号。

防重放 = 时间窗 + 一次性随机数 + 覆盖二者的签名。


### InformationSecurity-001-014 | ★★★★☆

HTTPS 防护范围

某网站已全站启用 HTTPS，下列哪种攻击风险**仍然存在**：

A. 网络链路上被窃听明文密码
B. 运营商在页面中插入广告脚本（传输层篡改）
C. 钓鱼网站诱导用户主动输入密码（应用层欺骗）
D. 中间人对合法证书域名的流量解密篡改

**答案：** C

**解析：**
- A：错误。HTTPS 加密保护传输机密性，链路窃听无法获得明文。
- B：错误。传输层篡改会被 TLS 完整性校验发现并终止连接。
- C：正确。HTTPS 不识别"用户访问的是假网站"——钓鱼属于应用层/人因欺骗，需反钓鱼教育、浏览器防护与域名监测。
- D：错误。在证书校验不被绕过的前提下，中间人无法伪造合法域名的证书。

HTTPS 解决"传输机密性+完整性+服务器身份"，不解决"用户去错了站、输错了窗"。


### InformationSecurity-001-015 | ★★★☆☆

SSRF 攻击

某服务提供"根据用户输入的 URL 抓取网页预览"功能，攻击者输入 `http://169.254.169.254/latest/meta-data/`（云平台元数据地址）试图获取主机凭证。这类攻击是：

A. XSS
B. CSRF
C. SSRF（服务端请求伪造）
D. SQL 注入

**答案：** C

**解析：**
- A：错误。XSS 是向页面注入脚本攻击其他用户。
- B：错误。CSRF 是借用户身份伪造跨站请求。
- C：正确。诱导**服务端**向攻击者指定（通常是内网/敏感）地址发起请求，即 SSRF；云元数据地址是经典目标。
- D：错误。与数据库查询构造无关。

SSRF 防御：URL 白名单/协议白名单、禁止内网网段与元数据地址、禁止重定向跟随、出口网络隔离。


### InformationSecurity-001-016 | ★★★☆☆

最小权限原则

下列做法符合"最小权限原则"的有：

A. 应用连接数据库使用仅授予所需表 SELECT/INSERT 权限的账号
B. 生产服务器上所有服务统一使用 root 运行以便管理

D. 人员离职当天回收其全部系统访问权限

### InformationSecurity-001-023 | ★★★☆☆

密钥管理原则

关于密钥管理，正确的有：

A. 密钥不应硬编码在代码或镜像中
B. 使用 KMS 集中管理，按需分发
C. 定期轮换，支持紧急吊销

### AI-001-001 | ★★★★☆

多模型接入层（LLM 网关）要解决什么问题？

**答案：**
应用不该直连各模型厂商——收敛到统一网关层，解决六件事：①统一协议——各厂商 API 差异（消息格式/参数/流式协议）在网关抹平，应用面向内部标准协议；②路由与降级——按任务类型/成本/时延路由（简单分类走小模型，复杂推理走大模型），主模型故障自动切备用（failover），同请求多供应商重试；③配额与成本——按应用/团队/用户的 token 配额、预算告警、用量计量计费（计费口径对齐厂商账单）；④安全合规——提示与输出审计留痕、敏感词与数据出域管控、密钥集中管理；⑤稳定性——限流（厂商速率限制的上游分配）、请求排队、超时熔断；⑥缓存——前缀缓存与语义缓存（相似问题命中直接返回，需评估风险）。选型：开源网关（OneAPI/Higress AI 类）或自研薄层。本质一句话：**把"不可靠且贵的下游"封装成"稳定可控的内部服务"**。


### AI-001-002 | ★★★★☆

流式输出（SSE）怎么实现？和普通接口有什么不同？

**答案：**
LLM 逐 token 生成，流式（SSE：HTTP 长连接 + `text/event-stream`，服务端单向推）让首字延迟从"全部生成完"降到"首 token 时间"，是体验刚需。实现要点：①网关/应用侧透传流——异步非阻塞管线（WebFlux/虚拟线程/async servlet），严禁同步线程等流（连接数被拖死）；②协议转换——厂商流式协议（SSE 分片 JSON）转内部统一事件（content/delta/tool_call/usage/done）；③完整性——前端按事件序列拼接，done 事件带结束原因与 usage 统计；中途断连要有会话恢复或重生成策略；④背压与超时——消费慢时的缓冲上限、生成超时主动断；⑤Nginx 等代理需关闭缓冲（X-Accel-Buffering: no）。SSE vs WebSocket：SSE 单向简单够用（请求-流式响应），双向交互（语音、协同）才上 WS（K-NET-004）。合规点：流式内容仍需过安全审核（增量审核或 done 后全量复审+撤回机制）。


### AI-001-003 | ★★★★☆

LLM 应用的限流、超时、重试、降级怎么做？

**答案：**
把 LLM 视为"慢、贵、有速率限制、会偶发失败"的下游，四件套定制化：①超时：分首字超时（TTFT 上限，快速识别卡死）与总时长超时；生成类任务超时阈值显著大于普通 RPC，并配流式尽早反馈；②重试：只重试可重试错误（429/5xx/超时），指数退避+抖动，尊重 Retry-After；幂等前提（生成类天然可重试，但要注意"结果可能已产生"的副作用场景）；重试预算防放大（K-DIST-008）；③限流：三层——厂商速率（TPM/RPM）向上分配配额、网关全局限流、按用户/应用配额（K-DIST-007），队列化削峰优于硬拒绝（体验权衡）；④降级：主模型故障切备用模型（能力差异要评测兜底）、非核心功能直接降级关闭、缓存兜底。专项：**预算熔断**——成本超阈值自动降级到低成本模型或关闭功能，这是 LLM 应用独有的保险丝（K-AIENG-005）。


### AI-001-004 | ★★★★☆

LLM 应用的可观测性要建哪些指标？

**答案：**
四层指标体系：①体验层——TTFT（首字延迟）、总延迟、流式中断率、错误率（按错误类型分：限流/超时/内容过滤/模型故障）；②成本层——每次调用 prompt/completion tokens、按应用/团队/模型维度的费用聚合、缓存命中率、预算消耗进度（K-AIENG-003）；③质量层——线上抽样人工/LLM 裁判评分、用户反馈（赞踩/采纳率/转人工率/重新生成率）、结构化解析成功率、安全拦截率；④系统层——模型服务商状态、队列深度、并发连接。工程配套：全链路 trace（请求→检索→生成→审核，K-MS-006），每次调用的输入输出/版本/参数快照存档（可回放调试），prompt 与模型版本作为维度参与所有指标聚合——没有版本维度的指标无法归因。工具形态：LLM 网关埋点 + OpenTelemetry + 专项观测平台（Langfuse 类）或自建。


### AI-001-005 | ★★★★☆

Token 成本优化的实用手段有哪些？

**答案：**
按"少用、用小、用久、用对"四招：①少用——需求裁剪（不是所有环节都要 LLM：规则能做的先规则）、缓存（前缀缓存命中系统提示，语义缓存谨慎用，K-LLM-006/K-AIENG-001）、压缩上下文（历史摘要、检索内容裁剪而非全塞、结构化状态替代全量对话 K-AGENT-004）；②用小——模型分级路由（简单任务小模型/蒸馏模型，复杂再升级），输出长度约束（max_tokens+提示要求简洁），批处理 API（非实时任务半价量级）；③用久——会话复用上下文、批量合并短请求；④用对——计费结构理解（输入贵输出贵因厂商而异、缓存读折扣）、自托管评估（量大时开源模型+GPU 的单位成本可能更低，算上运维要诚实）。治理动作：成本可见（分摊到团队）+ 预算告警 + 优化专项（Top 消耗场景逐个治理）。经验量级：模型路由+上下文治理两招通常能砍 50%+。


### AI-001-006 | ★★★☆☆

多轮对话的状态管理怎么做？

**答案：**
会话状态三份存储：①消息历史——会话 ID → 消息列表（DB/Redis），支持多端同步与恢复；②工作状态——当前任务的结构化上下文（已确认槽位、进行中动作、购物车等），以显式 JSON 状态维护而不是从对话里"猜"；③长期画像——用户偏好/事实（K-AGENT-004）。上下文组装策略：系统提示（稳定前缀）+ 用户画像摘要 + 近期历史（窗口/摘要）+ 本轮输入；关键工程点：并发同会话的串行化（同一会话请求按序处理防乱序）、超时与过期（会话 TTL、状态机卡死回收）、多端一致性（版本号/乐观锁）、敏感信息生命周期（会话结束清理策略，合规要求）。调试能力：能还原任意会话的"模型实际看到的完整上下文"——排障与评测都靠它。


### AI-001-007 | ★★★★☆

自托管开源模型还是调商用 API？怎么决策？

**答案：**
决策因子五维：①合规与数据——数据不可出域（金融/政务/涉密）直接锁定私有化部署（开源自托管或厂商专属实例）；②成本结构——量大稳定负载自托管边际成本低（算 GPU 折旧+运维），波峰波谷大或量小 API 更省（K-AIENG-005 的总账口径）；③能力差距——旗舰商用模型前沿能力仍领先，开源（DeepSeek/Qwen/Llama 系）在主流任务已够用且中文生态好，用业务评测集说话（K-PROMPT-004）；④运维能力——自托管要囤推理工程（vLLM 部署调优、显存规划、监控），没有专职团队就别接；⑤弹性与 SLA——API 免运维有厂商 SLA，自托管自己做高可用。混合形态是常态：敏感/高频走自托管，前沿能力/溢出流量走 API，网关统一路由（K-AIENG-001）。自托管技术栈：vLLM/SGLang 推理引擎 + 模型量化 + 前缀缓存。


### AI-001-008 | ★★★★☆

AI 应用怎么安全地上线（评测、灰度、回滚）？

**答案：**
把"模型/Prompt/检索配置"当发布单元，走完整的变更管理：①上线前——离线评测回归（质量/安全双指标门槛，K-PROMPT-004）、红队测试（提示注入、越权诱导、敏感问题对抗样本）、依赖审查（模型版本、工具权限变更一并对审 K-MCP-006）；②灰度策略——按流量比例/白名单用户渐进放量，观察护栏指标（安全拦截率、转人工率、投诉率、成本/会话），任一异常熔断；③运行时防护——输入输出双向审核（敏感内容、合规红线）、关键动作人工确认、实时质量抽样；④回滚预案——prompt/模型/检索配置三者的版本回滚都要一键化，且回滚后用户侧会话兼容（上下文格式变更要兼容设计）；⑤复盘机制——badcase 回流评测集与知识库治理清单。金融/政企附加：内容安全合规审查流程、算法备案与生成内容标识等监管要求要留接口。


### AI-001-009 | ★★★★☆

Embedding 模型升级/更换的迁移方案

**答案：**
向量不可跨模型混存（空间不一致，相似度无意义），迁移=全量重嵌入+切换：①双写灰度——新写入同时写新旧空间，按新空间检索的比例逐步放大；②全量回填——离线批量重嵌入存量（批处理 API+限流），新旧索引并行；③校验切换——抽样对比新旧 TopK 重合度与人工评估，达标后切读、观察、下线旧索引；④回滚窗口——保留旧索引一段时间。数据量决定方案：百万级可直接重建+停写窗口；亿级必须双写渐进。

**解析：**
切换期间的读一致性：查询路由按"数据写入时的模型版本"或直接按新空间（旧数据回填完成前接受召回略降）。迁移是"评测新模型→定版→双写→回填→校验→切换"的发布工程，不是换个配置。


### AI-001-010 | ★★★★☆

讲讲 Transformer 和自注意力机制的基本原理。

**答案：**
Transformer 是当前大模型的基础架构，核心是自注意力：每个 token 生成 Query/Key/Value 三个向量，用 Q·K 相似度经 softmax 得到注意力权重，对 V 加权求和——即"每个词根据相关性从全句其他词汇聚信息"，解决了 RNN 的长距离依赖与无法并行问题。多头注意力把 Q/K/V 投影到多个子空间并行计算再拼接，让模型同时关注不同模式（语法、指代、位置等）。整体结构 = 输入嵌入（token 向量 + 位置编码）→ N 层（多头注意力 + 前馈网络 FFN，各带残差连接与层归一化）→ 输出层。按结构分三类：Encoder-only（BERT，理解类）、Decoder-only（GPT 系列，生成类，当前主流）、Encoder-Decoder（T5，翻译类）。


### AI-001-011 | ★★★★☆

大模型是怎么训练出来的？预训练、SFT、RLHF 各是什么？

**答案：**
三阶段流水线：①预训练（Pre-training）：海量无标注语料做"下一个 token 预测"，学到语言与世界知识，算力占绝对大头；②监督微调（SFT）：高质量"指令-回答"对，教会模型听懂指令、按对话格式输出——从"补全机"到"助手"的转变；③对齐（RLHF/DPO）：用人类偏好数据调整输出风格——RLHF 训练奖励模型再强化学习优化；DPO 直接用偏好对做监督式优化，更简单稳定（K-AIENG 相关引用）。工程岗补充概念：继续预训练（领域语料注入知识）、指令数据质量 > 数量、对齐税（对齐后通用能力可能略降）。


### AI-001-012 | ★★★★★

Token 和上下文窗口是什么？对成本有什么影响？

**答案：**
Token 是模型处理文本的最小单位：文本先被分词器（BPE 类子词算法）切成 token 再映射为向量——英文约 1 token≈0.75 词，中文约 1 token≈1~1.5 个汉字（因分词器而异）。上下文窗口是模型单次能处理的最大 token 数（输入+输出共享），超了必须截断/压缩/分块。工程影响三点：①计价按 token（输入输出分开计费），长上下文=高成本；②注意力计算量随长度平方级增长（部分架构有优化），长输入延迟显著上升；③"中间丢失"现象——长文档中间部分的信息利用往往不如首尾，RAG 场景要控制单次注入长度而不是无脑塞满。


### AI-001-013 | ★★★★☆

温度（Temperature）、Top-P、Top-K 是什么？怎么设置？

**答案：**
三者控制"从概率分布里怎么选下一个 token"：温度缩放 logits——低温（→0）分布尖锐，输出确定保守；高温分布平坦，输出多样易跑偏。Top-K 只在概率最高的 K 个候选里采样；Top-P（核采样）在累计概率达 P 的最小候选集里采样，候选数随分布自适应，通常比固定 K 更稳。工程默认值取向：抽取/分类/代码等确定性任务 temperature 0~0.3；文案生成 0.7 左右；创意发散 0.9+。确定性要求高的场景除低温外还应固定 seed（支持的模型），便于回归测试复现。


### AI-001-014 | ★★★★★

大模型为什么会产生幻觉？怎么缓解？

**答案：**
幻觉=生成看似合理但与事实不符的内容。根源三层：①训练机制——模型学的是"统计上流畅的下一个 token"，不是"真值"；训练数据本身有错漏，且无法区分"知道"与"不知道"；②概率生成——采样天然可能选到偏移路径；③使用方式——诱导性问题、超出知识时效（训练截止后的事实）、要求提供不存在引用时模型会"编造像的"。缓解分层：数据/检索层——RAG 注入可信上下文并要求"仅依据给定资料回答"，附引用溯源（K-RAG-001）；提示层——明确允许回答"不知道"、要求逐步推理、少样本示范格式；工程层——事实校验器（NLI 比对/规则校验）、关键结论二次自检（self-check）、置信度路由（低置信转人工）；产品层——人类确认环节、免责与来源展示。要能坦诚：幻觉无法根除，只能压缩到业务可接受范围。


### AI-001-015 | ★★★☆☆

KV Cache 和 Prompt Caching 是什么？为什么重要？

**答案：**
自回归生成时，每生成一个 token 都要对"全部历史 token"做注意力；KV Cache 把历史 token 的 Key/Value 缓存下来，新 token 只计算自己的 QKV 并与缓存交互——把每步从"重算全部历史"降到"只算增量"，是推理提速的基石。代价是显存占用：缓存大小 ∝ 层数×头数×头维度×2(K/V)×序列长度，长上下文下显存成为瓶颈（这也是 MQA/GQA 减少 KV 头数、滑动窗口注意力等技术的动机）。Prompt/前缀缓存是应用层视角的复用：相同前缀（系统提示+少样本示例+长文档）的 KV 只算一次并缓存，后续请求命中直接复用——首 token 延迟与输入费用双降。工程用法：把稳定不变的公共前缀放在 prompt 开头，动态内容放尾部，前缀命中率显著提升。


### AI-001-016 | ★★★☆☆

MoE（混合专家）是什么？为什么 DeepSeek/Qwen 等在用？

**答案：**
MoE 把 Transformer 的 FFN 层替换为"多个专家 FFN + 一个路由器"：每个 token 由路由器打分，只激活 Top-K（常为 1~8）个专家，其余专家不参与计算。效果是"总参数量大（知识容量大）、单 token 计算量小（只走稀疏激活）"——DeepSeek-V3 总参数数千亿、激活参数约 37B 就是这个思路，性价比（性能/算力比）优于同等计算量的稠密模型。代价与挑战：①显存仍要装下全部专家参数（部署门槛高）；②训练负载均衡问题（专家冷热不均需要辅助损失）；③推理系统要做专家并行。应用岗理解到"稀疏激活=大容量低成本"这层即可，再能说出"路由是学习的、按 token 动态"就算扎实。


### AI-001-017 | ★★★★☆

LoRA 微调是什么？什么时候选微调而不是 RAG？

**答案：**
LoRA（低秩适配）是参数高效微调：冻结原模型权重，在目标层（常为注意力投影矩阵）旁挂两个小矩阵（秩 r 很小，如 8~64），只训练这对低秩矩阵——可训练参数量降到千分之一以下，单卡可训大模型；多个 LoRA 适配器可按需热切换（不同业务挂不同 adapter），合并后无推理额外延迟。它教的是"行为与风格"，量级在千~十万条高质量样本。与 RAG 的选择是高频决策题：**知识时效/私有事实 → RAG**（可随时更新、可溯源、成本低）；**输出风格/格式/领域话术/任务行为 → 微调**（改的是分布不是事实）；两者可叠加（领域微调 + RAG 注入实时知识）。反面清单：用微调塞事实知识（更新慢、易幻觉、贵）；用 RAG 教格式（不稳）。


### AI-001-018 | ★★★★☆

结构化输出（JSON Mode / Schema 约束）的原理与局限

**答案：**
两层机制：提示层（Schema+示例+低温）只是"请求"，模型仍可能漂；约束解码层（厂商 JSON Mode / Structured Outputs）在采样时把不合语法的 token 概率置零，语法上保证可解析——但不保证语义正确（字段值仍可能幻觉）。工程闭环必须加校验：Pydantic/JSON Schema 校验→失败带错误信息重试→仍失败降级。enum 字段用受控解码最稳；嵌套深 schema 的遵循率下降，宁可拆多次调用。

**解析：**
约束解码原理：按 JSON 文法构造状态机/受限文法，每个位置限制候选 token；代价是创造力归零（只适合抽取/结构化任务）。抽取类任务的最佳实践：字段少而精、enum 明示、必填声明、"不确定输出 unknown"的兜底枚举值防编造。


### AI-001-019 | ★★★★★

Prompt 工程有哪些实用的通用技巧？

**答案：**
组织成"输入结构六件套"：①角色与目标（你是资深客服，目标是……）限定语气与边界；②上下文与背景资料（检索内容、历史摘要）明确"仅依据以下资料"；③任务指令具体化——动词明确、拆步骤（先分类再摘要）、给输出 Schema/示例；④少样本示例（2~5 个，覆盖典型+边界 case，示例质量决定上限）；⑤约束与兜底（不确定就说不知道、禁止编造、格式校验）；⑥输出格式约定（JSON Schema/字段说明），配合低温度保证可解析。通用心法：Prompt 是"编程"，迭代靠评测（K-PROMPT-004），而不是凭感觉改字；把成功 prompt 版本化。


### AI-001-020 | ★★★★☆

怎么让模型稳定输出可解析的结构化结果（JSON）？

**答案：**
四层保障由强到弱：①模型原生能力——JSON mode/Structured Output（按 JSON Schema 约束解码），可用性最高；②提示层——给出精确 Schema（字段、类型、枚举、必填）+ 一个完整示例 + "只输出 JSON 不要解释"；③解析层——宽容解析（剥离代码块围栏、截取首尾大括号）+ 失败修复（把原输出+报错回喂模型修一次）；④校验层——Pydantic/Jackson Schema 校验，失败走重试（退避）或降级路径。配套参数：temperature 0~0.2、max_tokens 足够、枚举值显式列出。监控字段：解析成功率、字段缺失率——结构化输出的稳定性是可度量的工程指标。


### AI-001-021 | ★★★☆☆

思维链（CoT）是什么？什么时候有用、什么时候没用？

**答案：**
CoT 让模型"先写推理过程再给答案"，把多步问题拆解为中间步骤，显著提升算术、逻辑、多条件判断类任务的准确率——本质是给模型更多"中间 token 计算空间"（Transformer 单步计算有限，把思考外化成 token）。变体：少样本 CoT（给带推理的示例）、Zero-shot CoT（"一步步思考"）、自洽性（多次采样投票）。适用边界：数学/规则推理/复杂判断有效；简单分类、抽取、闲聊没必要（费 token 还可能画蛇添足引入错误）。工程取舍：推理 token 增加延迟与成本；新一代推理模型（o1 类）内化 CoT，应用侧只需给任务不必手写"一步步来"，但输出解释仍可要求。防幻觉用法：要求"引用资料编号+推理依据"，让错误可定位。


### AI-001-022 | ★★★☆☆

Prompt 的版本管理与效果评测怎么做？

**答案：**
把 Prompt 当代码管理：版本化存储（Git/配置中心）、变更走评审、与模型版本/参数一起构成"配置指纹"。评测体系三层：①离线评测集——从真实 case 抽取 100~500 条覆盖典型+边界，标注期望结果（分类标签/关键字段/答案要点）；跑批输出指标（准确率/字段抽取 F1/格式合法率），每次改动跑回归防止"改好一处坏三处"；②LLM-as-judge——用强模型按评分准则（rubric）打分，适合开放生成类，需抽样人工校准裁判偏差（位置偏置、长度偏置）；③在线 A/B——线上小流量对比业务指标（采纳率、转人工率、解决率）。铁律：没有评测集的 prompt 调优都是盲调；评测集要持续从线上 bad case 回流更新。


### AI-001-023 | ★★★★☆

Token 计算直觉

中文文本经常见分词器切分后，1 个汉字的 token 数量级通常是：

A. 1~1.5 个 token
B. 0.1 个 token
C. 10 个 token
D. 固定 0.5 个 token

**答案：** A

**解析：**
中文常见约 1 字 1 token（词表优化后部分词组合并），英文约 0.75 词/token；B/C/D 量级错误。

token 是计费与上下文计量单位，中文成本普遍高于英文。


### AI-001-024 | ★★★★☆

幻觉缓解组合

以下对缓解 LLM 幻觉最有效的工程组合是：

A. 调高温度增加多样性
B. RAG 注入可信上下文+要求仅依据资料回答+引用溯源

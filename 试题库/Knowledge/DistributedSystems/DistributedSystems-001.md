### DistributedSystems-001-001 | ★★★★★

CAP 理论讲一下？BASE 是什么？实际系统怎么取舍？

**答案：**
CAP 三性：一致性（线性一致：所有节点同一时刻读到相同值）、可用性（每个请求都能得到非错误响应，可以不是最新数据）、分区容忍（网络分区时系统仍能工作）。理论结论：网络分区不可避免（P 是前提），分区发生时只能在 C 与 A 之间二选一——CP（ZooKeeper/etcd：拒绝服务保一致）与 AP（Eureka/Cassandra：降级返回旧数据保可用）。常见误读要纠正：CAP 不是"三选二"，无分区时可同时具备 CA；分区是瞬时事件，系统可以在分区期间选择策略、恢复后弥补（最终一致）。BASE 是工程化的 AP 路线：基本可用（降级）、软状态（允许中间态）、最终一致（对账/重试收敛），是绝大多数互联网业务的一致性姿态。


### DistributedSystems-001-002 | ★★★★☆

一致性哈希的原理？解决什么问题？

**答案：**
普通哈希（hash % N）的问题：节点数 N 变化时几乎全部 key 重映射——扩缩容等于缓存大清洗。一致性哈希把哈希空间组织成环（如 0~2^32），节点与 key 都哈希到环上，key 顺时针找到第一个节点归属；增删节点只影响环上相邻区间的数据（迁移 1/N）。未解决的问题是数据倾斜（节点少时分布不均），解法是虚拟节点：每个物理节点映射成上百个虚拟点均匀撒在环上，既均衡又保持"只迁移邻近区间"的性质。应用：分布式缓存（Memcached 客户端）、负载均衡会话粘性、分库分表扩容、P2P（DHT 的思想源头）。Redis Cluster 用的是哈希槽（预分配 16384 槽映射到节点），逻辑上等价于"固定数量虚拟分片"，扩容迁移以槽为单位。


### DistributedSystems-001-003 | ★★★☆☆

讲讲 Raft 共识算法：选举和日志复制。

**答案：**
Raft 把共识拆成三个可理解的子问题。leader 选举：节点三种角色（leader/follower/candidate），follower 超时收不到心跳就自增任期 term 发起选举拉票，获得多数票当选（每节点一任期只投一票保证唯一 leader）；任期号是逻辑时钟，旧任期消息被拒。日志复制：所有写请求经 leader → 追加日志 → 并行发给 followers → 多数派持久化确认后提交 → 应用到状态机并通知 followers 提交；日志按索引对齐，不一致时 leader 强制 follower 覆盖为自己的日志。安全性保证：投票时候选者日志必须不落后于投票者（保证已提交日志不被覆盖）。工程实现：etcd、TiKV、RocketMQ DLedger、Consul——答出"多数派+任期+日志对齐"三个关键词即结构清晰。


### DistributedSystems-001-004 | ★★★★★

分布式事务有哪些方案？各自的适用场景？

**答案：**
按一致性与侵入度排序讲五类：①2PC/XA：准备-提交两阶段，强一致，同步阻塞+协调者单点，跨库低频强一致场景（数据库原生支持），吞吐差；②TCC：Try-Confirm-Cancel 三段业务编码，资源预留思想（冻结额度），最终一致，侵入大但并发好——资金类核心链路；③SAGA：长事务拆成有序的本地事务序列+每步配补偿动作，失败逆序补偿，适合长流程（跨服务旅行预订），要处理补偿失败与空回滚/悬挂；④本地消息表/事务消息：把"跨系统调用"转为"消息最终一致"（K-MQ-002），侵入小，最常用的业务解耦方案；⑤最大努力通知：重试+对方查询对账，适合通知类（支付结果通知商户）。选型公式：强一致低频用 2PC/XA；资金扣减用 TCC；长流程用 SAGA；解耦联动用消息最终一致+对账兜底。

**解析：**
TCC 三大经典缺陷与防护（必会）：空回滚（Try 未到达 Cancel 先到——Cancel 判断 Try 记录不存在则直接成功并记录）、悬挂（Cancel 执行后 Try 才到——Try 前检查 Cancel 标记拒绝执行）、幂等（三阶段都可能重试，全部要求幂等）。框架：Seata 的 AT 模式（自动生成 undo log 反向补偿，侵入小）是主流落地方案，TCC 模式手工编排。

SAGA 的编排与协同：中央编排器（状态机，可控可视）vs 事件链（去中心，耦合低难追踪）；补偿不可用时的"人工介入"是终点设计。


### DistributedSystems-001-005 | ★★★★★

接口幂等性的完整设计（分布式视角）？

**答案：**
幂等=同一操作执行一次与多次结果相同，是重试机制的前提（K-MQ-003 是消息侧，本题全面化）。按实现强度分层：①天然幂等——查询、基于唯一业务键的条件更新（update ... where status='待支付'）、delete by id；②防重提交——前端防抖只是体验层，服务端用"token 机制"：进入页面发一次性 token，提交时 Redis 原子删除成功才处理（setnx/del Lua）；③防重表/唯一索引——DB 唯一键兜底并发窗口，冲突即重复；④状态机——订单状态不可逆流转天然幂等；⑤分布式锁——串行化同 key 并发，锁内仍需幂等校验（锁只是排队不是去重）。设计清单：接口必须定义幂等键（客户端生成的请求 ID/业务单号），全链路透传，存储与校验位置明确。


### DistributedSystems-001-006 | ★★★★☆

分布式锁的实现对比（Redis / ZooKeeper / etcd）？

**答案：**
Redis：SET NX PX + 唯一值 + Lua 解锁 + 看门狗续期（Redisson），性能最高，AP 语义——主从切换可能锁丢失，RedLock 多数派方案存在争议（K-REDIS-006），适合高并发、可容忍极小概率双持有的场景（任务防重）。ZooKeeper：临时顺序节点 + 监听前驱——会话断开锁自动释放（解决"持锁进程死了锁不释放"），CP 语义，无锁丢失问题，但性能低（写全量广播），且羊群效应要靠"只监听前一个节点"规避。etcd：事务 API（prefix 版本号比较）+ 租约 lease，CP，Kubernetes 生态原生。选型：高并发性能敏感 → Redis+业务幂等兜底；强正确性、低频（选主、元数据互斥）→ ZK/etcd；资金类 → 无论用什么锁，DB 层唯一约束/乐观锁兜底。


### DistributedSystems-001-007 | ★★★★☆

分布式限流怎么实现？算法和存储方案？

**答案：**
先分单机与集群。算法四件套：固定窗口计数（简单，窗口边界双倍突刺）、滑动窗口（多小格统计，平滑）、漏桶（恒定速率整流）、令牌桶（恒速放令牌允许突发，最通用，Guava RateLimiter/Sentinel 默认思想）。集群限流三种路径：①集中式计数：Redis+Lua 实现滑动窗口/令牌桶（原子），简单但每次请求一次网络 RT，Redis 成热点；②客户端分摊配额：中心服务（Sentinel Token Server）把全局限额分配给各实例本地消费，性能好，实现复杂，存在配额不均；③分层限流：网关粗粒度全局限流（挡洪峰）+ 服务内单机限流（精细保护），绝大多数系统的落地形态。热点参数限流（按 userId/apiKey 维度）防单点热度。被限流后的响应：429 + Retry-After、降级逻辑、监控告警。


### DistributedSystems-001-008 | ★★★★☆

调用链的超时、重试应该怎么设计？

**答案：**
超时设计核心是"超时预算沿调用链递减"：入口总预算（如用户 P99 1s）分配给各层级，每层留余量，确保下游超时后上游还有时间收尾（返回降级值），绝不层层同样超时导致"下游超时的同时上游也在超时"的重试风暴。重试设计五要素：①只重试幂等请求或用幂等键（K-DIST-005）；②指数退避+随机抖动（防止同时重试踩踏），限制次数（2~3 次）；③重试预算——限制重试流量占比（如 <10%），防止重试放大（下游 50% 失败时全量重试让流量翻倍彻底压垮）；④只重试可重试错误（超时/503/429 按 Retry-After，4xx 不重）；⑤重试换节点，避开刚失败的实例。与熔断配合：错误率熔断优先于盲目重试。


### DistributedSystems-001-009 | ★★★☆☆

分布式任务调度怎么设计（多实例不重复执行）？

**答案：**
多实例定时任务的三个层次：①互斥执行——全局锁（Redis/ZK）保证同一时刻一个实例跑（简单但无法水平扩展，单点慢）；②分片执行——任务按分片参数（shardingTotal/shardingItem）拆分，多实例各领一片并行（XXL-Job 的分片广播、Elastic-Job 思想），扩展性好，要求任务可按 key 切分且每片幂等；③任务抢占+可靠补偿——任务表模式：DB 存任务（状态/下次执行时间/owner），实例抢 UPDATE 占用（乐观锁），超时未完成被其他实例接管（防单点死亡挂起），加 SKIP LOCKED/版本号防并发抢。选择：单实例可完成→锁互斥足够；数据密集批处理→分片；高可靠→任务表+接管+幂等。配套：失败重试上限、告警、手动触发与参数、运行日志可查。


### DistributedSystems-001-010 | ★★☆☆☆

分布式系统里的"时间"有哪些坑？

**答案：**
三组概念四个坑：①墙上时钟不可靠——机器间偏移（NTP 校准但可能跳变/渐变），跨节点"按时间戳排序"不可靠，订单/事件排序用单调递增 ID 或节点内序列号；②单调时钟才是测耗时的正确工具（System.nanoTime/Go monotonic），System.currentTimeMillis 是墙上时钟可用于展示不可用于计时；③时钟回拨——雪花 ID 的经典雷区（K-MYSQL-017），本质是"把墙上时钟当单调时钟用"；④超时与租约依赖时间判断（分布式锁 TTL、租约续期），时钟跳变会造成锁提前失效——fencing token 用单调令牌解耦时间假设。TrueTime（Spanner）用原子钟+GPS 给出有界不确定区间，是"用硬件花钱买时间正确性"的极端方案，提一句体现广度。


### DistributedSystems-001-011 | ★★★★★

CAP 判定

网络分区发生时，ZooKeeper 的表现倾向是：

A. 放弃可用性保一致性（少数派不可服务）
B. 放弃一致性保可用性
C. 同时保证 CA
D. 崩溃退出

**答案：** A

**解析：**
ZK 基于类 Raft/ZAB 多数派，少数派侧无法选出 leader 而拒绝写入（CP）；B 是 Eureka 取向；C 违背 CAP（分区时必弃其一）；D 错。

CAP 中 P 必选，分区时 C/A 二选一。

以下防重复提交方案中，并发下最可靠的是：

### DistributedSystems-001-014 | ★★★☆☆

一致性哈希迁移量

一致性哈希环上 4 个节点扩为 5 个节点（虚拟节点充分），约有多大比例的 key 需要迁移？

A. 100%
B. 50%
C. 20%
D. 0%

**答案：** C

**解析：**
新增 1/N+1 = 1/5 = 20% 的 key 落入新区间需迁移；B 是"翻倍扩容取模法"（模翻倍迁移 50%）的对照；A 是普通取模改 N；D 不可能。

一致性哈希增删节点只影响相邻区间（约 1/N）；取模翻倍扩容迁移 50%。

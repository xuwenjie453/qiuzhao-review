### Microservices-001-001 | ★★★★☆

微服务与单体架构的取舍？什么时候该拆？

**答案：**
微服务的收益：独立部署与扩容、故障隔离、技术栈自由、团队自治（康威定律：架构映照组织）；代价：分布式复杂性（网络不可靠、数据一致性）、运维成本（注册发现、链路追踪、CI/CD、可观测）、接口治理成本。判断该不该拆的三问：组织规模是否到了"多团队互抢发布窗口"、业务模块是否增速/形态差异大到需要独立伸缩、是否真有运维与平台能力兜底。反模式警告：过早微服务化（分布式单体——拆了服务还共享数据库，最糟形态）。演进路线：模块化单体（清晰边界）→ 按需拆分 → 服务化，"先能拆再拆"。


### Microservices-001-002 | ★★★★☆

服务拆分的原则与实践？

**答案：**
核心原则：高内聚低耦合、单一职责、按业务能力/限界上下文拆（DDD），每个服务独享数据（database per service）。实操标准：①语义边界——领域术语一致、独立演进；②数据边界——数据归属唯一 owner，跨域只走接口或事件，禁止直连他库；③团队边界——一个服务一个负责团队（两披萨团队）；④变更频率与伸缩需求差异大的分开。落地手法：事件风暴梳理领域事件→识别限界上下文→定义上下文映射（防腐层 ACL 隔离老系统模型）。拆分顺序：先拆"增改最频繁"的域，稳定核心（账务）后拆。要能反着说：不按技术分层拆、不按团队人数凑数拆、不为拆而拆。


### Microservices-001-003 | ★★★★☆

服务注册与发现的原理？CAP 上如何取舍？

**答案：**
流程：服务启动时向注册中心注册（地址、元数据、健康状态）→ 消费者拉取/订阅服务列表（本地缓存）→ 通过心跳/健康检查剔除失效实例 → 调用时从缓存负载均衡选一个。CAP 取舍是核心考点：Eureka 选 AP—— peer-to-peer 复制，网络分区时各节点可用但可能拿到旧列表，宁可返回旧数据不拒绝服务；ZooKeeper/Consul 偏 CP——分区时为保证一致可能不可用（ZK 选举期间不可写）。微服务场景通常选 AP：调用失败可重试/熔断，而注册中心不可用会全站瘫痪。Nacos 双模式（AP 的 Distro/CP 的 Raft）按服务类型配置。客户端缓存的意义：注册中心全挂，存量调用仍可继续（退化可用）。


### Microservices-001-004 | ★★★★☆

负载均衡有哪些策略？客户端负载均衡和服务端负载均衡的区别？

**答案：**
常见策略：轮询/加权轮询（按机器配比分流）、随机/加权随机、最少活跃调用（Dubbo 默认思想，慢节点自动少接）、一致性哈希（同 key 同节点，会话粘性/缓存友好）、响应时间加权、区域感知优先（跨机房流量治理）。两类架构：服务端 LB（LVS/Nginx/网关统一转发，集中管控但多一跳）vs 客户端 LB（SDK 从注册中心拿列表自己选，少一跳、去中心化，Spring Cloud LoadBalancer/Dubbo 客户端）。现代 Mesh 方案：Sidecar 代理做 LB，SDK 零侵入。健康感知是所有策略的灵魂：主动探测+被动统计（失败率拉黑，恢复半开）。


### Microservices-001-005 | ★★★★★

熔断、降级、限流、隔离是怎么配合工作的？

**答案：**
稳定性四件套各司其职：限流是入口控制——只放系统承受得住的流量（阈值内拒绝多余）；熔断是依赖防护——下游错误率/慢调用比例超阈值后"跳闸"，一段时间内直接快速失败，避免线程池/连接被拖垮并给下游喘息；降级是价值取舍——被限流/熔断后返回兜底（默认值、缓存、简化流程），保证核心链路可用；隔离是爆炸半径控制——线程池/信号量按依赖隔离（舱壁模式），一个依赖故障不波及其他。经典状态机：熔断器 Closed（正常，统计失败率）→ Open（快速失败，计时）→ Half-Open（放行少量探测，成功则恢复）。实现：Sentinel（流控规则丰富、控制台）、Resilience4j（轻量、函数式）、Hystrix（已停更）。


### Microservices-001-006 | ★★★☆☆

分布式链路追踪的原理？TraceId 怎么传递？

**答案：**
原理：入口生成全局 TraceId，每次跨服务调用时通过协议头（HTTP Header/gRPC metadata/MQ 属性）传递；服务内每次处理单元是 Span，记录 spanId、parentSpanId、开始时间、耗时、标签——形成调用树。采样策略：全量太贵，头部采样（入口按比例）+ 尾部采样（完整trace结束后按"有错误/高延迟"优先保留）平衡成本与价值。OpenTelemetry 是事实标准（统一 SDK/API/协议 OTLP），后端可接 Jaeger/SkyWalking/Tempo。传递落地：框架自动埋点（agent 字节码增强）或 SDK 手动；跨异步边界（线程池/MQ）需要上下文桥接——ThreadLocal 换可传播 Context，MQ 场景属性透传+消费端还原。


### Microservices-001-007 | ★★★☆☆

服务网关的职责？鉴权、限流在网关层怎么做？

**答案：**
网关是南北向流量的统一入口，职责六项：动态路由（按路径/头/权重）、统一鉴权（Token 校验、签名、防重放）、限流熔断（全局与按 API 配额）、协议转换（HTTP→gRPC、WebSocket）、可观测（日志/指标/trace 起点注入）、灰度分流（按用户/设备标签路由到不同版本）。鉴权常见模式：网关统一验 JWT/会话 → 透传用户上下文头（x-user-id + 内部签名防伪造）到下游，下游专注业务鉴权（资源级权限）。技术选型：Spring Cloud Gateway（Java 生态、过滤器链）、Nginx+Lua（性能与灵活）、APISIX/Kong（插件生态）。BFF 模式：网关之上按端（App/Web/开放平台）建聚合层，裁剪与组装后端服务。


### Microservices-001-008 | ★★★☆☆

配置中心的原理与最佳实践？

**答案：**
核心能力：配置集中管理（环境/集群/命名空间隔离）、变更实时推送（长轮询或长连接）、本地快照容灾（配置中心挂了用上次快照启动）、变更审计与灰度发布、敏感配置加密（KMS/Jasypt）。最佳实践清单：①配置分层——应用内默认值 < 环境配置 < 全局配置，职责清晰；②什么进配置中心——会变的运行参数（阈值、开关、超时），不变的构建期依赖（连接串模板外的镜像版本）；③动态生效——监听器刷新 Bean（@RefreshScope/监听事件），线程池参数动态调整是典型应用（K-JUC-006）；④变更流程——评审+灰度+一键回滚，配置变更视同发布。大坑：配置依赖顺序（启动时配置中心不可用的重试与失败策略）。


### Microservices-001-009 | ★★★★☆

注册中心 CAP 选择

微服务注册中心在 CAP 中通常优先选 AP，主要原因是：

A. 数据不一致无法容忍
B. 注册中心短暂不可用/返回旧列表的影响，小于"整体拒绝服务"；调用失败可由重试熔断兜底
C. CP 实现简单
D. 强一致无法实现

**答案：** B

**解析：**
可用性优先：旧列表导致的失败可被负载均衡重试吸收；CP（ZK 选举期间）会全局瘫痪；A/C/D 错。

Eureka AP、ZooKeeper/Consul CP、Nacos 双模。


### Microservices-001-010 | ★★★★★

熔断器状态机

熔断器从 Open 状态恢复到 Closed 的必经状态是：

A. 直接恢复
B. Half-Open（放行少量探测请求，成功则闭合、失败则重回 Open）
C. Frozen
D. 不存在恢复机制

**答案：** B

**解析：**
冷却期后进入半开放行探测，验证下游恢复；A 错（可能再打挂）；C/D 无此概念。

Closed→Open→Half-Open→Closed/Open 循环。


### Microservices-001-011 | ★★★★☆

限流算法选择

要求"允许一定突发流量、平均速率受限"的限流算法是：

A. 固定窗口计数
B. 滑动窗口
C. 漏桶
D. 令牌桶

**答案：** D

**解析：**
令牌桶按速率放令牌、桶可积攒，空闲后的突发可立即消费积攒令牌；漏桶恒定速率整流不允许突发；A 有临界突刺；B 是精确化的窗口。

令牌桶=平均速率+突发容量；漏桶=绝对平滑。

### SoftwareTesting-001-001 | ★★★★☆

黑盒测试和白盒测试的区别？常见测试方法有哪些？

**答案：**
黑盒测试不关心内部结构，只根据需求验证输入输出行为，方法有等价类划分、边界值分析、因果图/判定表、场景法、错误推测法；白盒测试基于代码内部逻辑设计用例，覆盖标准从弱到强：语句覆盖 < 判定覆盖（分支）< 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖。两者互补：黑盒发现"功能不对"，白盒发现"内部逻辑路径没被走到"。测试层次金字塔：单元（白盒为主）→ 集成（接口）→ 系统（黑盒为主）→ 验收（用户视角）（K-SWE-006）。

**解析：**
等价类：把输入域分成若干"处理等价"的类，每类取一个代表（有效等价类+无效等价类都要测）；边界值在等价类基础上聚焦边界及其邻点（min-1, min, min+1, max-1, max, max+1）——缺陷最爱藏在边界。判定表适合多条件组合逻辑；白盒的判定覆盖要求每个判定的真假分支都执行一次，条件覆盖要求每个原子条件的真假都出现（判定覆盖≠条件覆盖的辨析是高频考点）。


### SoftwareTesting-001-002 | ★★★★☆

软件测试的四个层次分别测什么？

**答案：**
单元测试——最小可测单元（函数/类），开发编写，多用 Mock 隔离依赖；集成测试——模块/服务之间的接口与交互（关注契约、数据传递），常见手段 Testcontainers 起真实依赖；系统测试——在完整集成的系统上按需求验证功能与非功能（性能/安全），黑盒为主；验收测试——以用户/需求方视角确认"是否可交付"，含 UAT、Alpha/Beta 测试。越往下越白盒、越快、越多；越往上越黑盒、越慢、越少——测试金字塔的成本逻辑（K-SWE-006）。


### SoftwareTesting-001-003 | ★★★☆☆

测试金字塔是什么？单元测试怎么写才有价值？

**答案：**
金字塔三层：底层单元测试（大量、快、稳定，覆盖分支与边界）、中间接口/集成测试（API 层，真实依赖或 Testcontainers 起数据库）、顶层端到端（少量关键路径）。单测有价值的写法：测行为不测实现（重构后测试不该全崩）；AAA 结构（Arrange-Act-Assert）清晰；每个测试只验证一个行为；边界与异常分支优先（空集合、并发、金额精度）；命名表达场景（should_throw_when_negative_amount）。Mock 原则：只 mock 边界（下游 RPC、时钟、随机），不 mock 被测类内部；过度 mock 的测试=实现耦合的摆设。落地支撑：JaCoCo 覆盖率门禁、mutation testing（变异测试检验测试有效性，进阶加分）。


### SoftwareTesting-001-004 | ★★★★☆

等价类与边界值

程序要求输入 1~100 之间的整数。采用边界值分析法设计用例，下列哪组测试值最符合边界值思想：

A. 50
B. 1, 100
C. 0, 1, 2, 99, 100, 101
D. -100, 50, 200

**答案：** C

**解析：**
- A：错误。只取中间代表值是等价类（有效类）的做法，未覆盖边界。
- B：错误。只测上界两个端点，漏掉端点邻点与下界。
- C：正确。边界值分析取 min-1、min、min+1 与 max-1、max、max+1 共六个邻界点。
- D：错误。0 与 200 虽在界外但偏离过远，且漏掉 min/max 端点本身与邻点。

边界值 = 边界点 + 其相邻点；缺陷在边界聚集。


### SoftwareTesting-001-005 | ★★★☆☆

白盒覆盖强度

白盒测试覆盖准则中，满足"条件组合覆盖"则必然满足的是：

A. 语句覆盖
B. 路径覆盖
C. 判定覆盖与条件覆盖
D. 以上都不必然

**答案：** C

**解析：**
- A：虽然条件组合覆盖实际也能保证语句覆盖，但就"必然满足的准则层级"而言，标准的强弱链是条件组合 ⊇ 判定覆盖 + 条件覆盖；本题考标准链表述，C 最准确。
- B：错误。路径覆盖要求所有可执行路径，条件组合覆盖不保证路径可达性组合。
- C：正确。每个条件取值的所有组合都出现，则每个判定真假分支、每个原子条件真假都被覆盖。
- D：错误。C 成立。

覆盖强度链：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径。


### SoftwareTesting-001-006 | ★★★☆☆

测试层次归属

关于软件测试层次，下列说法正确的有：

A. 单元测试通常由开发人员编写，可使用 Mock 隔离外部依赖
B. 集成测试关注模块/服务之间的接口与交互
C. 验收测试由最终用户或需求方主导确认可交付性
D. 系统测试必须在单元测试全部通过之前完成设计但禁止执行

**答案：** A、B、C

**解析：**
- A：正确。单元测试开发自写，Mock 隔离下游是标准实践。
- B：正确。集成测试的核心对象是接口与交互契约。
- C：正确。验收测试（UAT）由用户/需求方确认。
- D：错误。V 模型确实要求测试设计提前，但执行上系统测试在集成与系统联调之后进行，"禁止执行"表述错误且不现实。

单元→集成→系统→验收的对象与责任人区分。


### SoftwareTesting-001-007 | ★★☆☆☆

判定表适用场景

某功能输出取决于"会员等级、订单金额、是否首次购买"三个条件的真假组合，最适合的黑盒测试设计方法是：

A. 判定表法
B. 场景法
C. 随机测试
D. 路径覆盖

**答案：** A

**解析：**
- A：正确。多逻辑条件组合决定动作的场景，判定表能系统枚举条件组合并消除遗漏与冗余。
- B：错误。场景法适合业务流程/事件流类功能。
- C：错误。随机测试不作系统设计方法。
- D：错误。路径覆盖是白盒方法，与题干的黑盒语境不符。

方法选择：条件组合→判定表；流程→场景法；输入域→等价类/边界值。


### SoftwareTesting-001-008 | ★★★☆☆

回归测试

关于回归测试，下列说法正确的有：

A. 修改代码后重跑已有测试用例，确认未引入新缺陷
B. 回归测试用例集应该优先自动化
C. 回归测试只需要测试被修改的函数本身
D. CI 流水线中的自动化测试本质上就是持续进行的回归测试

**答案：** A、B、D

**解析：**
- A：正确。回归测试的定义。
- B：正确。高频回归只有自动化才可持续。
- C：错误。修改可能影响调用方与间接依赖，回归范围应基于影响分析，而非仅改动的函数。
- D：正确。CI 每次合并自动跑测试集，正是持续回归。

回归测试 = 变更后的影响面验证；自动化是其工程前提。


### SoftwareTesting-001-009 | ★★★★☆

黑盒方法匹配

输入为 1~100 的整数（1~50 有效），划分有效等价类与两个无效等价类，最少需要的用例数是：

A. 1
B. 2
C. 3
D. 100

**答案：** C

**解析：**
有效类 1 个 + 无效类（<1、>100）2 个 = 3 个用例覆盖所有类；A/B 覆盖不全；D 是穷举误解。

每个等价类至少一个代表用例。


### SoftwareTesting-001-010 | ★★★☆☆

判定覆盖 vs 条件覆盖

判定 `if (A && B)`，测试用例使 A=true,B=false 与 A=false,B=true 两组执行。该用例集满足：

A. 条件覆盖但不满足判定覆盖
B. 判定覆盖但不满足条件覆盖
C. 两者都满足
D. 两者都不满足

**答案：** A

**解析：**
两组中每个原子条件 A、B 都取过真与假，满足条件覆盖；但 `A&&B` 两次都为 false，判定只走了假分支，不满足判定覆盖；B/C/D 错。

条件覆盖不蕴含判定覆盖（判定/条件覆盖才同时满足）。


### SoftwareTesting-001-011 | ★★★☆☆

软件测试原则

符合软件测试原则的有：

A. 测试应尽早、不断进行（测试左移）
B. 缺陷集群：少数模块集中多数缺陷
C. 穷举测试是不可能的
D. 杀虫剂悖论：重复同样用例会降低发现新缺陷的能力，需更新用例

**答案：** A、B、C、D

**解析：**
均为经典测试原则。

原则驱动测试策略：优先缺陷集群模块、及时更新用例。

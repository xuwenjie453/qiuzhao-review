### MySQL-001-001 | ★★★★★

为什么 MySQL 索引通常使用 B+ 树而不是 B 树、红黑树或哈希表？

**答案：**
索引存在磁盘上，核心矛盾是减少磁盘 IO 次数。对比四点：①哈希表只支持等值查询，不支持范围和排序；②红黑树/AVL 是二叉的，千万级数据树高几十层，每层一次 IO 不可接受；③B 树每个节点都存数据，单节点放不下更多键，树变高，且范围查询要中序回溯；④B+ 树非叶子节点只存键不存数据，单页（16KB）能放更多键，3~4 层可支撑千万级行，所有数据在叶子层且叶子间有双向链表，范围查询顺着链表扫即可。所以 B+ 树在"树高（IO 次数）"和"范围查询"两项上综合最优。

**解析：**
量化支撑结论：InnoDB 页 16KB。假设主键 bigint 8B + 页指针 6B ≈ 14B，一个非叶子页约 16K/14 ≈ 1170 个分叉；叶子页按每行 1KB 算放 16 行。三层树：1170 × 1170 × 16 ≈ 2190 万行——即三层 B+ 树可索引两千万行，一次主键查询最多 3 次页 IO（顶层常驻内存时更少）。这个数字要能现场推。

对比 B 树的第二层意义：B 树数据分散在所有层，范围扫描需要在树上反复定位；B+ 树叶子链表把范围查询变成顺序 IO，配合预读非常高效。

哈希索引并非不存在：Memory 引擎、InnoDB 的自适应哈希索引（AHI）是热点页的辅助加速，但不是通用索引形态。


### MySQL-001-002 | ★★★★★

聚簇索引和二级索引的区别？什么是回表？怎么避免？

**答案：**
InnoDB 是索引组织表：主键索引即聚簇索引，叶子页存整行数据；二级索引（普通/唯一/联合）叶子存"索引列+主键值"。用二级索引查询后还要拿主键回聚簇索引再查整行，这个动作叫回表——二级索引查到的主键越多，回表次数越多。避免方式是覆盖索引：把查询需要的列都放进联合索引，explain 出现 Using index，直接在二级索引树上拿结果不回表。设计启示：高频查询按需建联合索引；`select *` 是回表恶化的元凶。

**解析：**
成本模型举例：`select * from t where a=?`，a 有索引且命中 1 万行——1 万次回表（随机 IO）可能比全表还慢，优化器会转全表扫描。改写为 `select id,a,b from t where a=?` 且建联合索引 (a,b) 则零回表。

MyISAM 对比（历史）：数据文件与索引分离，所有索引叶子都存数据地址，无"聚簇/二级"差异——引擎对比时可提。

主键长度的影响：二级索引都携带主键，主键越长二级索引越胖，这也是"主键要短、有序"的原因之一。


### MySQL-001-003 | ★★★★★

哪些情况会导致索引失效？

**答案：**
高频失效场景：①对索引列做函数或运算（`date(create_time)='2026-01-01'`、`id+1=10`）；②隐式类型转换（字符串列传数字，或反过来按列方向转换）；③联合索引不满足最左前缀，或范围查询之后的列失效；④like 以 % 开头（前缀通配）；⑤or 两侧有非索引列；⑥优化器判断回表成本过高转全表（区分度低，如性别列）；⑦not in / != / is not null 视选择性而定；⑧join 字符集/排序规则不一致。核心判断方法不是背清单，而是看 explain：type 是否退化（index/ALL）、key 是否为目标索引、rows 估算是否异常。

**解析：**
原理性解释胜过背诵：索引按"列的原值"有序组织，任何"加工后才能匹配"的写法（函数、运算、隐式转换发生在列上）都无法利用有序性。隐式转换方向要记准：字符串列与数字比较时，MySQL 把**列**转成数字（每行转换，失效）；反过来把常量转数字不伤索引——所以"字符列传数字"失效，"数字列传字符串"多数场景可用（但常量转换有截断风险）。

范围之后的列失效原因：范围匹配后，后续列在索引内已无序，只能在这段范围内逐行过滤（可能用 ICP 优化）。


### MySQL-001-004 | ★★★★★

联合索引的最左前缀原则是什么？联合索引怎么设计顺序？

**答案：**
联合索引 (a,b,c) 的排序是先按 a、a 相同按 b、再按 c，因此"从最左列开始连续匹配"才能利用有序性：a / a,b / a,b,c 可用；b、b,c、a,c 只能用 a（c 部分无法直接定位，只能过滤）。遇到范围条件（>、<、between）后，范围列之后的索引列不再参与定位（8.0 的 ICP/跳扫能部分缓解）。设计顺序的经验法则：等值条件列在前、范围列靠后，排序列紧随等值列；同时考虑该索引能覆盖的查询集合，用最少索引服务最多查询。

**解析：**
设计推演示例：查询模式 `where user_id=? and status=? order by create_time desc limit 20` 与 `where user_id=?`，最优索引 (user_id, status, create_time)：两列等值定位后 create_time 有序，order by 免排序、limit 提前终止扫描。若把范围列放中间，如 (user_id, create_time, status) 且条件是 user_id+时间范围+status，则 status 只能过滤不能定位。

区分度原则：选择性好（基数/行数高）的列优先进入索引前缀，但也必须服从查询形态——不能脱离 SQL 谈顺序。

索引数量控制：每个索引都参与写放大（二级索引都带主键），单表索引建议克制，优先合并为联合索引。


### MySQL-001-005 | ★★★★☆

什么是覆盖索引？怎么利用它优化深分页？

**答案：**
覆盖索引指查询所需列全部包含在某个索引中，执行时在二级索引树上即可取齐数据，不回表，explain 显示 Using index。深分页 `limit 1000000, 20` 慢在OFFSET 前的 100 万行都要被扫描（即使不返回），且大多是回表后的浪费。两种优化：①游标/连续分页——记住上一页末尾的有序键，`where id > last_id order by id limit 20`，利用索引定位直接跳过；②延迟关联——`select * from t join (select id from t where ... order by x limit 1000000,20) tmp using(id)`，先用覆盖索引只翻主键，再对 20 行回表。跳转式深分页若业务必须，只能靠更强索引或搜索引擎。

**解析：**
游标分页的前提：排序键稳定且唯一（配合 id 兜底），不能跳页——这是产品交互的取舍点。延迟关联本质是"先在窄索引上完成全部过滤排序，再小范围回表"。

排序的坑：order by 列若不在索引内，会出现 filesort（临时表排序），深分页下代价爆炸；联合索引把排序列纳入即可消除。

count 与分页分离：列表页 count(*) 同样昂贵，可缓存计数或"下一页"式交互省 count。


### MySQL-001-006 | ★★★★★

事务的 ACID 分别靠什么实现？

**答案：**
原子性：undo log——修改前记录反向操作（insert 记 delete、update 记旧值），回滚时逆序重放。持久性：redo log——WAL（先写日志后写数据页），事务提交顺序化落盘 redo，宕机后重放恢复；脏页由后台异步刷盘。隔离性：锁 + MVCC——写写冲突靠锁，读写并发靠多版本快照读。一致性：前三者共同保证的最终结果，外加应用层约束（唯一键、外键逻辑、业务校验）。回答时点出"一致性是目的，AID 是手段"是加分项。

**解析：**
WAL 的意义：数据页随机写昂贵，redo 是顺序追加写，把随机写转化为顺序写+后台合并。redo log 是物理日志（页级修改），binlog 是逻辑日志（语句/行变更），二者职责不同：redo 保 crash-safe，binlog 服务复制与归档。提交时两阶段提交（K-MYSQL-011）保证两者一致。

undo 不只服务回滚：MVCC 的版本链（roll_pointer 串起历史版本）也依赖 undo 记录；purge 线程在无读视图引用后清理。

组提交（group commit）：多个事务的 redo 合并 fsync，高并发下显著提升提交吞吐。


### MySQL-001-007 | ★★★★★

事务隔离级别有哪些？MVCC 是怎么实现的？

**答案：**
SQL 标准四级：读未提交（脏读）、读已提交 RC（不可重复读）、可重复读 RR（默认，InnoDB 基本解决幻读）、串行化。InnoDB 的 MVCC 只作用于快照读（普通 select）：每行隐藏字段 trx_id（最后修改事务）与 roll_pointer（指向 undo 版本链）；事务读取时生成 ReadView，包含活跃事务列表、低/高水位；沿版本链找第一个"对该 ReadView 可见"的版本。RC 与 RR 的唯一实现差异是 ReadView 的生成时机：RC 每条语句生成一次（能看到别事务已提交的新数据，故不可重复读），RR 整个事务第一次快照读时生成并复用（整个事务视图一致）。当前读（select for update / update）不走 MVCC，靠锁保证。

**解析：**
可见性判定算法（要能口述）： trx_id < low_water：已提交，可见；trx_id >= high_water：ReadView 之后开启的，不可见；中间：在活跃列表里则不可见，不在（已提交）则可见；不可见就沿 roll_pointer 找上一版本重判。

RR 下"基本解决幻读"的准确表述：快照读靠 MVCC 看不到新插入行；当前读靠临键锁（next-key lock）锁住间隙阻止插入。但"先快照读后当前读"的混合序列仍可能观察到幻影行——严格说幻读是被规避不是被消灭。

长事务问题：RR 的 ReadView 会阻止 purge 清理旧版本，长事务导致 undo 膨胀、查询变慢——监控 information_schema.innodb_trx。


### MySQL-001-008 | ★★★★☆

可重复读下是怎么解决幻读的？间隙锁了解一下？

**答案：**
分读法处理：快照读（普通 select）用 MVCC，看不到其他事务插入的行，无幻读；当前读（for update/update）用临键锁 = 记录锁+间隙锁，锁住已存在记录及其前间隙，阻止其他事务在范围内插入新行。间隙锁只在 RR 存在（RC 没有间隙锁，所以 RC 有幻读但死锁少）。间隙锁的特性：只阻止插入，之间互相不冲突（两个事务可同时持有同一间隙的间隙锁），这也是间隙锁引发死锁的典型温床。混合读的边界情况：先普通 select 再 for update，可能看到"幻影行"——前后两个读法视角不同。

**解析：**
加锁规则（8.0 表述）：默认加临键锁（记录+前间隙）；等值命中唯一索引退化为记录锁；等值未命中，临键锁退化为间隙锁；范围查询对扫过的区间加临键锁。唯一索引等值锁定存在的行是"记录锁"——这解释了为什么 select for update 主键点查不会锁间隙。

死锁案例模型：A、B 都对同一间隙持有间隙锁（相容），随后 A 向该间隙插入 → 等 B；B 也插入 → 互相等待，死锁。缓解：RC 消除间隙锁、缩短事务、索引精确命中（避免锁扩大）。


### MySQL-001-009 | ★★★★☆

InnoDB 有哪些锁？行锁是怎么加的？

**答案：**
按粒度/意图分：全局锁、表级元数据锁 MDL（DDL 与查询互斥）、表级意向锁（IS/IX，表意"行已加锁"，用于快速表级冲突判断）、行级锁（InnoDB）。行锁加在索引记录上：记录锁（唯一索引等值命中）、间隙锁、临键锁（记录+间隙）、插入意向锁。共享锁 S（for share）与排他锁 X（for update/DML）。两个关键事实：①行锁锁的是索引项，条件无索引时升级为"扫过的所有记录"，近似锁全表；②不同索引上的锁可以同时持有（主键锁与二级索引锁共存），死锁常由此交叉产生。

**解析：**
MDL 的生产事故模型：长事务持有某表 MDL 读锁，DDL 请求 MDL 写锁排队，后续所有查询排在 DDL 之后——整表"假死"。治理：DDL 前 kill 长事务、用 online DDL/gh-ost 低峰变更、8.0 的 alter 可设等待超时。

AUTO-INC 锁：自增插入的并发控制，8.0 默认 interleaved 模式保证连续性弱化换取并发。

锁等待排查：`SELECT * FROM sys.innodb_lock_waits` 直接给出阻塞双方与 SQL。


### MySQL-001-010 | ★★★☆☆

MySQL 死锁怎么排查和避免？

**答案：**
排查入口：`SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 段（8.0 也可开 innodb_print_all_deadlocks 记入错误日志），能看到两个事务各自持有哪些锁、在等哪些锁、执行的 SQL；结合 performance_schema.data_locks 复盘。典型模式：①两个事务以不同顺序更新相同行集合；②间隙锁相容+插入互等（RR 特有）；③不同索引路径加锁交叉。避免手段：统一加锁顺序（按主键排序批量更新）、事务尽量短、索引精确命中避免锁放大、热点行用原子更新、必要时降 RC 消除间隙锁、应用侧重试（死锁会回滚一个事务并报 1213 错误，业务可捕获重试）。

**解析：**
InnoDB 死锁处理：等待图检测，选择回滚代价小（undo 量少）的事务，返回 ER_LOCK_DEADLOCK。应用必须处理该错误而不是裸抛——重试框架对 1205（锁等待超时）与 1213（死锁）都应支持有限次重试。

间隙锁死锁的最小模型值得会讲：RR 下 SELECT ... FOR UPDATE 未命中记录锁的是间隙（相容），两个事务都持有后同时 INSERT，互相等对方释放间隙锁。RC 无间隙锁即无此模式。


### MySQL-001-011 | ★★★★★

redo log、undo log、binlog 的区别？为什么要两阶段提交？

**答案：**
redo log：InnoDB 物理日志，记录页的修改，循环写，保证 crash-safe（持久性）。undo log：逻辑反向日志，用于回滚与 MVCC 版本链。binlog：Server 层逻辑日志（STATEMENT/ROW/MIXED），追加写，用于主从复制与数据恢复归档。两阶段提交的原因：redo 与 binlog 是两个独立日志系统，直接"先 A 后 B"提交会在中间宕机时产生不一致——redo 有 binlog 无（主库多了一条从库没有），或反之（从库多了主库没有）。2PC 把 binlog 作为事务提交的最终裁决点：redo prepare（写 xid）→ 写 binlog → redo commit；恢复时扫描 redo prepare 状态，据 binlog 是否完整 xid 决定提交或回滚。

**解析：**
崩溃恢复判定规则：redo 处于 prepare 时查 binlog——binlog 完整（含 xid event）则提交，否则回滚。保证的效果：binlog 一旦写下，主库必然提交，主从不丢。

组提交（binlog group commit）：多个并发事务合并一次 fsync，分 stage（flush/sync/commit），高并发 TPS 的关键。

binlog 三格式对比：STATEMENT 记语句（体积小，但 now()/limit 等不确定性语句主从可能不一致）；ROW 记行变更（一致性强、体积大，8.0 默认，配合 binlog_row_image 控制体积）；MIXED 折中自动切换。


### MySQL-001-012 | ★★★★☆

主从复制的原理？主从延迟怎么产生和解决？

**答案：**
复制链路：主库写 binlog → 从库 IO 线程拉取写入本地 relay log → SQL 线程重放（8.0 多线程复制按事务依赖并行）。延迟三大来源：①主库并发写、从库单/受限并行回放；②大事务（一条大 ROW 事务回放耗时等于执行耗时）；③从库机器/负载差、网络抖动。解决：并行复制（8.0 writeset）、拆大事务、半同步复制缓解"读从库拿旧数据"的程度、业务侧强制读主（关键路径写后读）、监控 Seconds_Behind_Master（有局限，配合 GTID 位点差）。CAP 上的事实：异步复制必然存在窗口，设计上要承认并绕开。

**解析：**
复制模式：异步（默认，主库不等）；半同步（至少一个从库收到 binlog 才返回，AFTER_SYNC 8.0 默认无损语义）；组复制 MGR（Paxos 多数派）。金融场景半同步/组复制起步。

GTID 价值：全局事务标识，主从切换免手工找位点，故障转移自动化基础。

读写分离的"写后读"问题：会话级方案（ Sticky 路由：写后 N 秒读主）、GTID 等待（select wait_for_executed_gtid_set）、关键读直连主库。


### MySQL-001-013 | ★★★★★

explain 的关键字段有哪些？慢 SQL 的排查流程？

**答案：**
重点字段：type（访问类型，性能序 system>const>eq_ref>ref>range>index>ALL，线上至少 range，出现 ALL 警惕）、key/key_len（实际用的索引及长度，判断联合索引用了几列）、rows（估算扫描行数）、filtered（过滤比例）、Extra（Using index 覆盖/Using where 过滤/Using filesort 排序/Using temporary 临时表，后两者是优化目标）。排查流程：慢日志定位 SQL → explain analyze 看真实计划与耗时分布 → 检查索引命中与扫描量 → 改写 SQL 或补索引 → 压测验证 → 上线监控。系统级入口：sys 库（statement_analysis）、慢日志、performance_schema。

**解析：**
key_len 计算（判断联合索引用了几列）要会：int 4、bigint 8、varchar(n) = 字符集宽×n+2（utf8mb4×4）、可空再+1。例如 utf8mb4 varchar(50) 可空 = 200+2+1=203。

Using temporary 高频来源：group by 无索引列、distinct + join、子查询物化。filesort 内存/磁盘排序受 sort_buffer 限制，超限落盘。

优化手段优先级：改写 SQL（等价变换、拆分复杂查询）→ 索引（联合、覆盖）→ 结构（冗余字段、汇总表）→ 架构（缓存、读库、搜索引擎）。


### MySQL-001-014 | ★★★☆☆

char 和 varchar 的区别？字段设 NULL 有什么影响？

**答案：**
char(N) 定长，不足补空格（取回时截断尾部空格），适合定长编码（国家码、MD5）；varchar(N) 变长，N 是字符数（utf8mb4 下最大字节数受限行大小），另需 1~2 字节长度前缀。NULL 的影响：①索引可以存 NULL（可空列索引多一个字节），但 `count(col)` 不计 NULL、聚合与比较语义易错；②NULL 参与 is null 查询与优化器统计的特殊性；③建议规范"能 not null 就 not null + 默认值"，但不要绝对化——"未填写"与"0/空串"语义确实不同时，NULL 是正确建模。大字段 text/json 建议拆表或对象存储，避免行溢出拖累缓冲池。

**解析：**
行格式与溢出：varchar 超长部分溢出页（DYNAMIC 格式留 20 字节指针）；一行总长受 65535 字节限制（含变长开销）。

排序规则（collation）是隐性坑：utf8mb4_general_ci vs _0900_ai_ci（8.0 默认） vs _bin（区分大小写、二进制序）——join 两表 collation 不一致导致索引失效（隐式转换），生产高频事故。

金额用 DECIMAL 不用 float/double（精度）；主键用 bigint unsigned。


### MySQL-001-015 | ★★★☆☆

count(*)、count(1)、count(列) 的区别？哪个快？

**答案：**
语义先分清：count(*) 与 count(1) 都统计行数（含 NULL），官方明确二者无性能差异，8.0 优化器对 count(*) 还有专门优化；count(col) 统计该列非 NULL 的行数，语义不同。性能上 count(col) 要逐行取值判 NULL，最贵；count(*) 可任选最小索引扫（优化器自动挑小的索引树）。大表 count 慢的本质是精确计数必须遍历，方案：①近似值 explain rows / information_schema.tables.table_rows；②计数缓存（Redis/汇总表，注意一致性）；③业务上避免精确总数（游标分页）。

**解析：**
MyISAM 无 where 的 count(*) 是 O(1)（存了总行数），InnoDB 因 MVCC 多版本无法缓存全局计数——不同事务看到的行数不同，这是"为什么 InnoDB count 慢"的根本原因，比背"扫描全表"更深一层。

汇总表方案的一致性：事务内同步维护 or 异步对账修正；Redis 方案要有重建任务兜底。


### MySQL-001-016 | ★★★☆☆

什么时候需要分库分表？怎么做？带来哪些新问题？

**答案：**
触发信号：单表数据量/索引深度导致写入与查询明显劣化（经验量级 B+ 树千万级后开始敏感，但以实测为准）、单机容量与吞吐到顶、需要隔离故障域。两条路线：垂直拆（按业务域分库、按冷热/大字段拆表）先行；水平拆（同一表按分片键 hash/range 拆到多库多表）解决规模。分片键选择是核心决策：让最高频查询路径单分片可达（如订单表按 user_id）。带来的新问题必须能列：跨分片查询与聚合、分布式事务、全局唯一 ID、扩容数据迁移（双写/影子表）、二次扩容的 hash 重平衡。中间件：ShardingSphere、MyCat；云上优先托管分布式库（PolarDB-X/TiDB）。

**解析：**
水平分片的形态：只分表不分库（IO 仍集中）、分库分表（并行度与容量都扩展）、外加每库一主多从。range 分片易热点（自增集中尾部）但扩容平滑；hash 分片均匀但扩容要迁移（一致性 hash/翻倍扩容缓解）。

跨分片聚合：中间件归并聚合代价高，复杂分析应走数仓/ES；业务上设计"查询键=分片键"的信息架构（订单同时提供 user_id 与 order_id 两种路由——order_id 里编码 user 片段，基因法）。

分布式事务：尽量单分片事务化（同 user 数据同分片），跨分片用最终一致（消息/对账），强一致成本极高。


### MySQL-001-017 | ★★★☆☆

分布式 ID（全局唯一 ID）有哪些方案？怎么选？

**答案：**
主流四类：①数据库号段：批取一段号在内存分配，DB 压力小、ID 趋势递增，重启有空洞，双 buffer 预取消除毛刺；②雪花算法 snowflake：64 位=时间戳+机器位+序列位，本地生成无依赖、趋势递增，问题是时钟回拨（等待/拒绝/历史位分配策略）与机器 ID 分配管理（ZK/DB/配置中心）；③UUID v4：全局唯一无协调，无序、36 字符太长，索引写放大，作主键不合适；④Redis/etcd 自增：原子计数器，强依赖可用性。选型逻辑：趋势递增对 B+ 树友好（K-MYSQL-001），故生产主键几乎都在号段与雪花之间选；小系统号段最省心，大规模独立服务用美团 Leaf/百度 UidGenerator 这类成熟实现。

**解析：**
雪花位分配可调：常用 1 符号+41 时间戳(69 年)+10 机器+12 序列（单机 4 万/毫秒）。高并发单机不够时增序列位减机器位。时钟回拨对策分级：小回拨自旋等待、大回拨拒绝服务+告警、或使用"逻辑时钟"取最大值。

业务属性 ID 与路由：ID 中嵌入分片基因（K-MYSQL-016）时，雪花自定义位段是常见改造。


### MySQL-001-018 | ★★★★★

线上一个 SQL 突然变慢，你的完整排查思路？

**答案：**
先分层定位是否真"变慢"：数据库层（同 SQL 历史对比）、实例层（整体负载）、还是应用层误报。数据库侧四查：①执行计划是否变化——统计信息过期、索引被删、优化器版本行为差异（explain 对比）；②锁等待——sys.innodb_lock_waits、长事务阻塞（information_schema.innodb_trx）；③服务器资源——CPU、IO、缓冲池命中率、swap；④外部因素——备份任务、DDL、批量 job、主从切换。常见根因清单：统计信息失真、隐式转换/collation 变化、参数化 SQL 计划抖动、大事务锁队、buffer 池被大查询冲刷。处置：kill 阻塞源/限流、analyze table、加 hint 稳定计划、SQL 改写，之后补防回归（SQL 审核卡点）。

**解析：**
"同一 SQL 忽快忽慢"的机理：参数不同导致优化器分别估算（自适应）；buffer 池冷热差异；绑定执行计划的缺失。8.0 无 plan cache（如 Oracle），每次硬解析+成本估算，统计信息漂移直接影响计划。

应急与根治分离：应急（kill/限流/hint）恢复服务；根治（索引重建、SQL 改写、统计信息自动任务、慢查门禁）防复发。


### MySQL-001-019 | ★★★★☆

为什么自增主键用 BIGINT UNSIGNED 更稳妥？AUTO_INCREMENT 的坑

**答案：**
INT 上限约 21.4 亿（UNSIGNED 约 42.9 亿），高写入业务可能触顶导致插入失败；BIGINT 天花板实际碰不到。AUTO_INCREMENT 的坑：①不保证连续——事务回滚/唯一键冲突会消耗号但不归还，重启前 MySQL 8 才持久化计数（5.7 重启回退到 max+1）；②批量插入（insert ... select）在基于语句复制下要加锁防主从号漂移；③它只保证"单调递增不重复"，不承诺无空洞，业务单号别直接当连续流水用。

**解析：**
8.0 的变化：自增计数持久化进 redo，重启不回退（5.7 是"max(id)+1"内存值）。分布式场景自增不全局唯一，需雪花/号段（K-MYSQL-017）。insert ignore/on duplicate key 也会烧号。监控 auto_increment_ratio 提前扩容。


### MySQL-001-020 | ★★★★☆

在线 DDL 的风险与大表变更怎么做

**答案：**
直接 ALTER 大表的三个风险：长事务/MDL 排队引发整表"假死"、锁表窗口、主从延迟。安全路径：①MySQL 8 的 INSTANT DDL（加列等秒级，只改元数据）；②pt-online-schema-change/gh-ost：建影子表+触发器或 binlog 同步增量+原子 rename，全程不锁；③低峰执行+超时与限流+可回滚方案。变更前必查长事务（information_schema.innodb_trx）——一个持 MDL 读锁的查询就能让后续全部排队。

**解析：**
MDL（元数据锁）机制：DML 加 MDL 读锁，DDL 需要 MDL 写锁，写锁到来后新读请求排队，形成"DDL 等长查询、全部等 DDL"的连锁。gh-ost 相比 pt-osc 的优点：不依赖触发器、可暂停限流、更可控的切换。云 RDS 的 DDL 通道通常封装了这些。回滚预案：加列易回滚，改类型/改字符集几乎不可逆，必须演练。


### MySQL-001-021 | ★★★★☆

事务隔离级别与读现象

事务 T1 两次执行同一条查询，期间事务 T2 提交了一条新插入行并可见，导致 T1 第二次查询多出一行。该现象与最低隔离级别的组合是：

A. 脏读 / 读未提交
B. 不可重复读 / 读未提交
C. 幻读 / 读已提交
D. 幻读 / 可重复读

**答案：** C

**解析：**
- A：错误。脏读是读到他人**未提交**的数据，题面明确 T2 已提交。
- B：错误。不可重复读针对"同一行数据值变化"，本题是多出一行。
- C：正确。前后两次查询结果集行数变化（多出一行）是幻读；读已提交（RC）不隔离新插入行，存在幻读。
- D：错误。InnoDB 的可重复读通过 MVCC（快照读）与临键锁（当前读）基本消除幻读；若 T1 是 RR 仍出现行数变化，通常因为混合使用了快照读与当前读。

脏读读未提交数据；不可重复读针对行值；幻读针对结果集行数。


### MySQL-001-022 | ★★★★☆

### MySQL-001-034 | ★★★☆☆

字段类型选择

下列表设计建议正确的有：

A. 金额字段使用 DECIMAL 而非 float/double
B. 时间字段推荐 datetime(6) 或 timestamp（注意 2038 与时区）
C. 是非标记用 tinyint(1)/boolean
D. 大文本与主表同表存放，便于 JOIN

**答案：** A、B、C

**解析：**
A 对，浮点有精度误差；B 对，datetime(6) 支持微秒；C 对；D 错，大字段应拆分扩展表，避免拖累缓冲池与行迁移。

类型选择影响存储、索引与查询行为。

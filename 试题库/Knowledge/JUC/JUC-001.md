### JUC-001-001 | ★★★★★

线程有哪几种创建方式？线程的生命周期有哪些状态？

**答案：**
创建方式上，真正创建线程的只有一种——new Thread，其他都是传任务的方式：Runnable（无返回值）、Callable+FutureTask（有返回值可抛异常）、线程池提交、以及 JDK 21 的虚拟线程。生命周期按 Thread.State 有六种：NEW、RUNNABLE（含就绪与运行）、BLOCKED（等 monitor 锁）、WAITING（wait/join/LockSupport 无限期等待）、TIMED_WAITING（带超时的等待）、TERMINATED。画状态图时关键是分清 BLOCKED 只对应 synchronized 的锁排队，Lock 排队是 WAITING。

**解析：**
状态转换主线：start() 后进 RUNNABLE；抢不到 synchronized 锁进 BLOCKED，释放后重新竞争；调 wait()/join()/LockSupport.park() 进 WAITING，notify/unpark/被中断方唤醒；sleep(n)/wait(n)/parkNanos 进 TIMED_WAITING；run 结束 TERMINATED。注意：调用 start() 两次抛 IllegalThreadStateException；run() 直接调用只是普通方法调用不产生新线程。

工程实践：业务代码不应直接 new Thread（无复用、无上限、无命名），统一走线程池；虚拟线程适合 IO 密集海量任务，详见 K-JUC-018。


### JUC-001-002 | ★★★★★

synchronized 的实现原理是什么？锁升级过程讲一下。

**答案：**
synchronized 依赖对象头的 Mark Word 与 monitor（管程）。字节码层面同步代码块用 monitorenter/monitorexit，方法用 ACC_SYNCHRONIZED 标志；任意对象都关联一个 monitor，进入时计数器加一、持有线程记录 owner，可重入就是同一线程重复进入计数递增。为减少加锁成本，JDK 6 引入锁升级：无锁 → 偏向锁（只有一个线程反复进入，只在 Mark Word 记线程 ID）→ 轻量级锁（交替竞争，CAS 自旋）→ 重量级锁（竞争激烈，阻塞挂起走操作系统互斥量），整体只升不降（偏向锁可批量重偏向）。注意 JDK 15 起偏向锁默认禁用并已标记废弃，因为维护成本高于收益，现代应用大多直接从轻量级锁开始。

**解析：**
Mark Word 结构随锁状态复用 64 位（64 位 JVM）：无锁存 hashcode/分代年龄；偏向锁存线程 ID+epoch；轻量级锁存指向栈上 Lock Record 的指针；重量级锁存 monitor 对象指针。GC 分代年龄也在 Mark Word，所以锁状态与 GC 元数据共享空间，互斥复用。

重量级 monitor（ObjectMonitor）的关键字段：_owner 持有线程、_recursions 重入计数、_EntryList 阻塞队列、_WaitSet wait 集合。wait/notify 本质是线程在 _WaitSet 与 _EntryList 之间的迁移。

自旋的意义：短临界区下自旋等待比内核态挂起/唤醒便宜；自适应自旋由 JVM 根据历史成功率调整次数。


### JUC-001-003 | ★★★★★

volatile 的作用和底层原理？什么是 happens-before？

**答案：**
volatile 保证两件事：可见性（写立即刷新到主存并使其他 CPU 缓存行失效，读绕过本地缓存）和禁止指令重排（编译器与 CPU 层插入内存屏障），但它不保证原子性——i++ 这种"读-改-写"复合操作依然会丢更新。happens-before 是 JMM 的核心规则：程序顺序规则、监视器锁规则、volatile 规则（写先行于后续读）、线程启动/终止规则、传递性等；只要两个操作有 happens-before 关系，前者对后者可见。典型应用是状态标志位和双重检查锁的单例。

**解析：**
可见性的硬件背景：每个核心有私有缓存，写操作停留在 Store Buffer/缓存中，其他核心看不到。volatile 写在 x86 上体现为带 lock 前缀指令/StoreLoad 屏障，强制写缓冲刷出并失效其他核心缓存行（MESI 协议配合）。x86 本身是强内存模型，只有 StoreLoad 重排存在，所以 volatile 写读之间插入的屏障在 x86 代价较高，在其他弱模型架构（ARM）屏障更多。

禁止重排的语义按"屏障策略"表述即可：volatile 写之前的普通写不能重排到写之后；volatile 读之后的普通读不能提前。双重检查锁为什么实例字段必须 volatile：`new Singleton()` 是"分配内存→初始化→引用赋值"三步，引用赋值可能重排到初始化之前，另一线程拿到未初始化完成的对象。

原子性缺口：`volatile int i; i++` 实际是三个操作，并发下丢更新——改用 AtomicInteger 的 CAS 或锁。


### JUC-001-004 | ★★★★☆

synchronized 和 ReentrantLock 怎么选？ReentrantLock 比 synchronized 多什么？

**答案：**
功能上 ReentrantLock 多四件事：可中断获取（lockInterruptibly，避免死等）、超时获取（tryLock，适合防死锁）、公平锁（按排队顺序，吞吐低）、多个 Condition 精确唤醒分组。性能上 JDK 6 之后 synchronized 有了锁升级优化，两者无竞争/低竞争场景已接近，选型主要看功能：默认 synchronized，需要上述能力才用 ReentrantLock，且必须 try-finally 里 unlock。底层 ReentrantLock 基于 AQS：state 表示重入次数，公平版每次加锁先看队列有没有前驱，非公平版直接抢一次。

**解析：**
AQS（AbstractQueuedSynchronizer）是 JUC 锁体系的骨架：一个 volatile int state + CLH 变体的 FIFO 双向队列 + 模板方法（tryAcquire/tryRelease 由子类实现）。加锁失败线程封装成 Node 入队并 LockSupport.park 挂起，前驱释放时 unpark 后继。ReentrantLock 非公平加锁：先 CAS 抢一次 state，失败才入队；公平版用 hasQueuedPredecessors 检查队列。

Condition 与 wait/notify 对应：await 释放锁进条件队列，signal 把节点转移到同步队列；一个 ReentrantLock 可建多个 Condition（如"非满""非空"两个条件），比 synchronized 单一等待集精确。

可重入实现：持有线程记录 + state 计数，重入 state 递增，释放对称递减到 0 才真正释放。


### JUC-001-005 | ★★★★☆

讲讲 AQS 的原理。

**答案：**
AQS 是 JUC 里锁和同步器的公共骨架：核心是一个 volatile int state 表示同步状态，加一个 FIFO 的 CLH 变体双向等待队列。线程获取状态失败就被包装成 Node 入队并 park 挂起；释放时修改 state 并 unpark 队列里的后继节点。AQS 用模板方法模式把"state 怎么算获取成功"留给子类：ReentrantLock 把 state 当重入计数，Semaphore 当剩余许可，CountDownLatch 当剩余屏障数，读写锁把 state 拆成高低位表示读/写计数。独占模式和共享模式分别对应排他获取与批量放行。

**解析：**
入队细节：Node 用 CAS 追加到队尾；被唤醒的后继线程从 park 中恢复后再次 tryAcquire。前驱节点 cancel 时会有"跳过已取消节点"的清理逻辑。propagate 状态处理共享模式的唤醒传播（CountDownLatch/Semaphore 的连锁放行）。

独占 vs 共享：tryAcquire 返回是否成功；tryAcquireShared 返回负/零/正表示失败/成功但不再传播/成功且需传播。阻塞与唤醒统一由 LockSupport 完成（park/unpark，许可机制，unpark 可先于 park 生效一次）。

公平性由子类在 tryAcquire 里是否检查 hasQueuedPredecessors 决定，AQS 本身不强制。


### JUC-001-006 | ★★★★★

线程池的核心参数和任务执行流程？为什么先入队再增线程？

**答案：**
七个核心参数：corePoolSize、maximumPoolSize、keepAliveTime+unit、workQueue、threadFactory、handler（拒绝策略）。execute 提交后：核心线程数没满就创建新线程执行；满了先入队；队列满了再创建非核心线程直到 maximum；再满就执行拒绝策略（默认 Abort 抛异常，另有 CallerRuns、Discard、DiscardOldest）。"先入队再增线程"看似反直觉，是刻意设计：队列承担缓冲，避免突发流量直接拉起过多线程压垮系统；这也是为什么用无界队列时 maximumPoolSize 和拒绝策略形同虚设。

**解析：**
线程复用：Worker 继承 AQS，runWorker 循环 getTask 从队列取任务；getTask 里非核心线程通过 `poll(keepAliveTime)` 超时返回 null 退出，核心线程 take 阻塞（allowCoreThreadTimeOut 可让核心也超时回收）。

关闭：shutdown 只拒绝新任务、处理完队列；shutdownNow 中断所有线程并返回未执行任务。优雅停机顺序：shutdown → awaitTermination(超时) → shutdownNow。

CallerRunsPolicy 的隐藏价值与风险：让提交线程自己执行形成天然背压，但会阻塞上游（Tomcat 线程被拖住），要结合场景判断。

ThreadFactory 务必自定义线程名，排查问题必备。


### JUC-001-007 | ★★★★☆

线程池大小怎么设置？IO 密集和 CPU 密集怎么区分？

**答案：**
经验公式：CPU 密集型线程数 ≈ CPU 核数 + 1（+1 是防页缺失/偶尔阻塞）；IO 密集型 ≈ 核数 × (1 + 等待时间/计算时间)，等待占比越高线程可以越多。但这些只是起点，真实值必须靠压测找拐点：观察吞吐不再上升、延迟开始爬升、CPU 利用率合理的区间。更要紧的是隔离：不同业务用不同线程池，避免互相拖垮；队列要有界，配合监控与拒绝策略形成背压。

**解析：**
推导逻辑：目标是在等待期间不让 CPU 闲着。单任务时间 T = 计算时间 C + 等待时间 W，利用率 1 时线程数 ≈ 核数 × T/C = 核数 × (1 + W/C)。例子：核数 8，W:C=3:1，则 8×4=32 线程——这正是 Web 服务数据库/远程调用占比高时线程数普遍在几十的原因。

现实约束：线程本身占内存（栈 1MB 级）、上下文切换成本、下游承受能力（DB 连接池往往才是真正瓶颈，线程数不应远超连接池×合理放大）。

压测方法：固定并发梯度扫吞吐/延迟曲线；区分 CPU 用满型瓶颈（加线程无益）与下游瓶颈（加线程加剧）。


### JUC-001-008 | ★★★★★

ThreadLocal 的原理？为什么会内存泄漏？

**答案：**
每个 Thread 内部有一张 ThreadLocalMap，key 是 ThreadLocal 对象的弱引用，value 是强引用。set 时以当前线程为入口，把 `threadLocal -> value` 存进自己的 map，实现线程间隔离。内存泄漏链条：线程长生命周期（线程池），ThreadLocal 外部引用被回收后，map 里的 key 变成 null 但 value 仍被强引用链（Thread → Map → Entry → value）持有，无法回收。JDK 有自愈机制——get/set/remove 时会顺手清理 stale entry——但线程"不再使用该 ThreadLocal"时不会触发。正确用法是每次用完在 finally 里 remove()，在线程池场景这是必须项。

**解析：**
为什么 key 用弱引用：如果 key 是强引用，只要 Thread 活着，即使外部已不引用 ThreadLocal，Entry 的 key 也永远不可达，泄漏更严重。弱引用让"无外部引用的 ThreadLocal"的 key 在下次 GC 被清掉，之后 set/get/remove 的探测序列中遇到 stale entry（key==null）会清除对应 value。

InheritableThreadLocal：子线程创建时复制父线程的值；线程池复用线程会错乱，跨池传递应使用阿里 TransmittableThreadLocal（TTL）——任务提交时捕获快照、执行时回放。


### JUC-001-009 | ★★★★☆

CAS 是什么？ABA 问题怎么解决？

**答案：**
CAS（Compare-And-Swap）是一条 CPU 原子指令：传入"内存位置、期望值、新值"，只有当前值等于期望值才更新，否则失败；Java 的原子类通过 Unsafe/VarHandle 调用它，失败后循环重试（自旋）。优点是无锁、无上下文切换；缺点有三：自旋空转在高竞争下浪费 CPU；只能保证单个变量原子；ABA 问题——值从 A 改成 B 又改回 A，CAS 感知不到中间变化。ABA 的解法是加版本号，即 AtomicStampedReference（stamp 随每次修改递增），普通数值场景用 AtomicLong 递增天然规避。

**解析：**
底层指令：x86 的 `lock cmpxchg`（带 lock 前缀保证多核原子性），ARM 的 LL/SC（ldxr/stxr）。JDK 9 后推荐 VarHandle 的 compareAndSet，语义等价且更规范。

原子类家族：AtomicInteger/Long（标量）、AtomicReference（对象引用，CAS 需引用未变——注意它比较的是地址，字段变了感知不到）、AtomicIntegerFieldUpdater（反射式更新普通对象字段）、LongAdder（分段累计，高并发写更优，见 K-COL-005）。字段可见性要求：updater 要求字段 volatile。

CAS 失败重试的工程含义：竞争激烈时自旋退化为忙等，此时锁（挂起）可能更优——这就是 LongAdder 分段、以及 synchronized 升级机制反向权衡的问题。


### JUC-001-010 | ★★★☆☆

Java 内存模型（JMM）是什么？为什么需要它？

**答案：**
JMM（JSR-133，JDK 5 起）是 Java 对"多线程下读写共享变量的可见性与有序性"的抽象规范：每个线程有工作内存（抽象，对应 CPU 缓存/寄存器），共享变量在主存；线程不能直接改主存，需同步回写。它屏蔽了不同硬件内存模型的差异，给程序员确定性规则。核心是 happens-before 偏序：程序顺序、monitor 锁、volatile、线程 start/join、传递性等——满足规则的读写保证可见。JMM 既给"允许重排的自由"（性能），又给"必要时的约束"（volatile/锁/final）。

**解析：**
三级重排：编译器优化、CPU 指令乱序执行、内存系统（写缓冲）重排。单线程内 as-if-serial 保证结果不变；多线程不保护，需要同步原语建立顺序。

happens-before 规则清单（面试要能列 5 条以上）：①程序顺序（单线程内）；②锁的解锁先于后续加锁；③volatile 写先于后续读；④Thread.start 先于新线程任何动作；⑤线程所有动作先于 join 返回；⑥线程中断检测到中断；⑦对象构造完成先于 finalize；⑧传递性。

final 字段安全性：构造函数内对 final 字段的写入，在引用发布后其他线程可见（不允许重排构造器内的赋值与引用发布）。


### JUC-001-011 | ★★★★☆

CountDownLatch、CyclicBarrier、Semaphore 的区别和用法？

**答案：**
CountDownLatch 是一次性倒计数门闩：主线程 await 等待 N 个子任务完成（countDown），到 0 放行，不可重置。CyclicBarrier 是可循环栅栏：N 个线程互相等彼此到达 barrier（await），人齐后一起继续，可 reset 复用，还支持到达时执行回调动作。Semaphore 是信号量：维护许可数，acquire 消耗、release 归还，用于限流、资源池（conn.acquire/release），支持公平模式。都基于 AQS：latch 是共享模式 state 递减，semaphore 共享模式许可增减，barrier 用 ReentrantLock+Condition 实现人齐放行。

**解析：**
选型口诀：一个等多个（汇聚）用 latch；多个互相等（同步齐步）用 barrier；限制并发数量用 semaphore。

细节：latch 的 await 可带超时；count 不能回升，重复使用场景换 barrier 或新建。barrier 若有线程中断/超时会 Broken（抛 BrokenBarrierException），需要处理。semaphore 的 release 不校验归属，乱 release 会虚增许可；acquire 可中断/可超时版本按需选。

延伸：Phaser 是更灵活的多阶段栅栏（可动态注册方）；CompletableFuture.allOf 也能表达"汇聚"语义且更好组合。


### JUC-001-012 | ★★★☆☆

阻塞队列 BlockingQueue 的常用实现和区别？

**答案：**
BlockingQueue 统一了"队列满时入队阻塞、空时出队阻塞"的语义，四组方法要能背：抛异常（add/remove）、返回特殊值（offer/poll）、阻塞（put/take）、超时（offer/poll 带时间）。常用实现：ArrayBlockingQueue（定长数组、一把锁、公平可选）、LinkedBlockingQueue（默认无界链表、读写两把锁分离、吞吐略高）、SynchronousQueue（容量 0，直接移交，cachedThreadPool 用）、PriorityBlockingQueue（堆排序，无界）、DelayQueue（按到期时间出队）。生产者消费者首选就是它，替代手写 wait/notify。

**解析：**
两把锁的 LinkedBlockingQueue：putLock/takeLock 分离，入队出队可并行（计数用 AtomicInteger，唤醒逻辑跨锁通知），这也是它吞吐高的原因；代价是节点分配与 GC。ArrayBlockingQueue 单锁简单，数组预分配无节点开销。

SynchronousQueue 语义：put 必须等到 take 才返回，无缓冲、直接握手，用于任务传递（线程池的"每个任务立刻交给新线程"）。

手写生产者消费者对比：wait/notify 版要处理虚假唤醒（while 判断条件）、通知丢失等细节；BlockingQueue 封装了这些，工程首选。


### JUC-001-013 | ★★★☆☆

wait/notify 和 sleep 的区别？如何正确写一个生产者消费者？

**答案：**
区别四点：wait 是 Object 方法、必须在 synchronized 块内调用且会释放锁；sleep 是 Thread 静态方法、哪里都能调、不释放锁；wait 被 notify 唤醒（或超时/中断），sleep 到点自然醒；wait 属于对象等待条件，sleep 只是计时暂停。正确写生产者消费者的关键：用 while 循环判断条件而不是 if（防虚假唤醒和被抢跑），谁改了条件 notifyAll 或精确 notify；工程上直接用 BlockingQueue 免手写。

**解析：**
虚假唤醒（spurious wakeup）：操作系统层面允许 wait 无 notify 返回，所以规范要求循环内判断。另一个经典错误"信号丢失"：先 notify 后 wait，通知蒸发了——条件变量模式要求"先持锁检查条件再等待"正是为了消除这个窗口。

notify vs notifyAll：notify 只唤醒一个，如果唤醒的线程检查条件后继续等，而该条件只对其他线程成立，会发生全员等待的死等；保守用 notifyAll，性能敏感时精确 notify（每个 Condition 独立等待集）。

wait 释放锁的时机：进入等待前释放，被唤醒后重新竞争锁——所以从 wait 返回时条件可能又被别人改了，必须再查一遍（回到 while）。


### JUC-001-014 | ★★★★☆

死锁产生的四个必要条件？怎么排查和避免？

**答案：**
四个必要条件：互斥、持有并等待、不可剥夺、循环等待——打破任意一个即可避免，工程上最常用"全局固定的加锁顺序"打破循环等待，其次用 tryLock 超时回退打破持有并等待。排查手段：jstack 线程栈直接显示 "Found one Java-level deadlock"；jconsole/Arthas 的 thread 命令；应用日志中表现为一组线程集体卡死、CPU 不高。运行期兜底：ReentrantLock.tryLock 带超时的获取策略。

**解析：**
典型案例：转账场景线程 1 锁 A 再锁 B，线程 2 锁 B 再锁 A。修复：按账户 ID 排序后依序加锁（System.identityHashCode 一致化处理）；或用 tryLock 拿不到第二把就释放第一把重试。

排查步骤：①监控发现接口超时/线程池耗尽；②jstack <pid> 看 BLOCKED 链与 "waiting to lock <0x...>" 交叉引用；③确认持锁代码路径；④修复锁序或缩小临界区。数据库层面的死锁（间隙锁交叉）同理用 `SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK。

活锁与饥饿区分：活锁是互相让路反复重试不前进；饥饿是优先级/调度导致某线程长期得不到锁或 CPU。


### JUC-001-015 | ★★★★☆

Future 和 CompletableFuture 的区别？CompletableFuture 有哪些常用编排方式？

**答案：**
Future 只有 get（阻塞）、cancel、isDone，无法表达"完成后自动做什么"，任务间依赖只能靠阻塞轮询。CompletableFuture 实现了 CompletionStage，把回调链与组合器做成流式 API：thenApply（转换结果）、thenCompose（串联另一个异步任务，避免嵌套 Future）、thenCombine（合并两个独立结果）、allOf/anyOf（汇聚/竞速）、exceptionally/handle（异常兜底）。还可以指定每步在哪个执行器跑（async 后缀重载），把阻塞型下游调用的回调切到独立线程池。

**解析：**
默认线程规则（必考）：不带 async 的回调由"完成它的线程"执行，若调用时已完成则由调用线程执行；async 版本默认走 ForkJoinPool.commonPool——在 Web 应用里这是隐性共享池，IO 型回调必须显式传入自定义线程池隔离。

超时：JDK 9+ 的 orTimeout(timeout, unit)/completeOnTimeout(fallback, timeout)。异常传播：链条上任一环节异常，后续非异常处理步骤被跳过，直到 exceptionally/handle/whenComplete；handle 无论成败都执行且可转换结果。

allOf 的返回是 CompletableFuture<Void>，通常接 thenApply 逐个 join 取结果；join 抛非受检异常，get 抛受检需处理。


### JUC-001-016 | ★★☆☆☆

ThreadLocalRandom 为什么快？随机数在并发下要注意什么？

**答案：**
共享的 Random 用一个 AtomicLong 做 seed，每次 nextLong 都 CAS 更新，多线程竞争下大量自旋浪费。ThreadLocalRandom 把 seed 放进 Thread 对象的字段，各线程用各自 probe 推进，完全无竞争，取值 O(1) 且质量足够。用法上必须 `ThreadLocalRandom.current().nextInt(...)`，不要 new 它（构造器私有）。要跨线程可复现或加密级安全时：可复现用显式种子 new Random(seed)（单线程内），安全场景用 SecureRandom（性能低但密码学安全）。


### JUC-001-017 | ★★★★☆

什么是乐观锁和悲观锁？在 Java 和数据库里分别怎么体现？

**答案：**
悲观锁假设冲突频繁，访问前先加锁：Java 的 synchronized/ReentrantLock，数据库的 SELECT ... FOR UPDATE（行锁）。乐观锁假设冲突少，不加锁，提交时校验有没有人动过：Java 的 CAS/原子类，数据库的版本号（update ... set version=version+1 where id=? and version=?）或条件更新。选型看冲突率与代价：写多冲突高、临界区复杂用悲观；读多写少、单条状态更新用乐观，冲突时重试或报冲突。

**解析：**
乐观锁在应用层的完整闭环：读取数据与版本 → 业务计算 → 条件更新 → 影响行数为 0 表示被并发修改 → 按策略重试（有限次+退避）或返回冲突错误。注意重试要重读最新数据重算，不是盲重放。

分布式场景的对应物：Redis 的 WATCH/MULTI 事务是乐观锁；setnx/redisson 看门狗是悲观式分布式锁；数据库 FOR UPDATE 是最简单可靠的悲观互斥（注意走索引，否则锁全表扫描行）。

与隔离级别的关系：乐观锁本质是应用层机制，与 RR/RC 无关；悲观 FOR UPDATE 在不同隔离级别下加锁范围不同（间隙锁），要结合具体行为讨论。


### JUC-001-018 | ★★★☆☆

JDK 21 虚拟线程是什么？它会取代线程池吗？

**答案：**
虚拟线程是 JDK 21 正式的轻量线程：由 JVM 调度到少量载体线程（carrier）上运行，创建成本 KB 级、阻塞代价极低（阻塞时把栈挂起让出载体线程），因此可以用"每请求一线程"的同步阻塞写法支撑百万级并发连接，特别适合 IO 密集场景。它不会全面取代线程池：CPU 密集任务没有收益；需要控制并发上限的场景仍然要用 Semaphore/连接池限流——虚拟线程解决的是"线程贵"，不是"资源无限"。使用上一般用 Executors.newVirtualThreadPerTaskExecutor()，每个任务一个新虚拟线程，不再复用。

**解析：**
工作机制：虚拟线程栈存在堆上，运行时挂载到 ForkJoinPool 管理的载体线程；遇到阻塞 IO（NIO 通道）时自动 unmount，让出载体；synchronized 块内阻塞会 pin 住载体线程（JDK 24 已修复为可释放），早期版本建议热点路径换 ReentrantLock。

生态注意点：ThreadLocal 在海量虚拟线程下可能成为内存放大器（每线程一份）；池化虚拟线程是反模式（本来就是临时对象语义）；监控线程池的旧指标需要换视角（看队列与信号量，而不是活跃线程数）。

适用判断：下游调用是阻塞 JDBC/HTTP 客户端、并发连接数大、调用时长以 IO 为主——收益显著；纯计算任务、需要精细优先级调度——无收益。


### JUC-001-019 | ★★★★☆

为什么双重检查锁（DCL）在旧 JVM 时代有争议，现在怎么写才对

**答案：**
争议根源是"无 volatile 的 DCL"在旧内存模型下可能读到"已分配未初始化"的对象（构造器写与引用发布重排）。JDK 5 明确 JSR-133 后，实例字段加 volatile 即可安全：第一次判空避免不必要加锁，锁内第二次判空防并发重复创建，volatile 禁止重排保证其他线程看到引用时对象已初始化完成。替代方案静态内部类（类加载机制保证）与枚举更简洁；持有实例的"不可变对象+volatile 引用发布"是同一原理的推广。

**解析：**
半初始化对象问题的 happens-before 推导：volatile 写之前的构造器写，对后续 volatile 读线程可见。延伸追问：为什么 final 字段也能提供构造安全发布；为什么"out-of-order 写"在 ARM 等弱内存模型上更容易复现。


### JUC-001-020 | ★★★★☆

线程池的 shutdown 与 shutdownNow 的区别与优雅停机实践

**答案：**
shutdown：拒绝新任务，已提交（含队列中）任务继续执行完；shutdownNow：尝试中断正在执行的任务、清空队列并返回未执行任务列表，"尽量停"。两者都不等完成，需 awaitTermination(timeout) 阻塞等待。优雅停机组合拳：先 shutdown → awaitTermination 超时 → shutdownNow 兜底 → 再 await；任务内部要响应中断（可中断阻塞+清理逻辑），Spring 的 @PreDestroy/SmartLifecycle 就是这套。

**解析：**
中断语义：interrupt 只是标志，shutdownNow 后任务是否真停取决于代码对 InterruptedException 的处理（K-JUC-001）。K8s preStop+SIGTERM 的链路最终落到这里（K-TOOL-010）。追问：为什么"吞中断"会导致优雅停机卡死成强杀。

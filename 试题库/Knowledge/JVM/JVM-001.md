### JVM-001-001 | ★★★★★

JVM 运行时数据区有哪些？哪些线程共享、哪些线程私有？

**答案：**
线程私有：程序计数器（记录当前字节码执行位置，唯一不会 OOM 的区域）、虚拟机栈（每个方法一个栈帧：局部变量表、操作数栈、动态链接、返回地址，递归过深抛 StackOverflowError）、本地方法栈（native 方法）。线程共享：堆（对象实例，GC 主战场，物理上可分区）、方法区（JDK 8 起由元空间实现，存类元信息、运行时常量池，使用本地内存）。直接内存（NIO DirectByteBuffer）不属于运行时数据区但受 -XX:MaxDirectMemorySize 约束，也有 OOM 风险。

**解析：**
堆内划分随 GC 而定：分代收集器（Serial/Parallel/CMS/G1 的逻辑分代）下有新生代（Eden+两个 Survivor）与老年代；ZGC/Shenandoah 是分代之前的设计（ZGC 在 JDK 21 补上分代）。"堆=新生代+老年代"要说明是逻辑视图。

方法区是规范，永久代（JDK 7 及以前，在堆内）是实现；JDK 8 移除永久代改元空间（本地内存），原因：字符串常量池早已移到堆（JDK 7），永久代大小难调、易 OOM，与堆 GC 耦合。

栈帧结构中动态链接指向运行时常量池的方法引用，支撑多态分派。


### JVM-001-002 | ★★★☆☆

对象在堆上如何分配？什么是 TLAB？

**答案：**
绝大多数对象优先在新生代 Eden 区分配，流程：先尝试在 TLAB（线程本地分配缓冲）内指针加一式快速分配——每线程从 Eden 划一块私有缓冲，分配无需同步，这是"几乎免费的对象分配"的关键；TLAB 满了就申请新 TLAB 或退回 CAS 抢 Eden 公共空间。大对象（超过 -XX:PretenureSizeThreshold 或 G1 的 region 一半）直接进老年代，避免频繁复制。栈上分配在 HotSpot 以标量替换形式存在：逃逸分析确认对象不逃逸时，拆散成基本量直接在栈帧里用掉。

**解析：**
TLAB 消除的竞争：Eden 是多线程共享的，若无 TLAB，每次分配都要原子更新分配指针；TLAB 把"批量申请"与"单次分配"分离，单次分配只是指针移动 + 初始化为零，接近 malloc 最优路径。

分配后动作：设置对象头（Mark Word、类型指针）、执行构造。JIT 逃逸分析的三个优化：栈上分配（标量替换）、锁消除（同步块对象不逃逸）、锁粗化。_hotspot 默认开启逃逸分析，但复杂调用链上失效很常见，不要夸大其效果。


### JVM-001-003 | ★★★★☆

如何判断对象可以被回收？四种引用的区别？

**答案：**
主流是可达性分析：从 GC Roots（虚拟机栈局部变量、静态字段、常量、JNI 引用、活跃线程等）出发，不可达的对象判定可回收；引用计数法有循环引用问题，JVM 不用（部分运行时如 Python/COM 在用）。四种引用强度：强引用（不回收）、软引用（内存不足才回收，适合缓存）、弱引用（下次 GC 必回收，如 WeakHashMap、ThreadLocalMap 的 key）、虚引用（唯一作用是回收时的通知，配合 ReferenceQueue 管理堆外资源）。

**解析：**
可达性分析的工程含义：静态集合、线程、类加载器是泄漏三大源头——静态 Map 无限增长、线程池任务持有外部大对象、容器类加载器持有旧应用类。判断"该不该被回收"与"为什么没被回收"是排查内存泄漏的核心问题。

finalize 兜底回收（对象可在 finalize 中自救一次）机制已废弃；Cleaner/PhantomReference 是替代。

软引用缓存注意：只有内存不足才清，软引用对象本身还有 ReferenceQueue 可注册；WeakHashMap 的 key 弱引用在 key 被回收后整个 entry 移除。


### JVM-001-004 | ★★★★☆

常见的垃圾回收算法有哪些？分代收集的理论依据是什么？

**答案：**
三种基础算法：标记-清除（简单但产生碎片、标记停顿）、标记-复制（存活少时高效、无碎片，代价是空间折半，适合新生代）、标记-整理（移动存活对象消除碎片，适合老年代）。分代假说是分代收集的理论依据：绝大多数对象朝生夕死、且"熬过越多次 GC 的对象越可能长期存活"，所以新生代用复制算法高频回收，老年代用标记-整理低频回收。要能补一句：这些是思想，具体收集器是它们的组合与并发化实现。

**解析：**
复制算法细节：Eden 与两个 Survivor 配合，每次 GC 把 Eden+from 存活对象复制到 to，年龄+1，达到阈值（默认 15，动态对象年龄判定可提前）晋升老年代。代价：空间利用率 90%（Eden:S0:S1=8:1:1 时）。

标记阶段为何是主要停顿来源：标记需要从 roots 遍历对象图，且并发标记时应用还在改引用，需要写屏障（记录引用变化）做增量修正（三色标记法的"漏标"问题：黑指向白且灰到白路径被切断，用增量更新或 SATB 修正）。CMS 用增量更新，G1 用 SATB——这是收集器对比的高频深挖点。


### JVM-001-005 | ★★★★☆

CMS 和 G1 的区别？为什么 CMS 被废弃？ZGC 解决了什么？

**答案：**
CMS：老年代并发收集器，标记-清除，目标是低停顿，步骤为初始标记(STW)→并发标记→重新标记(STW)→并发清除；缺点是碎片、并发失败退化成串行 Full GC、无法处理浮动垃圾，JDK 9 弃用、14 移除。G1：面向服务端的分代+Region 化收集器，把堆划分为等大 region，按回收收益优先收集垃圾最多的 region（Garbage First 名字来源），停顿目标由 -XX:MaxGCPauseMillis 设定（默认 200ms），整体标记-复制+整理，无碎片。ZGC：着色指针+读屏障实现的全并发标记与整理，停顿亚毫秒级且与堆大小基本无关（TB 级堆），JDK 21 支持分代 ZGC 后吞吐损失显著下降，适合超大堆低延迟场景。

**解析：**
G1 要点：region 大小 1~32MB（2 的幂），Eden/Survivor/Old/Humongous 是逻辑角色；RSet（记忆集）记录跨 region 引用，使"只回收部分 region"成立，代价是写屏障维护 RSet 的内存与 CPU 开销（一般 5%~10%）；Mixed GC 阶段混合回收新生代+部分老年代 region；Evacuation（复制）仍是 STW 但一次只搬被选中的 region。

CMS 退化条件：并发阶段用户线程分配速度超过清理速度 → Concurrent Mode Failure → Serial Old 全停顿整理。碎片问题导致大对象分配失败提前触发。

选型口诀：JDK 8 老系统仍 CMS/Parallel；JDK 11+ 默认 G1；超大堆（几十 GB 以上）+ 极低延迟 SLA 用 ZGC（21+ 建议分代 ZGC）。


### JVM-001-006 | ★★★★★

Minor GC、Full GC 的触发条件和排查思路？

**答案：**
Minor GC：Eden 满时触发，只收集新生代，高频且通常短暂。Full GC（广义的"整堆收集"，G1 下对应 Full GC 或老年代比例触发的 Mixed GC）：①老年代空间不足（晋升过快/大对象直入/内存泄漏）；②元空间不足；③System.gc() 显式调用（可用 -XX:+DisableExplicitGC 屏蔽）；④CMS 并发失败、G1 预测失败（to-space exhausted）退化；⑤堆外内存/NIO 触发的担保。排查路径：先看 GC 日志与监控定位类型和频率 → jmap/mat 分析堆里什么在涨 → jstat 看晋升速度 → 结合代码找引用持有方。频繁 Full GC 的三大常见原因：内存泄漏、堆太小/Young 比例不合理、元空间或显式 GC。

**解析：**
GC 日志关键字（G1）：`Pause Young (Normal)`、`Pause Full`、`to-space exhausted`、`Humongous regions`。分析工具：gceasy/gcviewer 看频率、停顿、回收效果。

晋升过速的典型模式：Survivor 太小导致对象未熬过年龄就晋升（动态年龄判定：Survivor 中同龄对象总和超其一半直接晋升）；每次 Minor GC 晋升量大 → 老年代周期性满 → Full GC 循环。

泄漏 vs 堆小：堆 dump 中老年代占用持续增长且回收不掉是泄漏；回收得掉但分配速率高是容量/代码问题（过度缓存、大对象、批处理不流式）。


### JVM-001-007 | ★★★★☆

类加载过程和双亲委派机制？

**答案：**
类加载五步：加载（读字节码生成 Class 对象）→ 验证（格式/语义/字节码安全）→ 准备（静态变量分配零值）→ 解析（常量符号引用转直接引用，可延迟）→ 初始化（执行静态变量赋值与 static 块，即 <clinit>）。双亲委派：收到加载请求先委派给父加载器（Bootstrap → Ext/Platform → Application），父加载器无法完成才自己加载，保证核心类（如 java.lang.String）由 Bootstrap 加载、全 JVM 唯一且安全。打破场景：SPI（线程上下文类加载器让父加载器"借用"子加载器）、OSGi/容器隔离（每应用独立 loader）、热部署、以及重写 loadClass 的自定义逻辑。

**解析：**
初始化触发时机（主动引用六种）：new、读写静态字段（非 final 常量）、调用静态方法、反射、子类初始化连带父类、主类。被动引用（数组定义、引用常量、父类通过子类名访问静态字段等）不触发初始化——常考细节。

Thread Context ClassLoader 存在的原因：JDBC 的 DriverManager 在 Bootstrap 加载，但驱动实现类在应用 classpath，父加载器看不到子加载器的类；通过 TCCL（默认=应用类加载器）反转委派方向完成加载。

自定义类加载器：通常重写 findClass（保持双亲委派），重写 loadClass 才是打破。相同类名+不同加载器 = 不同类，这是容器隔离与 ClassCastException("same class") 神秘报错的根源。


### JVM-001-008 | ★★★★★

线上 OOM 怎么排查？说说你的思路和工具。

**答案：**
第一步分类：看报错是 Java heap space、Metaspace、unable to create new native thread、direct memory 还是 GC overhead limit——不同类型查不同方向。堆 OOM：看 -XX:+HeapDumpOnOutOfMemoryError 留下的 dump（没留则低峰 jmap 抓），用 MAT/JProfiler 看支配树与 Leak Suspects，找最大对象及其 GC Root 引用链，对照业务判断泄漏（该死没死）还是容量不足（都该活但太多）。元空间：动态生成类（CGLIB/反射/Groovy）泄漏。线程 OOM：ulimit、线程数监控、检查无限创建线程的代码。直接内存：NIO/Netty 相关，看 MaxDirectMemorySize 与 buffer 统计。应急手段：重启换血、扩内存、限流降级。

**解析：**
标准排查流程细化：①监控确认 OOM 时间点与流量相关性（流量放大=容量问题；平稳增长=泄漏）；②dump 分析四步：直方图（什么多）→ 支配树（谁占大头）→ 引用链（谁拴着它）→ 代码定位（谁创建）；③修复后验证：压测复现、观察老年代回收曲线恢复锯齿形。

泄漏高频源头清单：静态集合缓存无上限、ThreadLocal 未 remove（线程池）、资源未关闭（连接/流）、监听器未注销、缓存键设计缺陷、类加载器泄漏（热部署）。

工具链：jps/jstat（GC 统计）、jmap（histo/dump）、jstack（线程）、arthas（heapdump、dashboard、vmtool）、MAT、async-profiler（火焰图，含内存采样模式）。


### JVM-001-009 | ★★★★☆

线上 CPU 飙高怎么排查？

**答案：**
经典五步：①top 找到占用高的 Java 进程；②top -Hp <pid> 找到进程内高 CPU 线程的 TID；③printf '%x' 转十六进制；④jstack <pid> 抓栈，按 nid=0x<tid> 定位线程正在执行的代码栈；⑤判断类型——业务死循环/正则回溯/GC 线程忙（GC 线程高说明内存问题）/JIT 编译线程（短暂正常）。进阶用 async-profiler 火焰图看聚合热点，比单次 jstack 抽样更准。如果是周期性飙高，固定时间多抓几份对比。

**解析：**
常见根因清单：正则灾难性回溯（嵌套量词）、大集合全量计算在请求线程、无限循环（等待条件写错）、序列化超大对象、频繁 Full GC（GC 线程吃 CPU）、自旋 CAS 竞争、容器 CPU limit 与线程数不匹配（切换开销）。

容器注意：top -Hp 在容器内看到的 CPU 可能受 cgroup 限制，可宿主机视角确认；JVM 参数 UseContainerSupport 让核数感知正确。

GC 线程高的识别：线程名 GC task thread / G1 xxx；此时按内存问题路径（K-JVM-006/008）排查。


### JVM-001-010 | ★★★☆☆

对象什么情况下会进入老年代？

**答案：**
五条路径：①年龄达到阈值（默认 15，MaxTenuringThreshold，G1/Parallel 支持，CMS 下受位宽限制）；②动态年龄判定——Survivor 中同龄及以下对象总大小超过 Survivor 空间一半，该年龄及以上直接晋升；③大对象直接分配老年代（PretenureSizeThreshold / G1 humongous）；④Minor GC 后 Survivor 放不下的存活对象经分配担保直接进老年代；⑤某些特殊场景（如大数组、长期持有对象随业务自然存活）。

**解析：**
年龄阈值 15 的由来：对象头 Mark Word 中分代年龄字段 4 bit，最大 15。

动态年龄判定的工程意义：Survivor 空间偏小或突发流量时，大量"本应年轻"的对象提前晋升，老年代压力陡增——这是"调大 Survivor/年轻代比例"与"控制突发分配速率"的依据。

分配担保：Minor GC 前老年代要能容纳新生代所有对象（保守）或历次晋升平均（HT 优化），担保失败触发 Full GC（策略依收集器版本而异）。


### JVM-001-011 | ★★★☆☆

常用的 JVM 调优参数有哪些？你怎么判断要不要调？

**答案：**
先说原则：能不改就不改，先解决代码里的分配问题，调参是最后一步。常用参数四组：①堆：-Xms/-Xmx（设成一样避免动态扩容抖动）、-Xmn 或 NewRatio、-XX:MetaspaceSize/MaxMetaspaceSize；②收集器：-XX:+UseG1GC（8 手动指定）、-XX:MaxGCPauseMillis、-XX:+UseZGC（15+/17）；③诊断：-XX:+HeapDumpOnOutOfMemoryError/-XX:HeapDumpPath、-Xlog:gc*（8 是 -XX:+PrintGCDetails）、-XX:+DisableExplicitGC；④容器：-XX:MaxRAMPercentage 代替写死 -Xmx。判断要不要调：看 GC 监控——频率（Minor 过频=Eden 小/分配率高，Full=老年代/元空间）、单次停顿（超过 SLA 才动收集器）、晋升速率。

**解析：**
决策树式回答更稳：延迟问题 → 看停顿分布，换/调低停顿收集器 + 排查大对象与并发标记启动时机；吞吐问题 → 分配速率、Eden 大小、批处理放大；容量问题 → 先定位泄漏/热点数据结构，扩堆是最后手段。

容器化要点：JVM 10+ 默认感知 cgroup；设 `MaxRAMPercentage=75` 级别给元空间/直接内存/线程栈留余量，避免 OOMKilled。

参数记忆优先级：面试能准确说出 8~10 个常用参数及其默认值方向即可，切忌报一堆过时参数（PermSize、CMS 默认）。


### JVM-001-012 | ★★★☆☆

对象在内存中的布局是怎样的？

**答案：**
三段式：对象头（Mark Word 8 字节：哈希、GC 年龄、锁状态；类型指针 Klass Pointer 8/4 字节，压缩指针开启为 4；数组对象多 4 字节长度）、实例数据（字段按类型宽度排布，同宽度聚集，压缩后引用 4 字节）、对齐填充（整体补齐到 8 字节倍数）。引出结论：一个"空对象"16 字节（头 12+填充 4，开启压缩指针），这也是"包装类比基本类型贵一个数量级"的内存依据。

**解析：**
字段重排（-fieldarchive 优化）：HotSpot 按字段宽度从大到小排列（long/double → int → short/char → byte/boolean → 引用），减少填充浪费；父类字段在前。压缩指针（UseCompressedOops，堆 <32G 默认开）：引用与类型指针压到 4 字节，以"8 字节偏移量"寻址——堆超 32G 自动失效，这也是"32G 附近堆容量魔数"的由来。

布尔数组每元素仍占 1 字节+JVM 无位打包，校验"为什么用 bitset"这类问题。


### JVM-001-013 | ★★☆☆☆

JIT 即时编译是什么？解释执行和编译执行的关系？

**答案：**
Java 源码编译成字节码，运行期由解释器逐条执行；JVM 统计"热点代码"（调用/回边次数达阈值的方与循环，On-Stack-Replacement 支持循环内触发），C1/C2 编译器把热点编译成本地机器码缓存复用，即分层编译（1~5 级）。C1 快速出码、优化少，C2 慢工出细活。基于计数器的优化有"去优化"能力：假设失效（类加载打破单态假设）会回退解释执行。由此带来的实践现象：服务刚启动接口慢（预热）、基准测试要预热忽略 JIT 阶段。


### JVM-001-014 | ★★★☆☆

metaspace 里的运行时常量池和字符串常量池是一回事吗？

**答案：**
不是一回事。class 文件常量池是编译期产物（字面量与符号引用）；加载后进入运行时常量池，位于元空间（JDK 8+，属方法区实现）；字符串常量池是堆里的一个全局 HashTable（JDK 7 从永久代移到堆），专门存放 String 实例引用供字面量共享。三者关系：源码字面量 → class 常量池 → 运行时常量池；字符串字面量额外登记进字符串池，intern() 手动登记堆中字符串。

**解析：**
为什么字符串池在堆里：字符串是高频 GC 对象，放永久代（旧版）会因 Full GC 才回收导致膨胀 OOM；JDK 7 移堆后随 Minor/Full GC 正常回收。intern 的版本行为差异：JDK 6 intern 复制到永久代，7+ 只登记首次出现的引用——`String s = new String("a"); s.intern() == s` 的经典结果 6 为 false、7 为 true（字面量 "a" 已先入池时仍 false），体现版本差异。

运行时常量池的动态性：可运行期新增常量——如 Integer.valueOf(-128~127) 缓存、String.intern、动态生成的符号引用（invokedynamic 的引导方法结果）。


### JVM-001-015 | ★★★★☆

JIT 逃逸分析与锁消除：为什么局部 StringBuffer 在高版本不再需要

**答案：**
逃逸分析判断对象是否逃出方法/线程；未逃逸的对象可标量替换（拆成局部变量，不分配在堆）、锁消除（sync 块对象局部可见时直接去掉锁）。经典案例：方法内局部 StringBuffer/JDK 8 的 `synchronized` 局部对象，JIT 检测不逃逸后锁被消除——所以"局部 StringBuilder 还是 StringBuffer"在新 JIT 下性能差距会消失，但编码规范仍推荐 Builder（语义清晰、不依赖优化）。-XX:+DoEscapeAnalysis 默认开启。

**解析：**
三个优化：逃逸分析是前提，标量替换/锁消除/栈分配（HotSpot 实际以标量替换实现，无真栈分配）是产出。这也解释了"过度优化碎对象"多数场景无益（TLAB 分配+逃逸分析已经很快）。局限：分析保守，对象传入未知方法即判逃逸；跨方法内联后才可能不逃逸——内联是其它优化的地基。


### JVM-001-016 | ★★★☆☆

类加载时机

下列不会触发类初始化（<clinit>）的是：

A. new 该类实例
B. 访问该类的 static final int X = 10 常量
C. 调用该类静态方法
D. 反射 Class.forName 加载该类（含初始化）

**答案：** B

**解析：**
编译期常量（static final 基本类型/字符串字面量）在编译期被内联进调用方常量池，访问不触发类初始化；A/C/D 都是主动引用，触发 <clinit>。

常量传播消除加载；被动引用不初始化。


### JVM-001-017 | ★★★★☆

CMS 与 G1 辨析

与 CMS 相比，G1 的特点包括：

A. Region 化堆布局，可预测停顿目标
B. 整体上标记-整理，基本不产生碎片
C. 默认 JDK 9+ 的收集器
D. 完全不发生 Stop-The-World

**答案：** A、B、C

**解析：**
A 对，G1 按回收集选择性回收；B 对，复制式整理无碎片（CMS 是标记-清除有碎片）；C 对，JDK 9 起默认；D 错，G1 的 Young GC 与转移阶段仍 STW，只是短而可控。

G1=Region+可预测停顿+整理；CMS 已在 JDK 14 移除。


### JVM-001-018 | ★★☆☆☆

finalize 地位

关于对象回收，正确的是：

A. 对象不可达后立即执行 finalize 并释放
B. finalize 执行时机不确定且已废弃，资源释放应使用 try-with-resources 或 Cleaner
C. 重写 finalize 可以保证对象复活
D. finalize 由开发者手动调用

**答案：** B

**解析：**
A 错，可达性分析后至多执行一次 finalize 且由后台线程异步执行，时机不定；B 对，JDK 9 起 Deprecated；C 错，finalize 中赋值引用可"自救一次"，但不可靠；D 错，由 GC 调用。

finalize 不可靠三宗罪：时机不定、可复活、性能差。


### JVM-001-019 | ★★★☆☆

双亲委派打破者

JDBC 利用什么机制解决"驱动实现类在应用 classpath、而 DriverManager 在启动类加载器"的可见性问题？

A. 自定义 ClassLoader 重写 loadClass
B. 线程上下文类加载器（TCCL）
C. OSGi 模块化
D. 字节码织入

**答案：** B

**解析：**
父加载器（DriverManager）需要"反向"加载子加载器的实现类，双亲委派不支持，故通过线程上下文类加载器（默认应用类加载器）反转方向；A/C/D 是其他打破场景。

双亲委派的三种典型打破：SPI/TCCL、容器隔离、热部署。


### JVM-001-020 | ★★☆☆☆

JVM 分代年龄

对象头中分代年龄字段为 4 bit，故常规收集器下年龄最大为：

A. 7
B. 15

D. 63

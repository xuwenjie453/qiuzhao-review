### Git-001-001 | ★★★★☆

git merge 和 git rebase 的区别？团队怎么选？

**答案：**
merge 把两条分支历史合并产生合并提交，历史真实保留分叉脉络；rebase 把当前分支的提交"摘下来"重放到目标分支顶端，历史线性整洁但**改写了提交**（hash 变化）。团队约定（黄金法则）：rebase 只用于"自己的、未推送共享"的本地分支整理（feature 分支同步主干 rebase 后强推自己的分支）；已共享分支禁止 rebase，用 merge。工作流选择：Git Flow（重发布模型，适合版本化产品）、GitHub Flow（主干+PR，持续部署）、Trunk-Based（短命分支高频合入，配 feature flag）。回答时主动给出团队规范视角而不是背命令。


### Git-001-002 | ★★★☆☆

git reset、git revert、git checkout（restore）的区别？

**答案：**
三个"回滚"作用对象不同：reset 移动当前分支指针到指定提交，可带 --soft（保留改动在暂存区）/--mixed（默认，回到工作区）/--hard（丢弃）；revert 生成一个"反向提交"抵消指定提交，历史不被改写，适用于已共享分支；checkout/restore 切换分支或恢复工作区文件（新版语义拆分 restore 恢复文件、switch 切分支），不动历史。选择规则：未推送的本地整理用 reset；已推送的公共回滚用 revert；只想丢弃某文件改动用 restore。保命技巧：任何 reset --hard 前先 `git branch backup` 或记下 hash，reflog 兜底。


### Git-001-003 | ★★★☆☆

分支操作

误把一次提交提交到了 feature 分支，想把它挪到 master，正确操作序列是：

A. `git checkout master && git cherry-pick <commit>`
B. `git merge feature`
C. `git reset --hard`
D. 删库重建

**答案：** A

**解析：**
cherry-pick 把指定提交复制到当前分支；B 会带全部分支历史；C 丢弃改动风险大；D 荒谬。

cherry-pick 摘单个提交；场景：hotfix 同步、误提交挪移。


### Git-001-004 | ★★★★☆

回退已推送提交

已推送到共享分支的提交需要撤销，安全做法是：

A. `git reset --hard HEAD~1 && git push -f`
B. `git revert <commit>` 生成反向提交并正常推送
C. 直接改远端历史
D. 删除分支

**答案：** B

**解析：**
revert 不改历史，对共享分支安全；A 强推会摧毁他人工作；C/D 危险。

reset 改历史（本地未推送用），revert 反做提交（共享分支用）。

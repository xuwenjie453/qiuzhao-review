### Agent-001-001 | ★★★★★

什么是 AI Agent？它和大模型调用有什么本质区别？

**答案：**
区别在于"谁主导过程"。单纯 LLM 调用（一次问答）里，人给定输入、模型给输出，流程终止；Agent 是"LLM 作为决策核心 + 工具（Tools）+ 记忆（Memory）+ 循环（Loop）"构成的系统：模型根据目标自主决定下一步做什么（调用哪个工具、参数是什么）、观察执行结果、迭代推进直到目标完成——主导权从人转移到模型。判定一个系统是不是 Agent 的试金石：给它一个目标，它能不能**自己规划步骤并调用工具达成**，中途无需人工逐步指挥。构成要素拆解（面试标准结构）：LLM（推理决策）、Tools（行动能力：查库、调 API、执行代码）、Memory（上下文与长期记忆）、Planning（任务拆解）、以及工程化的循环调度与终止条件。


### Agent-001-002 | ★★★★★

Agent 和 Workflow 的区别？什么场景该选哪个？

**答案：**
本质区别是**流程控制权**：Workflow 的流程由开发者预定义（节点、分支、顺序固定），LLM 只在节点内完成"理解/生成/分类"等任务，执行路径确定；Agent 由 LLM 动态决定下一步，路径不确定。选型判据三问：①任务路径是否可枚举？可枚举（客服退款的固定步骤）用 Workflow——可控、可测、成本低；②环境变化是否需要即兴决策？需要（开放式研究、复杂诊断）用 Agent；③错误容忍度？低容错场景用 Workflow+人工卡点，或 Agent 外包一层强校验。工程事实：多数生产系统是**两者混合**——主流程 Workflow 保证确定性，个别开放步骤内嵌 Agent 自主性（"流程里的智能节点"）。Workflow 工具链：Dify/LangGraph（图编排）；纯 Agent 循环：手写或框架。


### Agent-001-003 | ★★★★★

ReAct 模式是什么？怎么实现的？

**答案：**
ReAct = Reasoning + Acting，Agent 最经典的运行模式：LLM 按固定节奏输出"思考（Thought：当前该做什么、为什么）→ 行动（Action：调用某工具及参数）→ 观察（Observation：工具返回结果）"，循环往复直到模型输出"最终答案（Final Answer）"。实现层面是一个工程循环：①系统提示注入目标+可用工具清单（名称/描述/参数 Schema）；②调用 LLM 生成下一步（现代实现多用原生 function calling 结构化输出，而不是解析文本）；③执行工具返回结果；④把结果追加进对话历史再次调用 LLM；⑤循环直到终止条件（模型给出最终答案 / 达到最大轮数 / 预算耗尽）。理解要点：ReAct 的"推理"就发生在Thought 里——推理外化为 token（与 CoT 同源，K-PROMPT-003）；工具描述质量直接决定 Agent 选择工具的准确率。


### Agent-001-004 | ★★★★☆

Agent 的记忆机制怎么设计？

**答案：**
按生命周期与用途分层：①短期/工作记忆——即对话上下文窗口，受长度限制；治理手段：滚动裁剪、历史摘要压缩（把早期轮次总结成要点）、结构化状态对象（把关键事实抽成 JSON 状态而非全量对话，token 效率高且稳定）；②长期记忆——跨会话持久化，两类实现：向量库语义记忆（历史对话/事实切片，检索注入，K-RAG-004）与结构化事实库（用户画像、偏好，显式字段更新）；③外部记忆/工具化——把记忆存成可检索资源（知识库、数据库），Agent 按需查询而不是全量塞上下文。设计原则：记忆写入要有选择（不是什么都要记：重要事实、用户修正、任务结论），要有更新与遗忘（冲突时以新覆旧、过期衰减），检索回的记忆要标注来源与时间（防旧信息误导）。


### Agent-001-005 | ★★★☆☆

多 Agent 系统有哪些协作模式？什么时候需要多 Agent？

**答案：**
先立判断标准：多 Agent 不是越多越好——单 Agent+多工具能解决的不要拆多 Agent（通信成本、上下文割裂、失败面变大）。需要多 Agent 的信号：①职责需要不同配置（不同模型/不同提示/不同工具集，如"审稿 Agent"与"写作 Agent"）；②需要对抗/校验结构（生成者-批评者，提升质量）；③上下文隔离需求（每个 Agent 专注自己的信息子集，防污染）。常见协作模式：主管-执行者（Orchestrator-Workers：主 Agent 拆任务分发、汇总结果，最常用最可控）；流水线（Pipeline：顺序加工，本质是 Workflow）；辩论/评审（多角色对同一产物互评取优）；群聊式（自由协作，实验性强，生产慎用）。通信载体：消息传递（结构化任务描述与产物），共享工作区（共同读写文档/黑板）。


### Agent-001-006 | ★★★☆☆

Agent 的任务规划（Planning）怎么做？

**答案：**
规划谱系按"计划时机"分三档：①完全动态（ReAct 式）：走一步看一步，灵活但易绕路；②先规划后执行（Plan-and-Execute）：开局先产出完整步骤清单，逐步执行，执行中发现偏差可重规划（ReWOO 思想：规划与执行解耦省 token）；③分层规划：先粗计划（阶段）再逐阶段细规划。工程增强：计划显式化——把计划渲染为带状态的任务清单（TODO/进行/完成），用户可见可干预，执行器按清单推进；反思机制嵌入——每阶段结束让模型自评（目标达成？遗漏？）触发重规划（Reflexion 思想）；不确定性处理——把"需要澄清"做成一等公民动作（向用户提问），而不是带猜硬做。评估规划质量看三点：步骤完备性、粒度合理性（可执行可验证）、动态调整能力。


### Agent-001-007 | ★★★★☆

生产环境的 Agent 怎么保证可靠性（护栏、降级、可观测）？

**答案：**
把 Agent 当"会写代码的新员工"管理——权限最小化+过程可观测+结果要验收。护栏清单：①预算与终止：最大轮数、最大 token/费用、最大墙钟时间，任一触顶强制收尾（产出"未完成+已获得信息"而不是挂死）；②动作白名单与审批：高危工具（删除、转账、对外发送）二次确认或仅预演（dry-run），生产环境工具权限按角色收敛（K-MCP-006）；③输出校验：结构化校验+业务规则校验（金额范围、SQL 只读检查、目标路径白名单），不合法即拒绝执行并反馈修正；④循环防护：重复动作检测、反思触发重规划（K-AGENT-006）；⑤降级路径：模型超时/失败时回退到规则流程或人工；⑥可观测：每步的 thought/action/observation 落库（trace 串联 K-MS-006），成本与轮数指标化，bad case 可回放。测试方法：用固定任务集做回归（成功率/平均轮数/成本），上线前沙箱环境全量预演。


### Agent-001-008 | ★★★☆☆

自研 Agent 框架还是用 LangChain/LangGraph？怎么选？

**答案：**
先看事实：Agent 的核心循环（LLM 调用+工具执行+历史管理）代码量并不大，"手搓"完全可行且可控性最高——很多团队的核心 Agent 是自研薄层 + 复用组件库。框架的价值在生态与工程配套：LangChain（组件全家桶：模型接入/工具/文档加载）、LangGraph（图编排：节点/边/状态机/检查点，支持 Workflow 与 Agent 混合、持久化与 human-in-the-loop）、LlamaIndex（RAG 数据框架强项）、Dify 类平台（低代码快速搭，深度定制受限）。选型建议：①原型验证/内部工具 → 平台（Dify 类）最快；②需要精细流程控制、持久化、人工介入 → LangGraph；③团队强工程能力、性能与可控性敏感 → 自研循环+按需引库（避免全家桶绑定）。判断框架是否值得用的标准：它是否在你需要的扩展点（自定义工具协议、上下文管理、重试策略）上"让路"，还是处处接管。


### Agent-001-009 | ★★★★☆

Agent 的"验收"怎么做：从自动校验到验收 Agent

**答案：**
分层验收：①规则层——结构化校验（Schema、字段类型）、业务规则校验（金额范围、日期合法、SQL 只读）；②对照层——产物与任务要求逐条比对（要求清单 checklist 化，逐项判定满足/不满足）；③模型层——独立"验收 Agent"按评分 rubric 给分并说明扣分点（LLM-as-judge 的项目化）；④人工层——低于阈值自动转人工，带完整执行轨迹。核心思想：不能验收的自主性不可上生产；验收标准本身要版本化、进回归。

**解析：**
验收 Agent 的防串通：与执行 Agent 用不同模型/不同提示、只给产物与要求不给执行过程（防"过程合理化"）。量化：验收通过率、自动修订成功率、转人工率三个指标构成 Agent 质量大盘。


### Agent-001-010 | ★★★★☆

Agent 终止条件

生产环境 Agent 必须具备的护栏包括：

A. 最大轮数/预算/时长上限
B. 高危工具人工确认或 dry-run
C. 输出结构化与业务规则校验
D. 完全信任模型的自主决策

**答案：** A、B、C

**解析：**
三件套防"无限循环烧钱"与危险动作；D 是反模式（失控事故根源）。

Agent=能力+护栏；模型不是权限主体。

### Agent-002-001 | ★★★★☆

什么是LLM Agent？

**答案：**
LLM Agent是以LLM为'大脑'的智能体系统：LLM负责感知理解与推理决策，通过调用工具、访问记忆、执行动作与环境交互，按'观察→思考→行动'的循环自主完成目标，而不只是单轮文本生成。


### Agent-002-002 | ★★★★☆

LLM Agent有什么关键能力？

**答案：**
关键能力包括：①规划：任务分解、子目标设定、自我反思修正；②记忆：短期上下文记忆与长期外部记忆（向量库等）；③工具使用：调用搜索、代码执行、API等扩展能力；④行动执行：与环境真实交互并利用反馈迭代；底层是强推理与指令遵循能力。


### Agent-002-003 | ★★★★☆

怎样构建基于LLM的Agents？

**答案：**
构建要素：①LLM作为推理内核；②规划模块（CoT/ReAct/Plan-and-Execute做任务分解）；③记忆模块（上下文+向量库长期存储）；④工具集与调用协议（function calling/MCP）；⑤执行循环：观察结果回喂模型迭代决策直到满足终止条件；再加护栏、评测与日志可观测。可用LangGraph/AutoGen等框架或自研循环实现。


### Agent-002-004 | ★★★★☆

LLM Agents有哪些类型？

**答案：**
按结构：单Agent（ReAct式工具循环）与Multi-Agent（协作/竞争/层级分工）；按自主性：固定Workflow型→半自主型→全自主型（AutoGPT类）；按形态：对话助手型、任务执行型（代码Agent、浏览器操作）、自主研究型、模拟社会型（Generative Agents）。


### Agent-002-005 | ★★★★☆

是什么让Agent有了自制（自主）的能力？

**答案：**
自主性来自：①LLM本身的推理与规划能力，能把目标分解为步骤；②工具调用接口使其可以'动手'改变环境；③记忆与反馈闭环——行动结果作为观察回喂模型进行下一轮决策；④调度循环机制驱动持续运行。四者结合使其无需人工逐步指令即可迭代逼近目标。


### Agent-002-006 | ★★★★☆

什么是Agent？与大模型有什么本质不同？

**答案：**
Agent是能感知环境、自主决策并采取行动以达成目标的系统；大模型只是被动的输入→输出生成器，单轮、无状态。本质区别：LLM是推理引擎，而Agent = LLM + 规划 + 记忆 + 工具 + 执行循环，具有目标导向性、状态持续性和对真实世界的作用能力。


### Agent-002-007 | ★★★★☆

Agent的基本架构由哪些核心组件构成？

**答案：**
通常包括规划（Planning）、记忆（Memory）、工具调用（Tool Use）和执行流程控制等模块。


### Agent-002-008 | ★★★★☆

Workflow、Agent、Tools这三个的概念和区别介绍一下？

**答案：**
Tools是可被调用的外部能力单元（搜索、API、代码执行等）；Workflow是预先编排好的固定流程，由代码定义控制流、LLM在节点上被调用，确定性强；Agent是以LLM为控制器的动态循环，模型在运行时自主决定调用哪个工具、执行几步。核心区别是控制权：workflow由开发者写死路径，agent由模型动态决策（Anthropic《Building Effective Agents》的界定：能用workflow解决就别用agent）。


### Agent-002-009 | ★★★★☆

Agent推理模式有哪些？ReAct是啥？具体是怎么实现的？

**答案：**
常见推理模式：CoT（思维链单次推理）、ReAct（推理-行动交替）、Plan-and-Execute（先全局规划再逐步执行）、Reflection/Reflexion（自我反思迭代改进）、ToT（树搜索多条推理路径）、工具增强推理等。ReAct实现：在prompt中给出任务、可用工具清单和Thought/Action/Observation格式约定；模型每轮输出Thought（分析）+Action（工具名与参数），运行时解析Action并实际执行工具，将结果作为Observation追加进上下文，循环迭代直到模型输出Final Answer或达到最大步数/终止条件。


### Agent-002-010 | ★★★★☆

ReAct、Plan-and-Execute、Reflection三种范式有什么核心区别？实际项目中该如何选型？

**答案：**
核心区别：ReAct是'思考-行动-观察'逐步交替，灵活但步数多、易偏航；Plan-and-Execute先产出整体计划再逐步执行，结构清晰、省token、适合长任务，但计划可能过时需replan；Reflection是执行后自我批判再重试，提升质量但增加轮次成本。选型：简单直接任务用ReAct；多步骤明确任务用Plan-and-Execute；质量要求高且有验证手段时叠加Reflection；生产上通常组合使用并给反思/重试设上限。


### Agent-002-011 | ★★★★☆

复杂任务怎么做的任务拆分？为什么要拆分？效果如何提升？

**答案：**
为什么拆：单步上下文与推理深度有限，拆分后单步难度降低、错误可隔离重试、子任务可并行/缓存/复用并独立验证。怎么拆：让LLM基于目标与约束做递归分解（Plan、CoT、ToT），或按业务模板拆成DAG，每个子任务定义清晰的输入、工具与验收标准。效果提升来源：降低单步出错率、便于针对性优化子任务、并行执行缩短时延、中间结果可检查拦截错误传播。


### Agent-002-012 | ★★★★☆

请你介绍一下AI Agent的记忆机制，并说明在实际开发中应该如何设计记忆模块？

**答案：**
记忆机制：短期记忆即上下文窗口内的对话与中间状态；长期记忆是外部持久存储（向量库、KV存储、文件、图数据库），通过embedding检索按需注入prompt。设计要点：①定义写入时机（关键事实、用户偏好、任务结论）；②存储粒度（消息/摘要/结构化原子事实）；③检索策略（相似度+时间衰减+重要性加权，top-k注入）；④遗忘与压缩（去重合并、摘要、淘汰）；⑤控制注入预算避免上下文爆炸。


### Agent-002-013 | ★★★★☆

Agent的长短期记忆系统怎么做的？记忆是怎么存的？粒度是多少？怎么用的？

**答案：**
短期记忆：当前会话上下文中的消息与工作状态，直接放prompt。长期记忆：持久化存储——语义记忆以原子事实/知识条目为粒度存向量库（embedding索引），情景记忆按时间组织事件，用户画像等结构化信息存数据库。使用时按当前query检索top-k相关条目+会话摘要注入上下文；会话结束后做摘要固化，重要事实单独抽取存储。粒度通常分三级：原子事实、事件/轮次、会话摘要。


### Agent-002-014 | ★★★★☆

Agent记忆压缩通常有哪些方法？

**答案：**
①摘要压缩：把长对话/历史事件总结成短摘要，可递归分层（rolling summary）；②关键信息抽取：只保留实体、事实、偏好等结构化条目；③检索替代全量：向量检索top-k注入，不携带全部历史；④窗口+重要度保留：近期原文+远期摘要；⑤记忆合并去重与遗忘机制（时间衰减、访问频率淘汰）；⑥知识图谱化/代码化存储压缩语义。


### Agent-002-015 | ★★★★☆

什么是Multi-Agent？说说Single-Agent和Multi-Agent的设计方案？

**答案：**
Multi-Agent是由多个具有不同角色、工具、记忆的Agent协作完成任务的系统。Single-Agent设计：一个LLM+工具循环+记忆，简单可控、成本低，适合边界清晰的任务。Multi-Agent设计：按角色分工（planner/worker/critic、coder/tester/reviewer等），通过消息传递、中心编排或共享黑板协作，可并行、可对抗校验，适合大型复杂任务；代价是通信开销、误差传播与调试复杂度上升。


### Agent-002-016 | ★★★★☆

如何设计多Agent的协作与动态切换机制？

**答案：**
协作机制：①中心化编排：orchestrator/router负责任务分发与结果汇总（supervisor模式）；②流水线接力：按阶段移交（handoff）上下文；③辩论/投票：多agent讨论或投票收敛提高质量；④群体协同（swarm）。动态切换：由路由Agent做意图识别与专家选择（function calling指定下一个agent）、基于状态机按任务阶段流转、按能力描述与负载动态路由，并用共享记忆/统一状态保证上下文一致与平滑交接。


### Agent-002-017 | ★★★★☆

在工程实践中，为什么有时候选择「手搓」Agent，而不是直接用成熟框架？

**答案：**
①Agent核心循环（LLM+工具+循环+重试）代码量很小，自研无黑盒，提示词、上下文管理、错误处理完全可控、易调试和优化；②框架抽象层往往遮蔽关键细节（prompt拼接、状态流转），出问题难定位，且依赖重、API变动快；③业务上常需要深度定制上下文工程、成本控制与可观测性，自研更灵活；实践中常见做法：直接用SDK+function calling手搓核心，把框架当参考实现。


### Agent-002-018 | ★★★★☆

如何赋予LLM规划能力？

**答案：**
①提示层面：CoT、ReAct、Plan-and-Solve等结构化提示引导分步思考与制定计划；②算法层面：任务分解（递归分解、思维树ToT搜索）、反思修正（Reflexion）、外部符号规划器（PDDL、代码生成再执行）；③工程层面：给明确目标与约束、提供环境反馈信号与重试机制、规划与执行解耦（planner/executor分离）、用少样本示范计划格式。


### Agent-002-019 | ★★★★☆

讲讲Agent的反思机制？为什么要用反思？具体怎么实现？

**答案：**
反思机制指Agent对自身输出或执行轨迹进行自我评估与批判，找出问题后生成改进方案并重试（Reflexion范式）。为什么：单次生成易出错，反思把环境反馈/错误显式化为语言经验，能显著提升复杂任务成功率而不需更新参数。实现：执行后将结果连同评价（自查清单、单元测试、人工或模型评审）回喂LLM，要求总结失败原因并形成改进建议，存入记忆指导下一轮尝试；需限制最大反思轮数以控制成本。


### Agent-002-020 | ★★★★☆

什么是Function Calling？原理是什么？

**答案：**
模型根据用户输入判断是否需要调用工具，输出结构化的函数名和参数JSON，由应用执行后把结果回传模型。


### Agent-002-021 | ★★★★☆

大模型的Function Call能力是怎么训练出来的？

**答案：**
主要通过SFT让模型在给定工具schema时输出结构化调用（JSON格式的函数名+参数），并用带工具结果回填的多轮对话数据训练其根据返回结果继续推理；进一步可用强化学习（以任务完成度/调用正确性为奖励）提升调用准确率。训练数据通常来自真实API调用日志改写或模型合成+人工校验。


### Agent-002-022 | ★★★★★

Function Calling与RAG的区别和联系是什么？什么时候用Function Calling，什么时候用RAG？

**答案：**
Function Calling让模型调用外部API/工具执行动作（写操作、实时查询、系统交互），RAG是从知识库检索文本作为上下文辅助生成（只读静态知识）。需要"做事"或获取实时/私有系统数据时用FC；需要"查资料"回答知识型问题时用RAG；二者常结合，如通过FC触发检索。


### Agent-002-023 | ★★★★☆

Agent是如何结合工具、知识和规划自主运行的？

**答案：**
以LLM为大脑：规划模块（ReAct/Plan-and-Execute）把目标分解为可执行步骤，工具模块通过Function Call/MCP与环境交互获取信息或执行动作，知识来自系统提示、RAG检索与记忆库；按"思考→行动→观察"循环运行，根据每步反馈动态调整计划直至完成目标。


### Agent-002-024 | ★★★★☆

多Agent架构下，主Agent和子Agent的通信链路应该如何设计？如何处理异常？

**答案：**
常采用主Agent中心化编排：任务经消息总线/队列传递结构化消息（JSON，含task_id、trace_id、上下文与结果），子Agent只回传结论性摘要。异常处理：失败重试（指数退避）、超时熔断与降级、失败状态结构化回传由主Agent重新规划或转人工，全程trace日志支持回溯。


### Agent-002-025 | ★★★★★

如何解决Agent的上下文漂移问题？如何防止工具调用出现幻觉？

**答案：**
上下文漂移：在关键节点重注入原始目标与系统约束、定期把无关历史压缩成摘要、用计划/检查点校验当前步骤是否对齐目标。工具调用幻觉：工具描述与参数schema写清晰、JSON Schema+枚举白名单校验参数、只注册审核过的工具、校验失败即拒绝并重试，工具结果也要经校验后才进入下一轮推理。


### Agent-002-026 | ★★★★☆

如何在有限的上下文窗口内放入关键内容？如何做短期和长期记忆压缩？

**答案：**
短期记忆用滑动窗口+滚动摘要（旧对话压缩为要点），长期记忆外置到向量库/结构化存储并按需检索注入；工具返回只保留关键字段，原始结果落库可回查；把目标、约束、关键事实固定放在上下文头部（system区），用重要性评分决定保留与压缩哪些内容。


### Agent-002-027 | ★★★★☆

在长任务或复杂任务中，如何保证模型不会偏离原始目标？

**答案：**
目标锚定：把目标与约束显式写入计划并在每轮prompt中保留；执行Plan→Act→Review闭环，每步完成后对照todo/checklist核验；设置里程碑检查点，Reviewer/评估器判断输出是否服务最终目标，发现偏差即重新规划或回滚到最近检查点。


### Agent-002-028 | ★★★★☆

如何处理工具调用的安全问题（如Key泄露、敏感信息暴露）？

**答案：**
凭证放服务端密钥管理（KMS/环境变量/secret manager），绝不进入模型上下文与日志；工具按最小权限配置（只读优先），敏感操作加人工确认与二次授权；执行前做参数白名单校验、注入检测，输出侧做敏感信息脱敏；沙箱隔离执行并保留完整审计日志。


### Agent-002-029 | ★★★★☆

Agent为什么要分成三层记忆？怎么保证长期记忆和外部记忆是正确的？

**答案：**
分层是为平衡容量-速度-成本：工作记忆（上下文窗口）快但极小，短期记忆保存会话内状态，长期/外部记忆（向量库、数据库）容量大且可跨会话。正确性保证：写入时记录来源、时间戳与置信度（可溯源），检索时用相似度阈值+重排，冲突时以更新/更权威版本为准，配合定期清理、一致性校验与人工纠错。


### Agent-002-030 | ★★★★☆

Plan-and-Execute基于DAG拓扑排序，说说你的设计。

**答案：**
Planner将任务分解为子任务节点并抽取依赖关系构成DAG（边表示数据/前置依赖）；按拓扑排序调度，入度为0的节点并发执行，节点输出回填到依赖节点的输入；执行中支持失败重试与局部重规划（只重排受影响子图），最终按依赖顺序汇聚结果。优势是并行度高、依赖关系显式可校验、无环保证不会死循环。


### Agent-002-031 | ★★★★☆

Planner、Worker、Reviewer的边界怎么设计？挂载的工具一样吗？

**答案：**
Planner只负责任务拆解、分配与依赖管理，不做执行；Worker负责调用工具完成单一子任务；Reviewer负责校验结果与目标一致性并决定通过或退回。工具不挂一样的：Planner基本不需要工具（至多轻量查询），Worker挂执行类工具（搜索、代码、API），Reviewer只挂评估类工具（比对、校验），按最小权限原则分别配置。


### Agent-002-032 | ★★★★☆

如果子Agent还能调用子Agent，怎么保证不会挤爆Token？

**答案：**
限制递归深度与每层扇出（如最多3层、每层N个子任务）；子Agent各自独立上下文，只向父级返回压缩后的结构化结论而非完整过程；设置全局Token预算，超限即熔断；详细中间结果落库，父级需要时再按需检索而非全量携带。


### Agent-002-033 | ★★★★☆

多个Agent的system、user、assistant、tool消息怎么编排，怎么保证不乱序？

**答案：**
以会话/任务为单位维护全局trace_id与单调递增的step序号，所有消息按序持久化，拼装时按序重放保证不乱序；每轮严格按system→user→assistant(tool_call)→tool(结果)结构编排，工具消息用tool_call_id与发起调用配对校验；并发分支各自独立会话，聚合时再按序合并。


### Agent-002-034 | ★★★★☆

DOM网页内容很大，怎么保证不撑爆上下文？

**答案：**
不把原始DOM直接喂模型：先解析抽取可交互元素生成精简的可访问性树/结构化摘要（元素id、角色、文本、是否可操作），过滤script/style等无关内容；超长时按视口或区块分片、按任务相关性检索相关片段，页面快照落库供按需查询，交互后只传增量变化（diff）。

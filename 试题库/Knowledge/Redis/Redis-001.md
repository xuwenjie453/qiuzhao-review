### Redis-001-001 | ★★★★★

Redis 为什么快？单线程为什么还能支撑高并发？

**答案：**
四个原因：①纯内存操作，无磁盘 IO；②高效数据结构（SDS、跳表、压缩列表/紧凑列表、dict 渐进式 rehash）让单命令 O(1)/O(logN)；③单线程命令执行避免锁竞争与上下文切换，实现简单且时延可预测；④IO 多路复用（epoll）事件驱动框架，单线程也能同时监听大量连接。要补版本演进：Redis 6.0 引入 IO 多线程——但只用于读写网络数据和协议解析，命令执行仍是单线程，所以依然没有并发安全问题；后台线程则一直存在（异步删除、fsync 等）。

**解析：**
单线程的收益本质：把"并行带来的复杂度"换成"事件驱动的吞吐"。瓶颈通常不在 CPU 而在网络与内存带宽，这解释了为什么 6.0 只多线程化 IO。危险在于单线程的"长命令"：KEYS *、大集合的全量操作、大 key 删除都会阻塞所有请求——这正是慢查询与大 key 治理的根源。异步删除 UNLINK、SCAN 渐进遍历是标配替代。

epoll vs select/poll：select 有 fd 数量限制且每次全量拷贝；epoll 红黑树管理 fd + 就绪链表回调，事件复杂度 O(1)。


### Redis-001-002 | ★★★★★

Redis 常用数据结构的底层实现？ZSET 为什么用跳表？

**答案：**
五大数据结构按小数据/大数据双编码：String 用 SDS（长度头+预分配，O(1) 取长、二进制安全）；Hash 小时 ziplist/listpack（7.0 替代 ziplist）大时 dict；List 用 quicklist（双向链表串 ziplist/listpack 节点）；Set 小时 intset/紧凑编码，大时 dict；ZSET 小时紧凑列表，大时"dict（member->score 定位）+ 跳表（按 score 排序）"双结构。ZSET 用跳表不用红黑树的原因：①范围查询天然沿层链遍历，实现简单；②平均 O(logN) 且常数小；③无旋转维护，代码简单；④按排名定位也容易。跳表靠多层概率索引（每层晋升概率 1/4）实现二分效果。

**解析：**
SDS 关键设计：len 头部记录长度（strlen O(1)）、记录 free 空间做预分配与惰性释放、兼容 C 字符串函数。这是"为什么 Redis 自己造字符串"的标准答案。

渐进式 rehash：扩容时同时持有新旧两张表，每次命令顺带迁移一桶 + 定时任务迁移，避免一次性百万 key 的长停顿。期间读查两表、写只进新表。

跳表细节：层数随机生成（幂次定律），节点带 span（跨度）支持 ZRANK O(logN)；与 dict 并存保证 ZSCORE O(1)。


### Redis-001-003 | ★★★★★

RDB 和 AOF 的区别？生产怎么选？

**答案：**
RDB：定时把内存快照二进制落盘（save 触发 bgsave，fork 子进程执行），文件紧凑恢复快，但两次快照之间的数据会丢。AOF：追加写命令日志，刷盘策略 appendfsync everysec（默认，最多丢 1 秒）/always（最安全最慢）/no（交给 OS）；文件大，靠 AOF 重写（bgrewriteaof，按当前数据状态生成最小命令集）瘦身。生产默认推荐 4.0+ 的混合持久化：AOF 重写时先写 RDB 格式全量、之后追加增量 AOF，兼得恢复速度与低丢失。fork 的代价要会讲：子进程写时复制（COW），大内存实例 fork 会瞬间拷贝页表造成停顿，且 COW 可能放大内存峰值。

**解析：**
AOF 重写原理：主进程 fork 子进程按内存现状生成新 AOF；重写期间的新命令写入 aof_buf 与 aof_rewrite_buf 双份，子进程完成后追加增量并原子替换。7.0 改为 Multi-Part AOF（base+incr 清晰分工）。

RDB 的 fork 停顿量级：fork 只复制页表，10GB 实例约几十毫秒级停顿，但 COW 在写入高峰期可能内存翻倍——设置足够的内存余量、避开高峰 bgsave。

恢复优先级：实例重启优先加载 AOF（数据更全）。


### Redis-001-004 | ★★★★☆

过期键怎么删除？内存满了怎么淘汰？

**答案：**
过期删除是"惰性 + 定期"组合：访问时检查到期则删（惰性）；后台定期随机抽查带过期时间的 key，超比例则继续下一轮（周期性），兼顾 CPU 与内存。内存达到 maxmemory 时按淘汰策略释放：noeviction（默认，写报错）、allkeys-lru/volatile-lru（近似 LRU：抽样淘汰）、allkeys-lfu/volatile-lfu（4.0+ 访问频率）、allkeys-random/volatile-random、volatile-ttl（越早过期越先删）。缓存场景几乎都配 allkeys-lfu 或 lru；注意 volatile 系列在没有任何带过期 key 时等于 noeviction。Redis 的 LRU 是抽样近似（默认 5 个样本取最久未用），LFU 用对数计数器+衰减因子抑制历史热度。

**解析：**
淘汰的运行位置：主线程内执行（同步删除可阻塞）或配 lazyfree-lazy-eviction 异步；大批淘汰时的延迟毛刺要监控。

过期与淘汰的区分（易混点）：过期是"key 到达 TTL"，淘汰是"内存压力下的牺牲"。两者都会导致"key 消失"，排查缓存 miss 时要分别看 expired_keys 与 evicted_keys 指标。

LFU 参数：lfu-log-factor（计数增长速度）、lfu-decay-time（衰减周期分钟），默认适合多数缓存。


### Redis-001-005 | ★★★★★

缓存穿透、击穿、雪崩分别是什么？怎么防？

**答案：**
穿透：查询**不存在的数据**，缓存永远不命中，请求全部打到 DB（恶意扫描典型）。防：空值缓存（短 TTL）、布隆过滤器前置拦截、接口参数校验与风控。击穿：**某个热点 key 过期瞬间**，大量并发同时回源。防：互斥重建（分布式锁/单飞 singleflight）、热点 key 逻辑过期（物理不过期+逻辑时间戳异步刷新）、热点永不过期+后台更新。雪崩：**大量 key 同时过期**或 **Redis 实例宕机**导致 DB 被冲垮。防：TTL 加随机抖动、多级缓存、集群高可用（哨兵/Cluster）、限流降级兜底。三者的记忆锚点：穿透=查不存在的、击穿=单点热点过期、雪崩=集体失效。

**解析：**
单飞（singleflight）模式值得展开：同进程内相同 key 的回源请求合并为一次（Go 官方 singleflight 的思想，Java 可用 Caffeine LoadingCache 或本地锁），配合分布式锁跨实例去重，锁内"二次检查缓存"避免重复回源。锁的粒度与超时要控制，避免锁服务本身成瓶颈。

布隆过滤器：位数组+k 个哈希，判"可能存在"与"一定不存在"，不支持删除（计数布隆/布谷鸟可），误判率与位数组大小、哈希个数相关。数据集动态变化时需要重建策略。

逻辑过期的实现：值里封装 {data, expireAt}，读到期不阻塞、起异步任务持锁刷新，读到旧数据是接受的一致性代价。


### Redis-001-006 | ★★★★★

怎么用 Redis 做分布式锁？有哪些坑？

**答案：**
正确加锁姿势是一条原子命令：`SET lock_key unique_value NX PX 30000`（NX 互斥、PX 防死锁、唯一值防误删）。解锁必须 Lua 保证"判断是自己的锁 + DEL"原子性。手写版的三大坑：①业务超时锁先过期被他人持有——用看门狗续期（Redisson 默认 30s，每 10s 续）；②释放别人的锁——value 唯一标识比对；③锁过期业务未完——看门狗守护线程解决。生产直接用 Redisson：可重入、看门狗、公平锁、读写锁、红锁都已封装。主从切换的锁丢失问题（主写锁未同步即宕机）引出 RedLock 争议：Martin Kleppmann 与 antirez 的著名论战，结论是 RedLock 实现复杂且并不完美，多数公司选择接受小概率风险或改用强一致存储（ZK/etcd 的 fencing token 思路）。

**解析：**
Redisson 加锁链路：Lua 判断存在性+owner 匹配 → hash 结构 {lockKey: {clientId:count}} 支持可重入 → pexpire → 订阅解锁频道 + 自旋重试（有等待超时）。看门狗只在"未显式指定 leaseTime"时启用。

fencing token 思想：锁附带单调递增令牌，存储层校验令牌新鲜度，彻底防"GC 停顿后旧持锁者回来写入"——Redis 方案缺这个兜底，这是 Kleppmann 批评的核心。

适用边界：分布式锁防的是"重复执行"这类非极致敏感场景；资金类强一致用 DB 行锁/乐观锁兜底，Redis 锁只做性能优化层。


### Redis-001-007 | ★★★★★

缓存和数据库的一致性怎么保证？先删缓存还是先更新库？

**答案：**
主流是 Cache Aside 写策略：**先更新数据库，再删除缓存**（不是更新缓存）。为什么删不更：更新缓存可能写了永不被读的值（写多读少浪费），且并发写覆盖容易错序；删除则让下次读触发惰性加载。为什么"先库后删"：先删后写的话，删除与写库间隙的读请求会把旧值又载入缓存，造成长期不一致。"先库后删"的残留风险（写库成功、删缓存失败）用三层兜底：重试队列/消息表、延迟双删（写后延迟几百毫秒再删一次，清掉并发读的回填）、或订阅 binlog（Canal）异步删除——把删除动作从业务代码解耦。要诚实说明：缓存方案本质是最终一致，要求强一致就别用缓存直读。

**解析：**
"先库后删"的理论破绽（并发时序）：读请求在"旧值仍在缓存被读到"之后、缓存删除之前发生，读到旧值——概率低（读远快于写+删除），且延迟双删/binlog 订阅可把窗口压到毫秒级。这就是"低不一致概率 + 简单实现"胜出"先删后写高不一致概率"的原因。

删除失败处理演进：本地重试 → 消息表/事务后钩子 → Canal 订阅 binlog 统一清理（推荐，业务零侵入）。

读侧配合：缓存 miss 回源要"查库后设缓存"原子性无碍，但要防击穿（K-REDIS-005）。


### Redis-001-008 | ★★★★☆

大 key 和热 key 分别是什么？怎么治理？

**答案：**
大 key：单个 key 的 value 过大（string 几 MB、集合元素数万级），危害是读写慢、删除阻塞主线程（尤其老版本 del）、网络带宽占满、迁移/过期卡顿。治理：拆分（hash 分桶、按业务切片）、压缩、UNLINK 异步删、lazyfree 开启、SCAN+--bigkeys 定期体检。热 key：单个 key 的 QPS 极高，单分片 CPU/网卡被打满（Cluster 下无法自动分摊）。治理：本地缓存（Caffeine/进程内 L1）挡读、key 加随机后缀分散到多个副本（读多写少）、读写分离多副本、限流保护。发现手段：--hotkeys、客户端埋点统计、代理层监控。

**解析：**
大 key 判定参考线（社区惯例）：string > 10KB、集合元素 > 5000 或总大小 > 1MB 就要审视（不同公司阈值不同，答"给出量级+说明按业务定"即可）。删除大集合的正确姿势：UNLINK 交给后台线程，或 SCAN 分批 HDEL/SPop。

热 key 的本地缓存一致性：L1 用短 TTL（秒级）+ 失效广播（pub/sub），接受秒级陈旧；写少读多的热点（商品、活动配置）天然适合。


### Redis-001-009 | ★★★★☆

Redis 主从、哨兵、Cluster 三种架构的区别与选型？

**答案：**
主从复制：读写分离+数据冗余，但不自动故障转移——主挂了要人工切换。哨兵（Sentinel）：在主从之上加自动监控与选主（每秒 ping，主观/客观下线 + 基于多数派投票选新主），解决 HA，但不解决容量与写扩展——仍是全量数据的单主写入。Cluster：16384 个哈希槽分片到多个主节点，每个主再带从，容量与写吞吐水平扩展，客户端按槽路由（MOVED/ASK 重定向），限制是多 key 命令/事务/Lua 要求 key 同槽（hash tag {} 可强制同槽）。选型：读扩展+HA 用主从+哨兵；数据量或写入超单机上限用 Cluster；小规模直接云托管版。

**解析：**
复制的核心机制：全量同步（PSYNC，生成 RDB 传输+缓冲增量）与部分重同步（replication offset + 复制积压缓冲区 backlog，断线重连若 offset 仍在缓冲区内则增量续传，否则退化全量）。backlog 大小要按"断线时长×写速率"估算。

哨兵细节：客观下线需要 quorum 个哨兵同意；选leader 用 Raft 式投票；故障转移选择从库的优先级（replica-priority）> offset 最大 > runid 最小。脑窗口：min-replicas-to-write 可降低丢写。

Cluster 的 hash tag：`user:{1000}:cart` 与 `user:{1000}:profile` 同槽，支撑多 key 原子操作——代价是业务要显式设计。


### Redis-001-010 | ★★★☆☆

Redis 事务和 Lua 脚本的区别？原子性到底怎么保证？

**答案：**
Redis 的 MULTI/EXEC 事务是"命令打包顺序执行"，保证隔离（执行期不被其他命令插队）但**不保证原子**：入队阶段语法错误整包作废，执行阶段某条运行时错误其余命令照常执行、不回滚——Redis 没有回滚机制。WATCH 提供乐观锁（执行前被改则 EXEC 失败）。Lua 脚本整体作为单命令执行，脚本内任何中间错误默认会中断（可编写容错），且能读值做逻辑判断，原子性和表达力都优于事务。所以"需要条件判断的多步操作"一律用 Lua（扣库存、限流、令牌桶），Cluster 下注意 key 同槽。

**解析：**
Lua 执行模型：脚本执行期间单线程独占，天然串行化；但脚本不能太重（等同长命令阻塞）。脚本缓存：EVALSHA + SCRIPT LOAD，避免每次传全量脚本。

库存扣减经典 Lua：读 stock → 判断 ≥ n → decr 并返回成功；否则返回失败码。用 WATCH+MULTI 也能做但冲突重试率高，Lua 一次到位。

Redis Functions（7.0）：服务端持久化函数库，替代散落脚本的工程化方案。


### Redis-001-011 | ★★★☆☆

Redis 实现延迟队列有哪几种方式？

**答案：**
三种常用实现：①ZSET：score 存执行时间戳，定时轮询 `ZRANGEBYSCORE queue now limit n` 取到期任务，处理成功 ZREM——简单通用，轮询间隔决定精度，多实例要用 Lua 保证"取出+删除"原子防重复消费；②Redisson DelayedQueue：基于 ZSET 的封装，提供 offer/到期转移语义，工程省心；③Stream + 消费组：本身不自带延迟，配"延迟桶"（按延迟分段 ZSET）到期后 XADD 进真实队列。选型建议：延迟精度秒级、量中小用 ZSET 自研或 Redisson；严格可靠/重试/死信要求高就上专业 MQ（RocketMQ 延迟消息、RabbitMQ 死信）。

**解析：**
ZSET 方案的可靠性细节：取任务（ZRANGEBYSCORE）与删除（ZREM）必须原子（Lua），否则多实例重复消费；消费失败的回退（score 改回未来时间+重试次数计数）；毒丸任务（反复失败）设上限入死信列表。

与 K-JUC-012 的 DelayQueue 对照：JVM 内延迟队列 vs 跨进程持久化延迟队列，场景不同。


### Redis-001-012 | ★★☆☆☆

Redis 和 Memcached 怎么选？

**答案：**
Memcached 优势：多线程（利用多核，吞吐在高并发简单 KV 场景优秀）、极简、内存管理（slab）成熟稳定。Redis 优势：丰富数据结构（hash/list/zset/stream）、持久化、主从/哨兵/Cluster 高可用与扩展、Lua、pub/sub、事务。选型事实：如今默认 Redis（生态与功能全面），Memcached 仅在"纯 KV、超高并发、无持久化需求、多线程吞吐敏感"的场景仍有价值（如社交 feed 的简单计数、session 等价物）。回答时顺带对比缓存三件套之一本地缓存：进程内缓存无网络开销但要处理一致性，通常是 L1+Redis 的 L2 结构。


### Redis-001-013 | ★★★☆☆

布隆过滤器的原理、误判率怎么算？有哪些变体？

**答案：**
位数组 + k 个独立哈希：插入时把 k 个哈希位置置 1；查询时 k 个位置全为 1 才"可能存在"，任一为 0 则"一定不存在"。核心特性是单向：可能误判存在（false positive），绝不误判不存在。误判率约 (1-e^(-kn/m))^k（n 元素、m 位数组、k 哈希个数），最优 k ≈ (m/n)ln2，此时 p ≈ 0.6185^(m/n)——即每元素约 10 bit 时误判率 1%。Redis 用 RedisBloom 模块的 BF.ADD/BF.EXISTS。局限：不支持删除（标准版）、容量需预估、无法枚举。变体：计数布隆（支持删除，空间大）、布谷鸟过滤器（删除+更高空间效率）、伸缩布隆（RedisBloom 支持自动扩容）。

**解析：**
工程闭环（防穿透场景）：①容量按"预期 key 数 × 安全系数"建；②数据导入期双写（DB+布隆）；③删除/失效的处理：定时全量重建（低峰）、或业务标记层（版本化重建）；④误判的兜底：穿透到 DB 的少量请求再走空值缓存，无害。

参数直觉：1 亿元素、1% 误判 ≈ 120MB 级内存——比空值缓存可控得多。


### Redis-001-014 | ★★★☆☆

用 Redis 的 ZSET 实现排行榜要注意什么？

**答案：**
基本玩法：ZINCRBY 更新分数、ZREVRANGE 取 TopN、ZREVRANK 查个人排名。工程注意四点：①并列分数的稳定排序——score 组合"业务分+时间戳小数位"（如 score = base + (MAX_TS - ts) * ε），先到先排前；②量级与分片——单 ZSET 千万成员后查询变慢，按周期（日/周）分 key + 归档，或分段（千名榜实时+长尾离线计算）；③防刷——限频（Lua 计数）、分数上限、异常分审计；④与 DB 的持久关系——Redis 是实时视图，最终数据落库对账。排名 O(logN) 靠跳表 span，这也是 ZSET 优于"DB order by"的延迟优势来源。


### Redis-001-015 | ★★★☆☆

Pipeline、事务、Lua 三者的批量与原子性差异？

**答案：**
解决的是不同问题：Pipeline 解决网络往返（RTT）——把 N 条命令一次性发出、统一收响应，省的是网络时间，不保证原子也不保证顺序外语义，中间某条失败不影响其他；MULTI/EXEC 解决"打包执行"，执行期不被插队（隔离）但无回滚；Lua 解决"原子+条件逻辑"。三者可叠加（事务/Lua 内部天然免多次 RTT）。Cluster 下 Pipeline 要按节点分组发送，客户端库已封装。批量写入的性能调优首选就是 pipeline 分批（如每批 500 条），注意单批太大占客户端与服务端缓冲。


### Redis-001-016 | ★★★☆☆

什么场景下不该用 Redis？缓存误用的典型反模式？

**答案：**
边界判断题，重点给出反模式清单：①把 Redis 当主存储——强业务数据（资金、订单状态）放缓存当唯一事实源，宕机/淘汰即丢数据；②单 value 巨型对象当 DB 行用——无法条件查询，全部读到内存；③用 KEYS/阻塞命令当日常操作；④把强一致需求塞给缓存（K-REDIS-007 的最终一致本质）；⑤无限增长的集合当队列/时序库用（无治理的大 key）；⑥用 pub/sub 做可靠消息（不持久化、无 ACK，那是 Stream/MQ 的事）。正确姿态：Redis 是高性能数据结构服务器/缓存层，"数据能丢吗、要查询吗、要强一致吗"三问决定它适不适合。


### Redis-001-017 | ★★★★☆

Redis 6 的 ACL 与生产权限管理

**答案：**
老版本只有一个 requirepass+危险命令靠 rename 关闭；Redis 6 引入 ACL：多用户、按命令类别（read/write/dangerous 等）与 key pattern 授权，`ACL SETUSER app_user on >密码 ~order:* +read +write -@dangerous`。生产基线：应用账号最小权限（只允许用到的前缀与命令）、禁用 FLUSHALL/KEYS/CONFIG 于业务账号、默认用户 off、网络层再叠加内网隔离与 TLS。这把"共享 root 密码"的老问题升级为可审计的权限体系。

**解析：**
类别速记：@read @write @connection @dangerous @admin；key pattern 限定可访问键前缀，天然隔离多业务共用实例。审计：ACL LOG 记录被拒命令。迁移路径：requirepass 时代→ACL 多用户→每应用独立账号+前缀隔离。云托管 Redis 通常提供账号体系替代。


### Redis-001-018 | ★★★★☆

Redis 大规模 key 的迁移方案（扩容/换云/双写）

**答案：**
三类路径：①官方迁移工具/云厂商 DTS：全量 RDB 快照+增量命令流追平+切换，停机窗口秒级；②双写迁移：应用同时写新老集群，回读对比校验，灰度切读再停旧写——可控但代码侵入；③按 slot 迁移的在线扩容（Redis Cluster 的 reshard，逐槽搬迁）。校验是关键：全量比对（scan 抽样+数量+checksum），切换保留回滚窗口，TTL 类数据要带上过期语义校验。

**解析：**
选型维度：可停机时长、数据量、是否跨版本/跨云、TTL 数据占比。同步工具的坑：大 key 传输超时、big pipeline 打爆目标端、命令版本不兼容（如新版本命令老版本不识别）。双写的一致性等级：先新后旧+补偿对账（类比 K-REDIS-007 缓存一致性的讨论）。


### Redis-001-019 | ★★★★☆

Redis 4.0+ 推荐的"恢复快+丢失少"持久化组合是：

B. 仅 AOF appendfsync always

aof-use-rdb-preamble yes。


### Redis-001-020 | ★★★★☆

过期删除策略组合

Redis 对过期 key 采用的策略是：

A. 仅定时扫描
B. 仅惰性删除
C. 惰性删除 + 定期抽样删除
D. 引用计数立即删除

**答案：** C

**解析：**
访问时惰性检查+后台周期随机抽样，兼顾 CPU 与内存；A/B 单独均有漏洞；D 错。

### Redis-001-022 | ★★★☆☆

### Redis-001-023 | ★★★★☆

布隆过滤器判读

布隆过滤器判断"某 key 存在"时，准确的说法是：

A. 一定存在
B. 可能存在（有一定误判率），但判断"不存在"时一定不存在
C. 一定不存在
D. 存在性与误判率无关

**答案：** B

**解析：**

### Redis-001-024 | ★★★☆☆

Pipeline 语义

关于 Pipeline，正确的是：

A. Pipeline 保证命令原子执行
B. Pipeline 只减少网络往返次数，不保证原子性与隔离性
C. Pipeline 等价于事务
D. Pipeline 必须在 Cluster 下分节点发送

**答案：** B

**解析：**
Pipeline 批量发送批量接收，省 RTT；中途其他客户端命令可插队，无原子性（原子要 MULTI/Lua）；C 错；D 是 Cluster 客户端的实现细节而非 Pipeline 语义。

Pipeline=网络优化；原子=事务/Lua。


### Redis-001-025 | ★★★★★

缓存三兄弟判别

"查询数据库中根本不存在的数据，缓存永远不命中"描述的是：

A. 缓存击穿
B. 缓存穿透
C. 缓存雪崩
D. 缓存污染

**答案：** B

### Redis-001-026 | ★★★★☆

分布式锁解锁原子性

解锁操作"先 GET 判断是自己的锁再 DEL"存在的问题与修复是：

A. 无问题
B. 判断与删除两步非原子，可能删掉他人的锁；应使用 Lua 脚本原子执行
C. 应该用 EXPIRE 代替 DEL
D. 应该改用 SETNX

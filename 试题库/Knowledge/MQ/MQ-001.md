### MQ-001-001 | ★★★★★

为什么要引入消息队列？带来哪些新问题？

**答案：**
三大价值：①异步提速——主链路只做核心动作，耗时操作（发通知、记积分）异步化，接口 RT 下降；②解耦——生产者只依赖消息契约，消费方增减不影响上游；③削峰填谷——突发流量先进队列，消费端按自身能力平稳处理。代价必须同步说出来（体现工程成熟度）：系统复杂度上升（多一个组件要维护监控）、一致性变弱（异步链路只能最终一致，需要幂等与对账）、可用性依赖 MQ 自身（MQ 挂了主链路是否受影响要设计清楚）、消息可靠性问题链（丢失/重复/顺序/积压）。回答公式："场景价值 + 我如何应对代价"。


### MQ-001-002 | ★★★★★

怎么保证消息不丢失？从生产、存储、消费三段分析。

**答案：**
按链路三段：①生产端：发送确认机制——Kafka 用 acks=all（min.insync.replicas≥2）+ 重试 + 回调处理失败；RocketMQ 同步发送+broker 确认；本地消息表兜底"业务成功则消息必达"。②存储端：持久化与副本——Kafka 分区多副本+leader 落盘确认、RocketMQ 同步刷盘（SYNC_FLUSH）或主从同步复制；至少保证"消息进了多个副本才 ack"。③消费端：手动 ACK——业务处理成功才提交位点，失败重试（RocketMQ 重试队列/DLQ，Kafka 提交位点前异常则重启后重放），绝不用自动提交掩盖失败。外加监控：生产失败率、积压、DLQ 告警。

**解析：**
本地消息表方案细节：业务与消息记录同库同事务写入 → 定时任务/CDC 扫描未发送记录补偿投递 → 消费端幂等去重。它的优点是把"业务成功"与"消息投递"绑定在同一个本地事务，规避分布式事务。

Kafka 的 ISR 机制配合 acks=all：只有 ISR 内全部副本同步完成才算成功；unclean.leader.election=false 防止落后副本当选造成数据丢失。

消费端"先提交后处理"是丢消息最常见姿势——位点提交与业务处理的顺序必须正确。


### MQ-001-003 | ★★★★★

消息重复消费怎么处理？幂等的几种实现？

**答案：**
先立结论：MQ 至少一次投递下重复不可避免（生产重试、消费重平衡、重发补偿），正确姿势是"接受重复 + 消费端幂等"，而不是幻想"恰好一次"。幂等实现按强度：①唯一业务键约束——DB 唯一索引（订单号/消息 ID），冲突即重复，最可靠；②去重表/Redis setnx 记录已处理消息 ID，处理与记录要原子（同事务或 Lua）；③状态机——`update orders set status='PAID' where id=? and status='UNPAID'`，条件更新天然幂等；④版本号乐观锁。设计要点：消息体必须带全局唯一 ID（业务 ID 优先于消息 ID，跨 MQ 迁移稳定）。

**解析：**
"恰好一次"的真实语义：Kafka 的 EOS（幂等生产者+事务）只覆盖 Kafka 内部（生产-消费位点），跨系统（消息→DB）仍需业务幂等——这层窗户纸捅破是加分项。

去重表的窗口与清理：记录 TTL（如 7 天）+ 索引，防止无限膨胀；极端高并发用 Redis 前置挡一层，DB 唯一键兜底。

条件更新幂等是"免费"的：不新增存储，靠业务状态推进的不可逆性。


### MQ-001-004 | ★★★★☆

怎么保证消息顺序消费？

**答案：**
先问自己：是全局顺序还是业务局部顺序？全局顺序代价极高（单分区单线程，吞吐归一），绝大多数业务只需**同一业务实体的局部有序**——如同一订单的创建/支付/发货。实现三要素：①发送端按 key 路由：相同 key（订单号）进同一分区/队列（Kafka 按 key 哈希分区、RocketMQ MessageQueueSelector）；②分区内部天然 FIFO；③消费端同 key 串行：单分区单消费者，或消费线程按 key 哈希到内存队列串行处理。破坏顺序的两个高频坑：分区数变更导致 key 重分布（老消息在旧分区）；消费失败重试跳过后续消息（需阻塞该 key 队列或本地重试队列）。

**解析：**
消费端并行的正确姿势：拉取一批 → 按 key 分发到固定 worker 线程的本地队列（同 key 永远同线程）→ 各线程串行处理。既保序又并发。

Kafka rebalance 的顺序风险：消费组重平衡期间，同 key 可能被新旧消费者同时处理——需要业务幂等兜底（顺序与幂等永远成对出现）。

RocketMQ 的 MessageListenerOrderly：对队列加锁串行消费，broker 端还有全局锁保证迁移时的一致。


### MQ-001-005 | ★★★★☆

消息积压了怎么办？

**答案：**
应急三板斧：①定位瓶颈——消费端处理慢（下游依赖/慢 SQL/锁）还是并发不足；②水平扩容消费者——Kafka 消费者数 ≤ 分区数才有效，分区不够就"紧急扩分区"或用"临时 topic 转发"模式：写一个快速消费者把积压消息按 key 轮询转发到 10 倍分区的新 topic，再由扩容后的消费者集群并行处理；③降级保主——非核心消息延后/丢弃计数，保护系统整体。根治看原因：下游慢就优化下游或加异步批处理；消费逻辑重就拆分轻处理（先落地后加工）；持续超出消费能力说明容量规划问题，重新评估分区数与消费并行度。监控先行：积压量、消费速率、消息年龄（最早未消费消息的时间）三个指标必须常备。


### MQ-001-006 | ★★★★☆

Kafka 为什么快？

**答案：**
五个设计叠加：①顺序写：分区日志追加写文件，磁盘顺序写接近内存速度；②页缓存：读写都走 OS page cache，不自建缓存（JVM 内存省、重启缓存不丢、进程缓存与内核一致）；③零拷贝：消费者拉取用 sendfile，数据从页缓存直达网卡（K-OS-009）；④批量与压缩：生产者累积批量发送，支持 gzip/snappy/lz4/zstd 压缩，网络与存储摊薄；⑤分区并行：主题水平分区分散到多 broker，消费组并行消费。再补一句实现取向：Java 层尽量少 GC（紧凑二进制格式、批量缓冲），把复杂度交给内核。


### MQ-001-007 | ★★★☆☆

Kafka 的消费组与 Rebalance 机制？

**答案：**
消费组模型：组内消费者分摊全部分区（一个分区同时只归一个消费者），组间互不影响——这是"广播 vs 集群"的实现开关（换 group id 即广播）。Rebalance 触发三因：成员增减（上线/下线/心跳超时）、订阅主题分区数变化、订阅正则匹配到新 topic。过程：GroupCoordinator 选 leader 消费者 → leader 制定分配方案（Range/RoundRobin/Sticky/Cooperative-Sticky）→ 全组生效。代价要会讲：rebalance 期间整个组停止消费（Eager 协议 revoke 全部分区），秒级到分钟级，表现为消费暂停与可能的重复消费（未提交位点被重新拉取）。优化：会话/最大轮询间隔调优、消费逻辑避免长时间处理（max.poll.interval.ms 超时被踢）、用 Cooperative-Sticky 增量迁移减少影响面、静态成员资格（group.instance.id）避免重启触发。


### MQ-001-008 | ★★★☆☆

RocketMQ 和 Kafka 怎么选？

**答案：**
按功能与生态匹配：Kafka 定位分布式日志流平台——超高吞吐、生态（Connect/Streams/Flink 对接）最强，但功能性偏薄：消息重试要自建、没有延迟消息、事务限于 Kafka 内部。RocketMQ 定位业务消息中间件——天然支持事务消息、定时/延迟消息、消费重试与死信队列、消息轨迹、tag/SQL 过滤，金融业务友好；吞吐略低于 Kafka 但足够大多数业务。选型口诀：日志/大数据管道/流计算 → Kafka；业务解耦/交易配套（要事务消息、重试死信开箱即用）→ RocketMQ；轻量场景 RabbitMQ（路由灵活、管理成熟）或云托管产品。同公司尽量收敛到一种以降低运维与人才成本。


### MQ-001-009 | ★★☆☆☆

RabbitMQ 的核心模型和适用场景？

**答案：**
AMQP 模型三件套：Producer → Exchange（交换机：direct 精确路由、topic 通配符、fanout 广播、headers）→ 按 routing key 绑定到 Queue → Consumer 消费。特色能力：消息确认（publisher confirm + 消费 ack）、TTL + 死信交换机（DLX）组合实现延迟队列（经典 hack，5.8 后有官方 delayed-message 插件）、优先级队列、镜像/仲裁队列（quorum，Raft）高可用。适用：中小规模业务消息、复杂路由需求、管理控制台友好；吞吐不及 Kafka/RocketMQ（Erlang 实现单队列性能有限）。镜像是老方案有脑裂争议，新项目用 quorum 队列。


### MQ-001-010 | ★★★★☆

如何设计一个可靠的消息投递链路（端到端方案题）？

**答案：**
这是一道方案组装题，把 K-MQ-002/003/004 的要点串成闭环：①发送侧——业务与消息同事务落库（本地消息表）或事务消息；发送确认+失败重试；消息带全局业务 ID 与 traceId。②Broker 侧——多副本/同步刷盘按业务等级配置，监控 ISR/积压。③消费侧——手动 ACK、消费幂等（唯一键/状态机）、失败重试有上限进死信、死信人工/自动处理流程。④对账兜底——定时对账任务比对"业务事实表 vs 消息投递记录"，补偿丢失环节；这是最终一致系统的最后一道闸。⑤可观测——消息轨迹（每条消息的生产/存储/消费状态）、积压与年龄告警。答题亮点：主动说出"每一环都可能失败，方案=让失败可发现可补偿"，而不是零散技巧。


### MQ-001-011 | ★★★★☆

Kafka 高吞吐要素

Kafka 高吞吐的设计要素包括：

A. 分区日志顺序写磁盘
B. 大量使用随机写与随机读
C. 页缓存 + 零拷贝（sendfile）
D. 生产者批量发送与压缩

### MQ-001-012 | ★★★★★

消息不丢失三段

Kafka 生产端配置 `acks=all`、`min.insync.replicas=2`，其含义是：

A. 仅 leader 确认即成功
B. 消息须被 ISR 中至少 2 个副本（含 leader）写入才算发送成功
C. 无需确认
D. 消费者确认后生产才成功

**答案：** B

**解析：**
acks=all 要求 ISR 全部确认，配合 min.insync.replicas=2 防 ISR 收缩到 1 时"伪安全"；A 是 acks=1；C 是 acks=0；D 混淆了生产与消费确认。

生产三段防丢：acks=all+重试+回调处理。


### MQ-001-013 | ★★★★☆

RocketMQ 事务消息

RocketMQ 事务消息的"半消息"是指：

A. 只有一半内容的消息
B. 已发送到 broker 但对消费者暂不可见的消息，等待本地事务结果提交或回滚
C. 消费了一半的消息
D. 事务日志的一半

**答案：** B

**解析：**
半消息先落 broker 但不投递；本地事务成功则 commit 投递、失败则 rollback 删除；broker 定时回查未决事务；A/C/D 错。

半消息+本地事务+回查兜底=最终一致。


### MQ-001-014 | ★★★★☆

顺序消息三要素

实现"同一订单的消息有序消费"，需要的组合是：

A. 生产端按订单号（key）路由到同一分区/队列
B. Broker 分区内 FIFO
C. 消费端对同 key 串行处理（单线程或 key 哈希到固定线程）
D. 增加消费者数量即可

**答案：** A、B、C

**解析：**

### MQ-001-015 | ★★★★☆

积压处理

Kafka 消费组 8 个消费者消费 6 个分区发生积压，最优处置是：

A. 继续加消费者
B. 消费者数已达分区数上限，应优化消费逻辑/扩分区（配合临时转发 topic）
C. 换更快的网络

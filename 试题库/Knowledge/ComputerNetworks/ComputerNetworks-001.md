### ComputerNetworks-001-001 | ★★★★★

TCP 三次握手的过程和每一步的作用？为什么不能是两次？

**答案：**
过程：客户端发 SYN（seq=x）进入 SYN_SENT；服务端回 SYN+ACK（seq=y, ack=x+1）进入 SYN_RCVD；客户端再回 ACK（ack=y+1），双方进入 ESTABLISHED。每一步的作用：①客户端确认"我能发"；②服务端确认"我能收能发"，同时把自己的同步序列号发给客户端；③客户端确认"我能收到服务端的信息"，服务端由此确认"我发的包客户端能收到"。两次不行：服务端无法确认自己发的 SYN+ACK 被收到，且历史失效的 SYN（网络中迷路的旧连接请求）会让服务端单方面建立连接浪费资源——第三次 ACK 让客户端有机会拒绝旧连接。四次不必要：SYN 和 ACK 可以合并，没有额外信息量。

**解析：**
握手阶段交换的关键参数：MSS（最大段长）、窗口缩放因子、SACK 允许——这些在 SYN 中协商，影响后续传输效率。

初始序列号 ISN 是随机的：防止被猜测伪造（安全），且区分新旧连接的报文。半连接队列（SYN_RCVD）与全连接队列（accept 队列）的溢出是高并发服务端常见问题：syncookies 应对 SYN Flood，backlog 参数调全连接队列。

状态异常排查：大量 SYN_RECV=半连接攻击或网络丢包；大量 CLOSE_WAIT=对端关闭而本端应用没调用 close（代码 bug 高发区）。


### ComputerNetworks-001-002 | ★★★★★

四次挥手的过程？TIME_WAIT 为什么等 2MSL？

**答案：**
主动方 FIN → 对方 ACK（此时对方还能继续发数据，半关闭）→ 对方数据发完后 FIN → 主动方 ACK，主动方进入 TIME_WAIT 等 2MSL 后彻底关闭。等 2MSL 的两个原因：①保证最后一个 ACK 若丢失，对方重传 FIN 时我方还在，能重发 ACK，否则对方收不到确认无法关闭；②让本连接期间所有迷路报文在网络中自然消亡，避免污染下一个复用相同四元组的新连接。服务端大量 TIME_WAIT 的治理：连接复用（keep-alive/连接池）、SO_REUSEADDR、端口范围扩大；本质是短连接过多，根治靠长连接。

**解析：**
TIME_WAIT 出现在主动关闭方——为什么服务端会有大量 TIME_WAIT：服务端作为 HTTP 响应方主动断开（Connection: close 或超时），角色互换所致。1MSL 是报文最大存活时间（Linux 实现常取 30s，2MSL=60s）。

CLOSE_WAIT 堆积才是代码问题：收到 FIN 后应用一直不 close，通常是连接未释放的资源泄漏；TIME_WAIT 是协议设计内的正常态，除非量级影响端口。

另外：FIN 的 ACK 可以与对方 FIN 合并（三次挥手形态）在特定时序下出现，不改变语义。


### ComputerNetworks-001-003 | ★★★★★

TCP 如何保证可靠传输？滑动窗口和拥塞控制分别解决什么问题？

**答案：**
可靠机制四件套：校验和（差错检测）、序列号+确认应答（排序与去重）、超时重传+快速重传/SACK（丢包恢复）、滑动窗口（流量控制，按接收方处理能力发）。拥塞控制是另一维度——避免压垮网络：慢启动（指数增长）、拥塞避免（线性加性增）、快速重传+快速恢复（3 个重复 ACK 触发重传并减半而不是回到慢启动）。一句话区分：流量控制是"对端的接受能力"，拥塞控制是"网络的承载能力"。现代算法 Cubic（Linux 默认）基于丢包，BBR 基于带宽与 RTT 估计（不再把丢包当拥塞信号），高带宽长肥管道收益大。

**解析：**
窗口机制细节：发送窗口 = min(接收窗口 rwnd, 拥塞窗口 cwnd)；接收方通过 ACK 携带 rwnd 广播剩余缓冲；零窗口有探测机制防死锁。

重传效率演进：超时重传（RTO 基于 SRTT/RTTVAR 动态计算，Karn 算法不测重传包 RTT）→ 快速重传（3 个重复 ACK，不等超时）→ SACK（选择性确认，明确告知收到哪些区间，只重传真正丢失的段）→ D-SACK（报告重复收到的段，识别伪重传）。

Nagle 与延迟确认的相互作用可能造成小包延迟，长肥交互场景禁用 Nagle（TCP_NODELAY）——RPC/游戏场景常识。


### ComputerNetworks-001-004 | ★★★★★

TCP 和 UDP 的区别？各自适合什么场景？

**答案：**
TCP 面向连接、可靠有序、字节流（无消息边界→粘包问题）、有拥塞/流量控制、头部 20 字节起；UDP 无连接、尽最大努力交付、报文（保留消息边界）、头部 8 字节、支持广播组播。场景选择：TCP 用于网页/文件/数据库连接等要正确性的；UDP 用于实时音视频（可容忍丢包、重传无意义）、DNS（单问一答）、游戏帧同步、以及作为 QUIC 的底座——QUIC 在 UDP 上实现了连接迁移、0/1-RTT、多路复用无队头阻塞，是"应用层自定义可靠传输"的代表。

**解析：**
"字节流 vs 报文"是比"可靠 vs 不可靠"更本质的差异：TCP 收到的数据像水流，应用要自己切分消息；UDP 每次 recvfrom 是一个完整报文。

队头阻塞层次：TCP 层丢一个段，后面所有已到数据都要等重传（HTTP/2 over TCP 的痛点）；QUIC 流间独立重传缓解此问题——回答演进类问题时的串联点。

UDP 的"不可靠"也可以自己补：应用层加序列号+ACK+FEC（前向纠错），WebRTC 是完整案例。


### ComputerNetworks-001-005 | ★★★★☆

HTTP/1.0、1.1、2、3 的演进各自解决了什么问题？

**答案：**
1.0→1.1：默认长连接（keep-alive）复用 TCP、Host 头支持虚拟主机、Pipeline 引入但因队头阻塞没普及、缓存控制完善（Cache-Control/ETag）。1.1→2：二进制分帧替代文本、单连接多路复用（并发流不再排队）、头部压缩 HPACK、服务器推送、流优先级——但 TCP 层队头阻塞仍在（一个包丢全部流等待）。2→3：底层换 QUIC（UDP），连接建立 1-RTT/0-RTT、流之间独立重传消除传输层队头阻塞、连接迁移（换网不掐断）。一句话主线：从"文本协议复用连接"到"二进制多路复用"再到"换传输层根治队头阻塞"。

**解析：**
HTTP/2 的队头阻塞要说准：应用层多路复用解决了 1.1 的"响应必须按序"，但 TCP 字节流保证有序——任何一段丢失，内核必须等待重传后才能交付后续字节给所有流。3 的 QUIC 以流为单位独立确认重传，丢包只影响所在流。

HTTPS 与 2/3 的耦合：实践中 HTTP/2 几乎必配 TLS（浏览器仅 h2 over TLS），握手成本促成 QUIC 的 TLS1.3 内嵌与 0-RTT。

服务器推送在实际部署中效果不佳，已被 103 Early Hints 等替代思路淡化——答特性时可补这句体现版本敏感。


### ComputerNetworks-001-006 | ★★★★★

HTTPS 的握手过程？证书是怎么验证的？

**答案：**
TLS1.2 四次握手概要：ClientHello（随机数+支持的套件）→ ServerHello（选定套件+随机数+证书）→ 客户端验证证书后发送预主密钥（用服务器公钥加密）或 ECDHE 参数并更换密钥 → 双方用两个随机数+预主密钥/密钥协商材料算出会话密钥，互发 Finished 校验。TLS1.3 精简为 1-RTT（握手即协商密钥，ECDHE 为主，去掉 RSA 密钥交换实现前向安全），支持 0-RTT 恢复。证书验证：逐级验证证书链（网站证书→中间 CA→根 CA），根证书在本地信任库；检查签名（上级公钥验签）、有效期、域名匹配（SAN）、吊销状态（CRL/OCSP）。非对称加密只用于身份认证与密钥交换，数据传输用对称密钥（性能）。

**解析：**
为什么必须 ECDHE 才有前向安全：RSA 密钥交换中预主密钥用服务器长期私钥加密，私钥一旦泄露，历史抓包可全部解密；ECDHE 每次会话临时密钥对，私钥泄露也解不开历史流量。

中间人攻击的防线就是证书链+信任根：自签证书浏览器告警、企业代理需装根证书（抓包工具原理）。OCSP 装订（stapling）解决实时查询吊销列表的隐私与延迟问题。

密钥导出与加密套件示例：TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256——密钥交换 ECDHE、签名 RSA、对称 AES-GCM、摘要 SHA256。


### ComputerNetworks-001-007 | ★★★★☆

常见 HTTP 状态码的分类和典型代表？301 与 302、401 与 403 的区别？

**答案：**
五大类：1xx 信息、2xx 成功（200 OK、201 Created、204 No Content）、3xx 重定向/缓存（301 永久、302 临时、304 Not Modified 走缓存、307/308 保持原方法的临时/永久重定向）、4xx 客户端错误（400 参数错、401 未认证、403 已认证但无权限、404 不存在、429 限流）、5xx 服务端错误（500 内部错误、502 网关收到无效响应、503 不可用/过载、504 网关超时）。关键区分：301/302 会被客户端"换方法"的历史坑（301 POST 变 GET），规范用 307/308 保持方法；401 是"你是谁"（未登录），403 是"我知道你是谁但你不行"。

**解析：**
304 的前提是缓存协商：If-None-Match（ETag）/If-Modified-Since（Last-Modified）与响应头的对应关系；强缓存（Cache-Control max-age）不发起请求，协商缓存才产生 304——两级缓存机制是高频追问。

502/504 是网关视角：502 上游崩溃或返回非法响应，504 上游超时——排障时区分是"上游挂了"还是"上游慢了"。

429 与限流配套 Retry-After 头，客户端指数退避的依据（K-AIENG-004 呼应）。


### ComputerNetworks-001-008 | ★★★★☆

Cookie、Session、Token（JWT）的区别与选择？

**答案：**
Cookie 是浏览器侧的存储与自动携带机制（域名、路径、过期、HttpOnly、Secure、SameSite 属性）；Session 是服务端会话状态，Cookie 只存 session id；JWT 是自包含签名的令牌（Header.Payload.Signature），服务端无状态、签名保证不可篡改。对比核心：Session 有状态——服务端存储、天然可吊销、水平扩展要共享存储；JWT 无状态——扩展友好、跨服务自校验，但无法主动作废（只能短有效期+refresh token 或黑名单，黑名单又变回有状态）。现代实践：浏览器 Web 常用 HttpOnly Cookie+Session/短 JWT；服务间/移动端用 Bearer JWT；敏感场景 access token 短效+refresh 轮换。

**解析：**
JWT 三段结构：Header（算法）+Payload（claims：sub/exp/iat/自定义）+Signature（HMAC 或 RSA/ECDSA）。注意 Payload 只是 Base64URL 编码不是加密，不能放敏感信息。算法混淆攻击（none/HS-RS 混用）是经典安全点，校验端要白名单算法。

CSRF 与 Cookie：自动携带是双刃剑，SameSite=Lax/Strict + CSRF Token 防；JWT 放 localStorage 则有 XSS 风险——"Cookie+CSRF 防"vs"localStorage+XSS 防"的取舍要能讲。

分布式 Session：Spring Session 存 Redis，粘性问题消失，代价是每次会话访问一次 Redis。

### ComputerNetworks-001-010 | ★★★☆☆

DNS 解析的完整过程？递归查询和迭代查询的区别？

**答案：**
客户端 → 本地 DNS（递归模式：你等着，我负责查到底）；本地 DNS → 根域名服务器（迭代模式：我不替你查，但告诉你下一站）→ 顶级域（.com）→ 权威域名服务器 → 返回 IP；沿途逐级缓存（受 TTL 控制）。递归/迭代的区别在于"谁负责跑腿"：客户端对本地 DNS 是递归，本地 DNS 对上游是迭代。工程要点：TTL 决定变更生效速度（切换前调小 TTL）；负载调度可用 DNS 轮询/地理调度；DNS 劫持与污染的防护（DoH/DoT 加密 DNS）。

**解析：**
记录类型顺带掌握：A/AAAA（IP）、CNAME（别名链，CDN 接入核心）、NS（权威服务器）、MX（邮件）、TXT（验证/SPF）。CDN 工作原理题的本质就是 DNS+CNAME：权威 DNS 返回 CNAME 指向 CDN 调度域，CDN 权威按用户本地 DNS 的位置/负载返回最优边缘节点 IP。

缓存层级：浏览器→操作系统→本地 DNS（运营商/公共 DNS 223.5.5.5 等）。排查"域名不生效"先查每层缓存与 TTL。


### ComputerNetworks-001-011 | ★★★★☆

TCP 粘包拆包是怎么回事？怎么解决？

**答案：**
先纠正概念："粘包"不是 TCP 的 bug，而是 TCP 字节流语义的必然——它只保证字节有序到达，不维护应用层消息边界；一次 send 可能被拆成多段到达（拆包），多次 send 也可能合并到达（粘包），受 MSS、Nagle、接收缓冲区影响。UDP 有边界所以无此问题。解决方案四类：①定长消息（浪费、少用）；②分隔符（如 \n，注意内容转义）；③长度前缀（消息头带 body 长度，最通用，Netty LengthFieldBasedFrameDecoder）；④应用层协议自带边界（HTTP 的 Content-Length/chunked）。本质：消息边界是应用层协议的职责。

**解析：**
长度前缀的细节：长度字段本身占几字节、字节序（网络序大端）、是否含头；半包处理需要"头够不够长→body 够不够长"的状态机。Netty 三件套：FrameDecoder（切消息）→ Decoder（字节→对象）→ Handler（业务）。

HTTP 的两种方案都存在：Content-Length 精确长度 vs Transfer-Encoding: chunked 分块（流式，长度未知场景）；两者不可同时用。


### ComputerNetworks-001-012 | ★★★★☆

IO 多路复用是什么？select/poll/epoll 的区别？

**答案：**
IO 多路复用=一个线程监听一批 fd，谁就绪处理谁，避免"每连接一线程"的开销。三代对比：select 用固定大小位图（默认 1024 上限）每次调用全量拷贝到内核并线性扫描；poll 用 pollfd 数组突破数量限制但仍全量拷贝+O(n) 扫描；epoll 用红黑树管理 fd + 就绪链表回调：epoll_ctl 注册一次、epoll_wait 只返回就绪列表，复杂度 O(1)/就绪事件，海量连接下优势碾压。还有 LT（水平触发：没处理完会反复通知）与 ET（边缘触发：只通知一次，必须一次读/写到 EAGAIN，配合非阻塞 fd）。Reactor 模式是其工程化封装：Netty 的 Boss/Worker 线程模型、Redis 的事件循环都基于它。

**解析：**
epoll 高效的三个机制要点：①红黑树避免每次传入全量 fd；②设备驱动就绪时回调把 fd 挂入就绪链表（事件驱动而非轮询）；③mmap？——常见错误说法，epoll 并不依赖 mmap 共享内存（内核与用户态通过 epoll_wait 拷贝就绪事件，量很小），这个以讹传讹的点说对了反而加分。

LT vs ET 取舍：LT 编码简单安全（默认）；ET 性能略高但要循环读写到 EAGAIN，Nginx 用 ET、Redis 用 LT。

连接数大但活跃少（长连接推送、IM）是 epoll 优势场景；高吞吐低连接数 select 也够。


### ComputerNetworks-001-013 | ★★★☆☆

GET 和 POST 的区别？语义上的差异比"长度限制"更重要？

**答案：**
语义差异（本质）：GET 是安全幂等的读取，参数在 URL 查询串，可被缓存/收藏/预取；POST 是提交处理，数据在 body，默认不缓存不幂等。技术差异：GET body 语义上不应有数据（多数服务端忽略），URL 长度受浏览器/服务器限制（几 KB 级）；POST body 理论无限制。工程红线：写操作绝不用 GET（爬虫预取/链接预览会误触发）、敏感数据不进 URL（日志/历史记录泄露）。RESTful 语义映射：GET 查、POST 建、PUT 全量更新（幂等）、DELETE 删（幂等）、PATCH 部分 update。


### ComputerNetworks-001-014 | ★★★☆☆

CDN 的原理是什么？回源和缓存策略怎么工作？

**答案：**
CDN=内容分发网络，核心是"就近返回+边缘缓存"。接入：域名 CNAME 到 CDN 调度域，DNS 调度按用户 LocalDNS 位置返回最优边缘节点 IP（K-NET-010 的应用）；命中：边缘节点有缓存直接返回（X-Cache: HIT）；未命中：按层级回源（边缘→区域中心→源站），取回同时缓存在沿途节点。缓存有效性继承源站响应头（Cache-Control/Expires/ETag），CDN 控制台可强制刷新（purge）与预热（push）。动态内容不缓存或走动态加速（链路优化/协议加速）。价值：降低延迟、抵御流量峰值（静态部分不再打源站）、节约带宽成本。


### ComputerNetworks-001-015 | ★★★☆☆

OSI 七层与 TCP/IP 四层模型？每层的典型协议与设备？

**答案：**
OSI 七层自下而上：物理（比特，网线/光纤/集线器）、数据链路（帧，以太网协议，交换机、MAC 地址）、网络（包，IP/ICMP/ARP，路由器、IP 地址）、传输（段，TCP/UDP，端口）、会话、表示、应用（HTTP/DNS/SMTP）。工程常用 TCP/IP 四层：网络接口、网络、传输、应用——OSI 的会话/表示并入了应用层。分层的价值：各层职责独立、协议可替换（同一张 IP 网上跑无数应用协议）。数据封装：发送端逐层加头，接收端逐层解头。常见对照：四层负载均衡（LVS，只看 IP/端口转发）vs 七层负载均衡（Nginx，解析 HTTP 内容路由）。


### ComputerNetworks-001-016 | ★★★☆☆

常见网络攻击与基础防御？SYN Flood、DDoS、中间人、DNS 劫持怎么防？

**答案：**
四类高频：①SYN Flood：伪造 SYN 耗尽半连接队列——syncookies、缩超时、网关清洗；②DDoS：分布式流量/应用层攻击——高防 IP/CDN 吸收、弹性带宽、限流与人机校验（应用层 CC）；③中间人（MITM）：劫持链路窃听篡改——TLS 全站加密、HSTS 强制、证书校验不放松、内网 mTLS；④DNS 劫持/污染：篡改解析——DNSSEC、DoH/DoT、HTTPDNS。通用原则：加密（TLS）、认证（证书/签名）、冗余与清洗（CDN/高防）、监控告警（流量基线突变）。回答时体现"攻击原理一句话+防御一句话"的对仗结构。


### ComputerNetworks-001-017 | ★★★★☆

TCP 的 keep-alive 与 HTTP 的 Keep-Alive 是一回事吗

**答案：**
不是。TCP keep-alive 是内核机制：连接空闲超过阈值（默认 2 小时）后发探测包，检测"对端是否还活着"，用于清理死连接，参数系统级、粒度粗；HTTP Keep-Alive 是应用层"长连接复用"：一个 TCP 连接上连续收发多个 HTTP 请求/响应，避免每次都握手挥手，由 Connection: keep-alive/keep_alive_timeout 控制。网关/NAT 的连接回收靠应用层心跳（如自定义 ping 帧、WebSocket ping）更及时，因为 TCP 默认探测太迟钝。

**解析：**
移动网络下 NAT 表项几分钟就回收空闲映射，服务端以为连接还在、发数据黑洞——所以 IM/推送必须在应用层定时心跳保活。HTTP/1.1 默认长连接；连接池上限、服务端 keep_alive_timeout 短于客户端复用间隔会收到 RST。


### ComputerNetworks-001-018 | ★★★★☆

从 ping 不通到"能连但很慢"：网络排查分层

**答案：**
四步分层：①连通性：ping/traceroute 看路径与丢包起点（ICMP 被禁时用 tcping/端口探测）；②端口层：telnet/nc 测端口、云安全组与防火墙放行；③协议层：curl -v 看握手/DNS/TLS 各阶段耗时，DNS 慢 vs TCP 慢 vs TLS 慢定位不同；④应用层：抓包 tcpdump + 时序分析（重传、零窗口、RST）。慢的常见根因：MTU 黑洞（大包丢弃小包通）、DNS 解析慢、跨运营商绕路、TCP 重传率高。

**解析：**
MTU 问题特征：小包 ssh 正常、大文件传不动——`ping -s 1472 -M do` 探测分界。重传定位：ss -i 看 retrans、nstat 的 RetransSegs 增速。容器环境加一层：Service/网络策略/CNI。排查的价值不在工具罗列而在"从下层往上逐层排除"的秩序。

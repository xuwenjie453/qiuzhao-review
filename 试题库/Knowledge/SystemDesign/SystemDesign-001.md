### SystemDesign-001-001 | ★★★★☆

设计一个短链接服务

**答案：**
先澄清需求（量级、是否需要自定义短码、有效期、统计），核心两件事：**发号**与**跳转**。发号方案：①自增 ID → 62 进制编码（6 位可表达 560 亿），趋势递增但可被遍历猜测，可加固定混淆位；②号段/雪花发号器分布式扩展；③哈希+冲突检测（MurmurHash 截断 + 唯一索引冲突重试）。存储：短码为主键的 KV（DB+缓存），跳转接口 301（永久，浏览器缓存省流量）vs 302（临时，可统计点击）——要统计就用 302。读多写少：Redis 缓存短码映射 + 布隆过滤器挡恶意不存在短码。加分项：防遍历（混淆）、过期与回收、热点短码缓存击穿防护、地域调度。


### SystemDesign-001-002 | ★★★★☆

设计一个秒杀系统

**答案：**
设计主线是"层层漏斗削减流量，库存原子扣减，异步化履约"：①前端/接入层：按钮防重、静态化页面走 CDN、答题/滑块打散请求、网关限流（按用户/IP/QPS）；②库存扣减：Redis Lua 原子预扣（check+decr 原子，预扣成功即"资格锁定"），拒绝超卖；③异步落库：预扣成功发 MQ，订单服务消费创建订单、DB 层 `update stock set n=n-1 where id=? and n>0` 终态兜底防超卖；④一致性：Redis 与 DB 对账修复、支付超时回补库存；⑤防护：防刷（风控）、热点隔离（独立部署）、降级预案（直接售罄页）。正确性底线：不超卖（硬约束）、少卖可修复（对账回补）。


### SystemDesign-001-003 | ★★★☆☆

设计一个消息推送系统（App/长连接推送）

**答案：**
核心结构：接入层（长连接网关，百万 TCP 连接，Netty+epoll，K-NET-012）、路由层（用户 ID→所在网关节点的映射，Redis 存储）、消息队列解耦业务与推送、离线消息存储（不在线时落库，上线拉取）。关键问题四个：①连接保持——心跳（智能间隔）、断线重连（指数退避+随机）；②可靠投递——seq 序号+ACK，未确认重发，客户端去重；③海量连接——单机 10 万级连接靠事件驱动与内存控制，水平扩容靠路由层；④推送 vs 轮询——推送实时省电，弱网退化为轮询兜底。移动端现实：厂商通道（APNs/FCM/厂商推送）保活兜底，自建长连接承载在线消息。IM 类再叠加以写扩散/读扩散的 timeline 设计。


### SystemDesign-001-004 | ★★★☆☆

设计一个延时任务系统（千万级定时任务）

**答案：**
需求澄清后（量级、精度、持久性、是否可取消），分层方案：①存储层——任务持久化（DB/Redis ZSET/专用日志），保证进程重启不丢；②调度层——时间轮（HashedWheelTimer：环形数组+指针 tick，插入/取消 O(1)，精度=tick 时长）承载内存到期任务；多层时间轮（时分秒层级+降级传递）支持长延迟；③触发层——到期任务投递到 MQ 由消费者执行（调度与执行分离，失败重试靠 MQ 可靠性）；④补偿——扫描器定期扫存储层兜底（时间轮是快路径，扫描是正确性兜底，两者以"已执行标记"去重）。规模路径：小量用 Redis ZSET 轮询（K-REDIS-011）；海量高精度用多级时间轮集群（每个时间轮节点持久化+分片）。


### SystemDesign-001-005 | ★★★☆☆

设计一个 Feed 流系统

**答案：**
两种基线：推模式（写扩散）——发布时把消息写入所有粉丝的收件箱（inbox，Redis ZSET 按 id/时间排序），读时只查自己收件箱，读快写重，适合粉丝量有限的互动关系；拉模式（读扩散）——只写自己的发件箱（outbox），读时聚合关注列表逐个拉取合并排序，写快读重，适合大 V/单向关注。工程标配是**推拉结合**：普通用户发布推给在线/活跃粉丝收件箱；大 V 不推（或只推活跃粉），粉丝读时聚合拉取大 V outbox + 自己 inbox 归并。配套：inbox 容量裁剪（只存最近 N 条）、去重（全局 ID）、分页（游标：按 id 翻页）、缓存未命中回源重建。


### SystemDesign-001-006 | ★★★☆☆

设计一个对账系统

**答案：**
对账是最终一致体系的"最后防线"。结构三步：①数据准备——拉取双方账单（渠道方文件/API + 我方流水），标准化格式，文件校验（条数/金额合计/哈希）；②核对——按业务单号+金额匹配（先精确、后 T+1 模糊窗），输出三类差异：单边账（一方有另一方无）、金额不一致、状态不一致；长期账（跨日未达）登记在途；③差错处理——自动处理可闭环的（掉单补单、状态同步），复杂差异转人工工单，全程留痕可审计。工程要点：对账任务本身要幂等可重跑（K-DIST-009）、按机构/日期分片并行、差异账单有生命周期（T+1 次日重核→转人工→销账）、所有修复动作可追溯（审计合规是金融硬要求）。

### OperatingSystems-001-001 | ★★★★★

进程、线程、协程的区别？上下文切换的成本？

**答案：**
进程是资源分配的基本单位（独立地址空间、fd 表）；线程是 CPU 调度的基本单位，同进程内线程共享地址空间与资源，只私有栈、寄存器、TLS；协程是用户态调度的轻量执行流，切换不进内核，成本是纳秒~微秒级。上下文切换成本排序：进程 > 线程 > 协程。进程切换要换页表（CR3）、刷 TLB 相关项；线程切换同进程内不换地址空间，只换寄存器与栈指针；协程只保存恢复少量寄存器。数量的工程含义：线程创建受内存（栈）与调度开销限制，几千即重；协程可百万级——这正是 JDK 虚拟线程（K-JUC-018）把"阻塞 IO 便宜化"的原理。

**解析：**
切换时机：时间片用尽、更高优先级抢占、阻塞式系统调用/IO、锁等待。切换成本两块：直接成本（保存恢复寄存器、内核调度决策）与间接成本（缓存/TLB 失效后的"缓存重热"，往往比直接成本更大）。

Linux 线程实现：pthread 是 NPTL，内核视角线程即 task_struct，轻量进程（clone 带 CLONE_VM 等标志）——"线程=共享资源的进程"是 Linux 的设计观。

调度单位事实：Linux 对线程调度（1:1 模型），Go/JVM 虚拟线程是 M:N 用户态调度（JVM 虚拟线程挂载在载体线程上）。


### OperatingSystems-001-002 | ★★★★☆

进程间通信（IPC）有哪些方式？各自的适用场景？

**答案：**
主流六种：管道（匿名 pipe：父子进程字节流；命名 FIFO：无亲缘也可）、消息队列（内核消息列表，按类型收）、共享内存（最快，同一物理页映射进多进程，需配信号量/互斥锁同步）、信号量（同步互斥原语，常与共享内存搭配）、信号（异步事件通知：SIGKILL/SIGTERM/SIGUSR）、Socket（跨主机通用，Unix domain socket 本机高效）。选型直觉：大数据量高频交换→共享内存+信号量；命令/状态传递→管道/消息队列；跨机→Socket；进程控制→信号。

**解析：**
为什么共享内存最快：其他方式都要"用户态→内核态→用户态"两次拷贝，共享内存直接映射同块物理内存，零拷贝（同步仍需自己解决）。这就是"最快 IPC"答案的原理支撑。

信号机制要点：异步、无数据载荷（编号+可选 sigqueue 值）、不可排队（标准信号可能合并）；SIGKILL/SIGSTOP 不能被捕获——优雅停机监听 SIGTERM 做清理是容器时代必会点（Docker stop 发 SIGTERM，超时 SIGKILL）。

Android Binder、Windows 的 LPC 是工程界 IPC 的其他实现，可提一句展示广度。


### OperatingSystems-001-003 | ★★★★☆

线程同步有哪些手段？互斥锁、自旋锁、读写锁、条件变量各自适用场景？

**答案：**
四类原语按场景：互斥锁（mutex）：临界区较长或可能睡眠时，阻塞等待不占 CPU；自旋锁：临界区极短且持锁者很快释放，忙等避免上下文切换，单核/长临界区是灾难；读写锁：读多写少，读共享写独占；条件变量：等待"某条件成立"，必须与互斥锁配合（while 循环判断，防虚假唤醒）。底层共通：都要原子性支撑（硬件 CAS/测试并设置指令），用户态 futex 机制——无竞争时纯用户态，有竞争才陷内核挂起，这是 Linux 高效锁的关键设计。Java 层的对应：synchronized/ReentrantLock（K-JUC-002/004）、读写锁、Condition。

**解析：**
futex 流程：用户态先 CAS 尝试，成功则零系统调用；失败进 futex_wait 陷入内核挂到等待队列；解锁方 futex_wake 唤醒。这一段是"为什么 Linux 锁快"的标准答案。

优先级反转问题（加分项）：低优先级持锁、高优先级等待、中优先级抢占低优先级造成事实反转——解决方案优先级继承。火星探路者事故是经典案例，一句带过即可。


### OperatingSystems-001-004 | ★★★☆☆

常见的进程调度算法有哪些？Linux 用什么？

**答案：**
经典算法谱系：FCFS 先来先服务（简单，护航效应）、SJF 短作业优先（平均等待最优但需预知时长、长作业饥饿）、RR 时间片轮转（公平响应，交互友好）、优先级调度（可抢占/不可抢占，低优先级饥饿→老化 aging 缓解）、多级反馈队列（融合前几种，Unix 传统）。Linux 现行 CFS（完全公平调度器，2.6.23 起）：不用固定时间片，按虚拟运行时间 vruntime 公平分配 CPU——跑得少的优先；用红黑树按 vruntime 组织，选最左节点 O(logN)；nice 值映射权重而非绝对优先级；新版本 EEVDF（6.6+）在公平基础上加入时延敏感度，可提一句体现时效。实时任务另有 FIFO/RR 两个实时调度类，优先级高于普通类。

**解析：**
CFS 关键量：vruntime += 实际运行时间 × (NICE0 权重/该任务权重)，实现"权重按比例分 CPU"；睡眠者补偿（醒来 vruntime 对齐公平线防饿）。目标延迟概念：所有可运行任务在一个调度周期内至少跑一轮。

多级反馈队列仍是考试/教学高频：多队列+时间片递增+优先级降级，回答时能给"新任务进高优队列，用完片降级，IO 型停留高层"的动态即可。


### OperatingSystems-001-005 | ★★★★☆

死锁的四个必要条件？处理策略有哪些？

**答案：**
四个必要条件：互斥、占有且等待、不可抢占、循环等待——同时成立才可能死锁，破坏任一即可预防：一次性申请所有资源（破坏占有且等待，浪费）、允许抢占（破坏不可抢占，复杂）、资源有序分配（破坏循环等待，最常用）。处理策略分四级：预防（静态规则）、避免（动态判断分配是否安全——银行家算法）、检测+解除（资源分配图检测，剥夺/回滚/杀进程）、鸵鸟策略（多数通用系统默认：假设少发生，出了再处理）。Java/数据库层面的具体落地见 K-JUC-014/K-MYSQL-010，本题重点在 OS 理论框架。

**解析：**
银行家算法核心：每次分配前模拟"最坏情况下（每个进程都还要最大资源）能否找到安全序列"，安全则分配。能讲清 Need ≤ Available 判断与安全序列搜索即可，不必展开矩阵演算细节。

资源分配图：进程→资源请求边，资源→进程分配边；死锁充要条件是图中存在"每类单实例资源的循环"（多实例循环只是必要条件）——这句体现深度。

活锁与饥饿的区分（常见追问）：活锁是互相礼让不停重试不前进；饥饿是调度/优先级导致长期得不到资源，系统仍在推进。


### OperatingSystems-001-006 | ★★★★★

虚拟内存是什么？页表和缺页中断怎么工作？

**答案：**
虚拟内存给每个进程独立连续的虚拟地址空间，由 MMU 通过页表把虚拟页映射到物理页帧，实现三件事：进程隔离与保护、按需加载（访问才调入）、内存超售（物理不足时换出到 swap/文件页）。页表多级结构（x86-64 四级/五级）避免单表巨大；TLB 缓存最近翻译结果，命中则零开销翻译。缺页中断流程：CPU 访问的页不在物理内存 → 页故障异常 → 内核检查合法性 → 空闲帧不够则页面置换（LRU 类）→ 从磁盘调入 → 更新页表 → 重执行指令。写时复制（fork）也建立在这套机制上：父子先共享物理页标只读，写时触发缺页才真正复制。

**解析：**
多级页表的动机：48 位地址空间单级页表需 TB 级内存；四级（PGD→PUD→PMD→PTE）每级 9 位索引，未使用的区域无需建下级表。

大页（huge page）：2MB/1GB 页减少页表项与 TLB miss，数据库/JVM 大堆受益；透明大页 THP 对延迟型应用有争议（合并停顿），Redis 官方建议关闭——工程细节加分点。

换页代价量级：内存命中纳秒级，缺页从磁盘调入毫秒级，差 5 个数量级——这就是"内存 swap 抖动比慢查询可怕"的原理。


### OperatingSystems-001-007 | ★★★☆☆

页面置换算法有哪些？LRU 在内核里怎么实现？

**答案：**
经典算法：FIFO（简单但有 Belady 异常：页框增多缺页可能反增）、OPT（理论最优，需未来信息，做基准）、LRU（利用局部性，硬件完全实现贵）、Clock/第二次机会（LRU 的近似：环形链表+访问位，指针扫到访问位 1 就清零跳过，为 0 才置换）、LFU（频率，对突发不敏感有历史包袱）。内核实现都是近似：Linux 的双链 active/inactive（本质是增强版 Clock，访问位+引用计数，文件页与匿名页分开回收）；Redis 的"LRU"是抽样近似（K-REDIS-004 同源思想）。考试层面要能手算 FIFO/LRU/Clock 的缺页序列。

**解析：**
Clock 算法手工演算方法（面试常考）：页框排成环，每页一位 R；缺页时指针前进，R=1 清 0 跳过，R=0 淘汰换新页并 R=0。相比纯 LRU 免去每次访问更新链表的硬件成本——访问位由 MMU 自动置位，这是"近似可行"的硬件基础。

工作集模型：进程在某时间窗口实际访问页集合，分配页框 ≥ 工作集才不抖动（thrashing，缺页率飙升 CPU 忙于换页）。


### OperatingSystems-001-008 | ★★★★☆

用户态和内核态是什么？什么时候切换？系统调用的过程？

**答案：**
CPU 分级保护：内核态（ring0）可执行特权指令、访问全部内存；用户态（ring3）受限，防止应用破坏系统。切换触发三类：系统调用（主动：read/write/fork）、中断（硬件：时钟、网卡）、异常（缺页、除零）。系统调用过程：用户态把系统调用号与参数放入约定位置 → 触发陷入指令（syscall）→ CPU 切内核态、切内核栈 → 内核查系统调用表执行 → 结果返回、恢复用户态。成本要点：模式切换本身（保存/恢复上下文、TLB/流水线影响）+ 安全检查，微秒级以下但高频调用累积可观——这正是"read 一字节一万次"与 vDSO（gettimeofday 等映射到用户态免切换）、io_uring（批量异步提交减少陷入）存在的动机。

**解析：**
切换类型区分（高频追问）：系统调用是"同进程内的模式切换"，进程切换是"调度切换"，二者不同——前者没有地址空间切换。中断与异常也是模式切换入口。

用户态/内核态各自栈：每线程一个内核栈（8~16KB），系统调用时切换；这解释了"线程多了内核栈内存也涨"。

零拷贝语境：sendfile 把"read（用户态来回）+write"合并为内核内直接转发，减少模式切换与拷贝（K-NET-012 呼应）。


### OperatingSystems-001-009 | ★★★☆☆

零拷贝是什么？sendfile/mmap 怎么减少拷贝？

**答案：**
传统"读文件发网络"四次拷贝+四次切换：read 把磁盘数据经 DMA→页缓存→用户缓冲区（第一次 CPU 拷贝），write 再用户缓冲区→socket 缓冲区→网卡（DMA）。零拷贝目标是消除"页缓存↔用户区"的冗余 CPU 拷贝：sendfile 一次调用完成文件到 socket 的内核内传输（数据不进用户态）；带 DMA gather 的网卡更进一步页缓存仅传描述符；mmap 把文件映射进用户地址空间，省 read 的显式拷贝但仍要 write 拷贝到 socket——适合需要"读出来改一改"的场景。收益排序：sendfile(+gather) > mmap+write > 传统。应用：Kafka/ nginx 静态文件 sendfile，RocketMQ 用 mmap。


### OperatingSystems-001-010 | ★★★★☆

五种 IO 模型是什么？阻塞、非阻塞、同步、异步怎么区分？

**答案：**
Unix 五种：阻塞 IO（read 一直等）、非阻塞 IO（轮询 read，没数据返回 EWOULDBLOCK）、IO 多路复用（select/poll/epoll 等"多个 fd 中任何一个就绪"，就绪后仍同步 read）、信号驱动（SIGIO 通知，实际少用）、异步 IO（aio/io_uring：内核完成数据拷贝后通知，全程无阻塞）。区分两对概念：阻塞/非阻塞看"调用立即返回还是等待"；同步/异步看"数据拷贝阶段由谁完成"——前四种的数据拷贝都由线程自己 read 完成（同步），只有真正异步 IO 由内核拷完再通知（异步）。所以 epoll 严格说是"同步非阻塞"模型——这个纠偏点很能体现理解。

**解析：**
为什么"epoll 也算同步"重要：它只解决"等多路事件"的等待问题，数据从内核到用户仍要线程主动拷；aio/io_uring 才是"两阶段都不用你管"。Windows IOCP 是成熟异步模型，Linux io_uring（5.1+）补齐了这块。

协程与 IO 模型的关系：Go/JVM 虚拟线程把"同步阻塞写法"翻译到底层事件驱动——应用视角同步，内核视角多路复用，理解这点能串起 K-JUC-018。


### OperatingSystems-001-011 | ★★★☆☆

fork 的原理？写时复制（COW）是怎么回事？

**答案：**
fork 创建子进程：复制进程描述符、页表等元数据，但**不立即复制物理内存页**——父子页表指向同一物理页且标为只读，即写时复制：任何一方写时触发缺页异常，内核才分配新页复制内容。收益：创建快（O(页表)而非 O(内存)）、省内存、支持"fork+exec"模式（exec 换程序映像，之前的复制本就多余）。Redis RDB 的 bgsave、ZGC/G1 的并发阶段都依赖 fork+COW——代价是 fork 瞬间复制页表的停顿与 COW 期间内存峰值（K-REDIS-003）。vfork 是更激进的"共享地址空间直到 exec"的历史优化；现代推荐 posix_spawn。


### OperatingSystems-001-012 | ★★★☆☆

内存泄漏和内存溢出在 OS 层面怎么看？和 JVM 层面的关系？

**答案：**
层次区分：JVM 堆内泄漏用 jmap/MAT（K-JVM-008）；OS 层面看的是进程 RSS 持续增长，来源可能是堆外内存（DirectByteBuffer/Netty）、元空间、线程栈膨胀、native 库泄漏（JNI）、glibc malloc 碎片（arena 不归还）。排查工具链：top/ps 看 RSS/VSZ → smaps/pmap 按映射段定位增长区（anon 段？堆？栈？）→ jemalloc/gperftools 的堆采样或 valgrind（离线）→ pmap -x 对比两次快照差分。容器内还要看 cgroup 内存计费口径：page cache 也计入 usage，文件读多会"虚高"。Java 进程内存=堆+元空间+直接内存+线程栈+代码缓存+native，总量要对着容器 limit 校准（K-JVM-011）。


### OperatingSystems-001-013 | ★★★☆☆

Linux 下怎么判断磁盘 IO 是不是瓶颈？

**答案：**
工具与指标：iostat -x 关键列——%util（设备忙时占比，机械盘接近 100% 即饱和；SSD/多队列设备参考意义弱）、await/r_await/w_await（IO 平均延迟，ms 级以内健康）、svctm（已废弃）、aqu-sz（队列深度）；vmstat 的 b 列（阻塞在 IO 的进程数）与 wa（iowait CPU 占比）。应用侧证据：请求延迟毛刺与 IO 曲线相关、数据库 binlog 刷盘延迟。排查链路：先 iostat 确认设备忙与延迟 → iotop/pidstat -d 找到具体进程 → strace/blktrace 下钻到系统调用与块层 → 判断是容量（换盘/扩容）、随机化严重（优化访问模式/加缓存）还是调度干扰（io scheduler、ionice）。云盘注意：虚化后的 %util 失真，以 await 与云监控 IOPS/吞吐上限为准。


### OperatingSystems-001-014 | ★★☆☆☆

软中断、硬中断是什么？网络收包的大致流程？

**答案：**
硬中断：硬件（网卡/时钟/磁盘）触发，打断 CPU 执行中断处理程序——必须快进快出，只做"取走关键数据+标记"。软中断（softirq）：把耗时的后续处理（协议栈解析、socket 唤醒）延迟到下半部执行，ksoftirqd 内核线程兜底；网络收包的 NET_RX/NET_TX 就是最繁忙的软中断。NAPI 的思想：中断+轮询混合——包少时中断省 CPU，风暴时切轮询减少中断开销。高流量机器调优：RPS/RFS 多队列分散软中断到多核、调整中断亲和性、监控 /proc/softirqs 与 si 列。一个 CPU 被软中断打满的典型现象：单核 100% 其余空闲——负载不均是经典排查入口。


### OperatingSystems-001-015 | ★★★☆☆

top 里 load average 怎么理解？CPU 使用率和负载的区别？

**答案：**
load average 是"可运行任务数 + 不可中断睡眠任务数（D 状态）"的指数加权平均（1/5/15 分钟）——注意 Linux 把 D 状态计入，所以 NFS/存储卡顿时 load 飙高但 CPU 使用率可能不高。经验判读：load ≈ 核数为饱和线，持续高于核数说明排队；但必须结合 CPU/IO 维度分解：us（用户态）、sy（内核态）、wa（iowait）、si（软中断）——us 高查业务热点，sy 高查系统调用/锁，wa 高查存储，si 高查网络/软中断。工具链：vmstat（r/b/cs/us/sy/wa）、mpstat -P ALL（核间不均）、pidstat -u（进程维度）。"load 高但 CPU 空闲"的经典答案就是 D 状态任务在等 IO/NFS。


### OperatingSystems-001-016 | ★★★★☆

Linux 下的零拷贝家族：sendfile/splice/mmap 分别适合谁

**答案：**
sendfile：文件→socket 的内核内直达，Kafka 消费、Nginx 静态文件的标配；splice：任意两个 fd 之间经管道搬运（不落用户态），适合 socket↔socket 转发；mmap+write：文件映射进用户地址空间，适合需要"读出来加工"的场景（修改、随机访问），比 sendfile 多一次用户态拷贝。Java 对应：FileChannel.transferTo=sendfile、MappedByteBuffer=mmap。共同本质：减少"内核缓冲区↔用户缓冲区"的冗余 CPU 拷贝与上下文切换。

**解析：**
传统读发 4 次拷贝 4 次切换（K-OS-009）；sendfile（+DMA gather）可压到 2 次拷贝；TLS 加密会使 sendfile 失效（需 kTLS 卸载配合）。追问：为什么 RocketMQ 选 mmap 而 Kafka 选 sendfile——一个是 CommitLog 随机读写、一个是分区日志顺序消费。


### OperatingSystems-001-017 | ★★★★☆

B. 全局变量
C. 打开的文件描述符表
D. 栈空间

**答案：** A、B、C

**解析：**

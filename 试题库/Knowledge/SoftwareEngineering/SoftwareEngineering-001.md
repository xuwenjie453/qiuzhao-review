### SoftwareEngineering-001-001 | ★★★★☆

常见的软件开发模型有哪些？各自适用什么场景？

**答案：**
四种主流：瀑布模型——需求→设计→编码→测试→运维线性推进，文档齐全、阶段评审严格，适合需求明确稳定的项目（传统银行核心系统常见）；增量模型——分批交付可用增量，每批走完整小周期；迭代模型——每轮迭代深化同一产品；敏捷（Scrum 等）——短周期冲刺、拥抱变更、可工作软件优先，适合需求多变、快速反馈的互联网业务。螺旋模型在瀑布基础上加风险分析，适合大型高风险项目。选型本质是"需求确定性 × 变更频率 × 合规文档要求"的权衡——银行内部常呈现"瀑布式管控 + 敏捷式迭代"的混合形态。

**解析：**
考点延伸：V 模型强调测试与开发阶段一一对应（单元测试对应详细设计、集成测试对应概要设计、验收测试对应需求），是国企笔试常见图；敏捷 manifesto 四价值观（个体交互/可工作软件/客户协作/响应变化 高于 过程文档/完整文档/合同谈判/遵循计划）。不要把"敏捷=没有文档"当卖点。


### SoftwareEngineering-001-002 | ★★★★☆

内聚与耦合是什么？好的设计追求什么？

**答案：**
内聚是模块**内部**元素关联的紧密程度，耦合是模块**之间**依赖的紧密程度。好的设计追求**高内聚、低耦合**。内聚从低到高：偶然、逻辑、时间、过程、通信、顺序、功能内聚（功能内聚最优——模块只完成单一功能）；耦合从低到高：非直接、数据、标记、控制、外部、公共、内容耦合（数据耦合最理想——仅传数据参数；内容耦合最差——直接访问另一模块内部）。落地映射：微服务的服务边界（高内聚的业务域、低耦合的接口依赖）、类的单一职责，都是这对概念的现代表述（K-SWE-004、K-MS-002）。

**解析：**
笔试常考"给场景判断内聚/耦合类型"：几个无关代码凑在一个模块=偶然内聚；把初始化代码都放一起（只因同时执行）=时间内聚；模块间通过全局变量共享数据=公共耦合；一个模块改另一个模块内部数据=内容耦合。记忆锚点：耦合越低，一个模块的改动传播半径越小；内聚越高，模块越容易被理解和复用。


### SoftwareEngineering-001-003 | ★★★★☆

软件生命周期各阶段及产出？

**答案：**
问题定义与可行性研究 → 需求分析（产出 SRS 需求规格说明书）→ 概要设计（架构/模块划分）→ 详细设计（数据结构/算法/接口）→ 编码实现 → 测试（单元/集成/系统/验收）→ 运行维护。维护四类：改正性（修 bug）、适应性（环境变化）、完善性（增强功能，占比最大）、预防性（为未来改造）。各阶段"产出文档"与"评审"是传统模型的重点，银行等合规行业对此要求严格。


### SoftwareEngineering-001-004 | ★★★★☆

UML 图有哪几类？常用的是哪几张？

**答案：**
UML 图分两大类：结构（静态）图——类图、对象图、组件图、部署图、包图；行为（动态）图——用例图、活动图、状态机图、序列图（时序图）、通信图。工程最常用三张：类图（静态结构与关系：关联/聚合/组合/泛化/依赖，强弱顺序 依赖<关联<聚合<组合<泛化）、序列图（对象间按时间顺序的消息交互，画接口调用链）、活动图（流程与并行分支，画业务流程）。设计模式与架构讨论中类图+序列图是通用语言。


### SoftwareEngineering-001-005 | ★★★☆☆

代码评审（CR）应该看什么？怎么让 CR 不流于形式？

**答案：**
CR 分层看：①正确性与安全（逻辑缺陷、边界、并发、SQL 注入、敏感信息）——人工重点；②设计与可维护性（职责、命名、重复代码、抽象合理）——人工核心；③规范类（格式、命名风格）——交给工具（CheckStyle/SpotBugs/SonarQube 门禁），人不再管格式。让 CR 有效：小步提交（<400 行关注度高）、MR 描述带"为什么"与自测说明、评审时限与升级机制、重要变更要求设计文档先行、评审意见分级（必须改/建议/讨论）。度量改善而非考核个人：缺陷逃逸率、评审意见采纳率。


### SoftwareEngineering-001-006 | ★★★★☆

技术方案设计文档的必备要素与评审清单

**答案：**
八要素：背景与目标（解决什么、不解决什么）、方案选型（≥2 候选+取舍表）、架构与流程图（含失败路径）、数据模型与变更、接口契约、容量与性能预估（量级推演）、上线计划（灰度/回滚/对账）、风险清单（依赖/单点/合规）。评审三问：失败路径画了吗（不止 happy path）、回滚真的演练过吗、量级数字怎么来的。文档不是形式，是"把思考外化让人攻击"的工具。

**解析：**
常见烂文档特征：只有目标架构图没有现状、只写怎么做不写为什么、无容量数字、无回滚。方案对比的写法：维度表（开发成本/性能/风险/可运维性），明确"为什么否掉 B"。附：跨团队依赖的时间线对齐（外部依赖是最大延期来源）。


### SoftwareEngineering-001-007 | ★★★☆☆

一套完整的 CI/CD 流程是什么样的？

**答案：**
CI（持续集成）：代码合并前自动触发——编译构建 → 静态检查（规范/安全扫描/依赖漏洞）→ 单元测试+覆盖率门禁 → 构建镜像（版本 tag）→ 推送制品库。CD（持续交付/部署）：环境晋升 pipeline——测试环境自动部署+自动化回归 → 预发验证 → 生产发布用安全策略（灰度/金丝雀：先 5% 流量观察指标 → 全量；或蓝绿：双环境切流）。发布配套：回滚一键化（镜像回退）、发布窗口与审批卡点、变更单关联。质量门禁（质量红线）要能举例：覆盖率 <60% 不许合入、高危漏洞阻断、主干必须绿。工具生态：Jenkins/GitLab CI/GitHub Actions + Harbor/Nexus + ArgoCD（GitOps 声明式发布）。


### SoftwareEngineering-001-008 | ★★★★☆

开发模型辨析

某银行核心系统的需求在项目启动前已完全明确且受监管要求文档齐备，最适合采用的开发模型是：

A. 瀑布模型
B. 原型模型
C. Scrum 敏捷开发
D. 探索式开发

**答案：** A

**解析：**
- A：正确。需求明确稳定 + 文档/评审要求高，是瀑布模型的经典适用场景。
- B：错误。原型模型用于需求不清晰、需要快速试错确认需求的场景。
- C：错误。敏捷适合需求多变的业务探索，此处监管文档与固定需求反而让冲刺机制成为负担。
- D：错误。探索式开发适合研究与原型验证，不适用受控交付。

模型选型 = 需求确定性 × 变更频率 × 合规要求。


### SoftwareEngineering-001-009 | ★★★★☆

V 模型对应关系

V 模型中，与"概要设计"阶段相对应的测试级别是：

A. 单元测试
B. 集成测试
C. 系统测试
D. 验收测试

**答案：** B

### SoftwareEngineering-001-010 | ★★★★☆

内聚类型判断

某模块把"日志初始化、数据库连接初始化、缓存初始化"三个无关功能放在同一个函数中，仅在"都需要在系统启动时执行"这一点上相关。该模块的内聚类型是：

A. 功能内聚
B. 通信内聚
C. 时间内聚
D. 偶然内聚

**答案：** C

**解析：**
- A：错误。功能内聚是模块只完成单一功能，与本例相反。
- B：错误。通信内聚要求各部分使用相同的输入/输出数据，本例各初始化互不共享数据。
- C：正确。各部分只因"同一时间段执行"而组合，是时间内聚的教科书定义。
- D：错误。偶然内聚是连执行时间上的关联都没有、纯属随手堆放；本例有明确的"启动时执行"关联。

内聚分级：偶然 < 逻辑 < 时间 < 过程 < 通信 < 顺序 < 功能。


### SoftwareEngineering-001-011 | ★★★★☆

耦合类型判断

模块 A 直接读取并修改模块 B 内部的全局变量来完成协作，这种耦合属于：

A. 数据耦合
B. 公共耦合
C. 内容耦合
D. 标记耦合

**答案：** C

**解析：**
- A：错误。数据耦合仅通过参数传递简单数据，是最理想的低耦合。
- B：错误。公共耦合是多个模块共享同一公共数据环境（全局数据结构），但通过约定接口访问；"直接进入另一模块内部读写"更严重。
- C：正确。一个模块直接访问另一个模块的内部数据或代码，属于最强的内容耦合。
- D：错误。标记耦合传递的是整体数据结构（如整个对象）但只用到部分字段。

耦合分级：非直接 < 数据 < 标记 < 控制 < 外部 < 公共 < 内容。


### SoftwareEngineering-001-012 | ★★☆☆☆

软件维护分类

因操作系统升级导致原有软件需要修改以继续正常运行，这类维护属于：

A. 改正性维护
B. 适应性维护
C. 完善性维护
D. 预防性维护

**答案：** B

**解析：**
- A：错误。改正性维护针对软件自身缺陷。
- B：正确。为适应外部环境（OS/硬件/法规接口）变化而修改，是适应性维护。
- C：错误。完善性维护是增强功能与性能以满足新需求，统计上占比最高。
- D：错误。预防性维护是为未来可维护性主动重构。

维护四类：改正（修错）、适应（环境变）、完善（增强，占比最大）、预防（重构前瞻）。


### SoftwareEngineering-001-013 | ★★☆☆☆

UML 关系强弱

类图中，"汽车类持有发动机类的引用，发动机随汽车销毁而销毁"，两类之间的关系是：

A. 依赖
B. 关联
C. 组合
D. 泛化

**答案：** C

**解析：**
- A：错误。依赖是临时使用（方法参数/局部变量），不持有引用。
- B：错误。关联是长期持有但生命周期独立。
- C：正确。整体持有部分、且部分生命周期与整体绑定（同生共死），是组合关系，UML 中实心菱形指向整体。
- D：错误。泛化是继承关系（is-a），不是持有关系（has-a）。

关系强弱：依赖 < 关联 < 聚合 < 组合；泛化是继承。
